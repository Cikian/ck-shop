## 1. 需求（用户原话）

> 商品详情页的评论区稍微做一些修改：评论只展示 2-3 条，有更多的需要点击按钮查看，
> 点击按钮后在**左侧弹出抽屉**，在抽屉中浏览更多评论；
> 抽屉中要做到**滚动翻页，尽量做到用户无感加载**。

参考图二（某电商详情页的左侧评价抽屉）：左侧滑出、全高、头部有标题/条数与关闭按钮、
列表可滚动、底部是"查看全部评价"的入口位置。

## 2. 结论（改完长什么样）

| 位置 | 行为 |
|---|---|
| 详情页评价区 | 汇总卡（分数 + 星级分布）不动；下方**只预览 3 条**，正文本 4 行截断 |
| 「查看全部评价 · N」 | 总条数 > 3 时才出现；点击 → 左侧抽屉（`USlideover side="left"`） |
| 抽屉头部 | 「用户评价 · N」+ 关闭按钮 + 压缩版汇总条（分数 / 星级 / 5→1 分布） |
| 抽屉列表 | 全部已加载评价，**自己滚动**；距底部 600px 就自动拉下一页（骨架屏占位） |
| 到底 | 「没有更多评价了」；失败时一行提示 + 重试（不打断已看到的评价） |
| 关闭 | ESC / 遮罩 / 关闭按钮都可；再次打开**保留已加载状态**，不重拉第一页 |

## 3. 关键设计决策

1. **正文预览条数 = 3**（`DetailSections.vue` 的 `PREVIEW_REVIEW_COUNT`）。
   2 条信息量不够、5 条会把「商品详情」推得太远；3 条 + 一行 CTA 是这类详情页的常见折中。
2. **抽屉不自己发请求**。沿用既有链路：抽屉 `emit('load-more')` → `DetailSections` 原样转发 →
   页面 `loadMoreReviews()` → `composables/useReviews.ts` 的 `loadMore()`。
   这样"页码 / hasMore / 汇总与列表同源"仍然只有一处实现（旧版「加载更多」按钮走的就是这条路）。
3. **无感加载 = 预取余量 + 双保险触发**：
   - `IntersectionObserver`（`root` = 抽屉滚动区，`rootMargin: 0 0 600px 0`）——
     哨兵进入预取余量就拉下一页，用户真正滚到底时内容已经在 DOM 里；
   - 每次续页结束再量一次"距底距离"：一页不满一屏时继续拉，直到填满或没有下一页；
   - 防重复请求：`inflight` 标记 + 10s 兜底解锁（父层若被并发守卫忽略，不会永久卡死）；
   - 防空转：某次请求回来条数没变（后端页码/条数不一致）→ `stalled`，停掉自动续页只留手动重试。
4. **加载中用骨架屏而不是"加载更多"按钮**：骨架高度接近一条真实评价，内容接上时列表不跳动；
   骨架 `aria-hidden`，另有一条 `aria-live="polite"` 的 sr-only 文案播报一次"加载中"（不逐条朗读）。
5. **抽屉内容用 `#content` 整块自定义**：头部固定、列表区自己滚。
   `DialogTitle` 仍由 `USlideover` 内部的 `VisuallyHidden` 提供（传 `title`），
   所以读屏听到的仍是「用户评价」，焦点由 reka-ui 的 Dialog 负责（打开落到关闭按钮、关闭后回到 CTA）。
6. **格式化函数上收到 `types/shop-review.ts`**（`reviewDisplayName` / `reviewDateText`）：
   正文预览与抽屉渲染同一条评价，昵称/日期必须同源，否则会出现一边"匿名用户"一边空字符串。

## 4. 顺带修掉的既有问题：评价区在 SSR 里根本没渲染

改造过程中发现：**服务端返回的 HTML 里评价区是 `<!---->`**（锚点栏也只有「规格参数 / 商品详情」），
评价要等客户端 hydration 才冒出来 —— 正是长详情页 CLS 的来源。

原因在 `composables/useReviews.ts`：`watch(initialOverview, cb, { immediate: true })` 用的是默认
`flush: 'pre'`。`useAsyncData` 的数据是在 setup 的**异步续体**里落到 ref 上的，默认 flush 会把回调
排进微任务，而 Vue 的 SSR 渲染紧接着 setup 完成就同步执行 —— 渲染那一刻 `summary / records` 还是空的。

修法：两个 watch 加 `flush: 'sync'`（数据落下的那一刻同步套用）。源每次请求只变一次，没有额外开销。
改完 `curl` 详情页即可看到 `id="review"`、3 条预览与 CTA 都在 SSR HTML 里。

## 7. 第二轮修订（按使用反馈）

### 7.1 抽屉太窄 → 加宽

`w-full sm:max-w-[600px] lg:max-w-[min(680px,55vw)]`（原来固定 520px）。
实测抽屉宽度：375 → 365、768 → 600、1024 → 563、1440/1920 → 680（并封顶 55vw，避免 1024 这类窄桌面被抽屉挤没）。
桌面一行能放下 4 张 108px 买家秀，正文每行 30+ 汉字；移动端整宽、3 列宫格。

### 7.2 开/关抽屉时导航栏左右跳动 → `scrollbar-gutter: stable`

原因：抽屉（reka-ui Dialog）会锁 body 滚动，滚动条消失后**视口宽度多出 10px**
（本项目 `::-webkit-scrollbar` 宽 10px），fixed 的 Header 里居中容器跟着重排，看起来像导航栏"抖一下"。

修法：`html { scrollbar-gutter: stable; }`（`app/assets/css/tailwind.css` 的 Base 段，含完整注释）。
滚动条槽位常驻，锁定/解锁前后内容宽度完全一致。实测：

```
HEADER_BEFORE {"linkLeft":16,"docClientWidth":1440,"bodyClientWidth":1430}
HEADER_AFTER  {"linkLeft":16,"docClientWidth":1440,"bodyClientWidth":1430}   → 位移 0px
HEADER_CLOSED {"linkLeft":16,...}                                            → 位移 0px
```

### 7.3 评价支持「买家秀图片」

原来的评价只有纯文本，参考图里的买家秀无处安放。整条链路补齐（**全栈改动**）：

| 层 | 改动 |
|---|---|
| DB | `ck_shop_product_review` 新增 `images varchar(1500)`（JSON 数组字符串，NULL=无图）<br>迁移脚本 `flyway/sql/mysql/V3.9.5_21__shop_review_images.sql`（`information_schema` 判断后动态 ALTER，可重复执行）|
| Java 实体 | `ShopProductReview.images`（String，JSON 字符串） |
| Java 出参 | `StoreReviewVO.images`（`List<String>`）；`toVO` 里 `parseImages()` **服务端解析 + 白名单**（只认 http(s)/站内绝对路径、最多 9 张、空即 null）——不让前端各自 split 一遍 |
| BFF | `types/shop-review.ts`：`StoreReview.images: string[]` + `normalizeReviewImages()`（兼容 `string[]` / JSON 串 / 逗号串，同样白名单 + 上限，脏数据不致崩） |
| 前端 | 新增 `app/components/product/ReviewPhotos.vue`：缩略图宫格 + 点击放大（复用 `ProductImageLightbox`）<br>预览态最多露 3 张、多的折成 `+N`；抽屉里 3 列宫格（移动端）/ 108px 方形（桌面）|

**嵌套浮层的 Esc 冲突**：灯箱打开时把抽屉设成 `:dismissible="!photoLightboxOpen"`，
否则"关图片"会顺带把整个评价抽屉关掉（用户刚滑到的位置全丢）。实测：灯箱里按 Esc → 灯箱关闭、抽屉仍在。

**旧缓存兜底**：`images` 在类型上是必填，但 SWR 30s 的旧 payload 可能没有这个字段，
两处渲染用 `review.images?.length` 守卫、`ReviewPhotos` 内部再兜 `?? []`（缺字段不该让整条评价渲染崩掉）。

## 8. 第三轮修订（按反馈）

### 8.1 「除了导航栏，整个页面还在左右跳」→ 滚动锁的**重复补偿**

第二轮只解决了导航栏（fixed，不吃 body 内边距），页面主体仍会跳，原因是两层补偿叠在一起：

- `html { scrollbar-gutter: stable }` 已经把滚动条槽位常驻了；
- reka-ui 的滚动锁**又**按 `innerWidth − documentElement.clientWidth` 算了一次滚动条宽度，
  写成 `body.style.paddingRight`。

结果：fixed 的 Header 不受 body 内边距影响（不动），而**所有文档流内容整体左移 10px** ——
正好是"除了导航栏整页在动"。

修法：`body { padding-right: 0 !important; }`（inline 样式只能靠 `!important` 覆盖，`tailwind.css` Base 段有注释）。
槽位已常驻，这层补偿本来就是多余的。

验证方式（headless 里 reka 自己算出来是 0，所以**手工模拟**它的 inline 补偿）：

```
BASELINE        bodyPaddingRight=0px  titleLeft=855
WITH_INLINE_PAD bodyInlinePaddingRight=10px  bodyPaddingRight=0px  titleLeft=855  → 位移 0px
OPENED          titleLeft=855 → 位移 0px      CLOSED titleLeft=855 → 位移 0px
```

> 兼容性备注：`scrollbar-gutter` 不支持的旧浏览器（如 Safari < 18.2）上这条 `padding-right: 0` 会让
> 经典滚动条的隐藏重新产生位移；这些浏览器默认是 overlay 滚动条，实际影响可忽略。

### 8.2 抽屉还是不够宽 → 840px

`w-full sm:max-w-[640px] lg:max-w-[min(840px,60vw)]`。实测：1440 → **840**、1920 → 840、1024 → 614、768 → 640、375 → 365。
买家秀在抽屉里放大到 **132px** 方形（840 宽度下一行 5 张），预览仍是 76px。

## 9. 第四轮修订：刷新后图片裂开 / 按钮半天没反应

### 9.1 根因（不是评价模块的问题，是图片缓存把二进制写坏了）

现象：刷新商品详情页，评价里的买家秀先显示**原生裂图图标 + alt 文字**，3~5 秒后才"自己"出现；
这段时间里页面上所有按钮都点不动。

用 Playwright 抓到的证据链：

| 观察 | 数据 |
|---|---|
| `<img>` 命中 `/api/img` 后立刻 error | 10/11 张图在 ~400ms 触发 `error`，`naturalWidth=0` |
| 该 URL 的网络响应其实是 200 | 但 `fetch` 出来用 sharp 解不开：`Input buffer contains unsupported image format` |
| 出错响应的**前 16 字节** | `7b0a2020227479706522` = `{\n  "type": "Buf` |
| 同一 URL 加 `&cb=时间戳`（绕过缓存） | 正常 webp，`304×304`，**10.7 KB**（缓存版 92 KB） |

结论：`nuxt.config` 里 `routeRules: { '/api/img': { swr: 86400 } }` 会把**响应体序列化成 JSON 再回放**，
图片这种二进制被存成 `{"type":"Buffer","data":[82,73,70,70,…]}`，命中缓存时浏览器拿到的就是这段文本 →
`<img>` 立即 error → `ShopImage` 退回**原图 URL**（1200×1200，几百 KB，跨域慢）→ 于是"3~5 秒后图片才出现"。
而 hydration 又要等同一批请求/模块，就表现为"按钮一直没反应"。

### 9.2 修法

1. **删掉 `/api/img` 的 routeRules swr**（`nuxt.config.ts` 里留了醒目注释，禁止再加回来）。
2. **缓存改到接口内部**（`server/api/img.get.ts`）：
   - 进程内 **Buffer LRU**（上限 64MB，单张 > 2MB 不入缓存）——只存字节，不经过任何序列化；
   - **in-flight 去重**：同一 `src+width+quality` 并发只跑一次 sharp（首屏一屏 20+ 张图时很关键）；
   - 浏览器侧仍靠 `cache-control: public, max-age=31536000, immutable`。
     > 顺手把 `swr` 摘掉后，缓存命中时响应体就是 10.7KB 的 webp，而不是 92KB 的 JSON 文本。
3. **加载态不再露原生裂图**（`ReviewPhotos.vue`）：图片在所有图片位铺 `.skeleton` 骨架，
   真实 `<img>` 先 `opacity-0`，`load`（或 `error`）后再淡入 —— 慢网下看到的是骨架，不是破图。

### 9.3 验证（同一页面，dev 3000 vs 生产构建 3001）

| 指标 | dev | 生产构建 |
|---|---|---|
| hydration 完成 | 1.7s（dev 要拉 ~1000 个模块，属 dev 特性） | **0.45~0.50s** |
| 「查看全部评价」可点 | 2.97s | **1.48~1.52s** |
| 评价区图片就绪 | ~2.8s | **~1.34~1.40s** |
| 裂图数量（滚到评价区瞬间） | **0** | **0** |
| `<img>` error 事件（含抽屉里 84 条评价的滚动过程） | **0** | **0** |
| 抽屉宽度 / 续页 | 840px / 84 条 | 840px / 84 条 |

截图：`review-images-1-dev.png`、`review-images-2-prod.png`、`review-images-3-loading-skeleton.png`。

## 10. 第五轮修订：图片加载期间"整页按钮都点不动"

### 10.1 结论先给：不是按钮坏了，是**页面还没水合**，而水合被图片管线拖住了

用 Playwright 量同一页面（1440×900，反复点击图集第 2 张缩略图，直到 `aria-current` 真的切过去）：

| 场景 | DOM 就绪 | 第一次点击生效 | 首屏图片请求 |
|---|---|---|---|
| 修复前（dev，图片全开） | 1756ms | **8339ms** | 27 个 `/api/img` |
| 修复前（dev，屏蔽图片） | 285ms | **1595ms** | 0 |
| 修复后（dev，图片全开） | 339ms | **1815ms** | **5 个** |
| 修复后（生产构建） | 221ms | **708ms** | 5 个 |

机理（关键）：`sharp` 的转码跑在 **libuv 线程池**里，而 SSR 调后端用的 `dns.lookup`、
Vite 读模块用的 `fs` 用的是**同一个线程池**。首屏一次 27 张图、每张都要"抓原图 + sharp 转码"，
4 个并发就能把线程池占满 —— SSR 与模块请求只能排队，水合被拖到 8 秒。
这段时间页面上是 SSR 出来的静态 HTML，**没有任何事件监听**，所以"所有按钮都点不动"
（包括图集缩略图）；图片恰好也在那几秒加载完，于是看起来像"图片加载完才能点"。

### 10.2 修法（三条，都在减少首屏的图片开销）

1. **首屏只加载首屏需要的图**：
   - `ReviewPhotos.vue`：买家秀改为 **IntersectionObserver 闸门**（进入视口下方 600px 才挂 `<img>`），
     SSR/首屏一个请求都不发；并加 `fetchpriority="low"`。
   - `pages/products/[slug].vue`：推荐区 6 张卡片去掉 `:eager="true"`（那块在首屏之外 3000px+，
     eager 会把它提到 high 优先级和首屏 JS 抢连接）。
   - 效果：首屏图片请求 **27 → 5**。
2. **服务端限制图片并发**：`/api/img` 加"上游抓取+转码"闸门（并发 2）+ `sharp.concurrency(1)`，
   把线程池留给 SSR 与 Vite；命中进程内 LRU 时不经过闸门，热缓存零额外开销。
3. **失败不再 500**（顺手修的回归）：上游超时/转码失败一律 **302 回原图**，
   sharp 解不开时**原样透传字节**；`FETCH_TIMEOUT_MS` 4s → 8s。
   否则会抛 500 → `<img>` 立刻 error → 前端退回原图 → 又回到"裂一下再出来"。

另外修掉一个只在生产构建暴露的问题：抽屉匿名头像用的 `lucide:user-round` 没被打进图标包，
`UIcon` 会去 `api.iconify.design` 拉图标、被本站 CSP（`connect-src 'self'`）拦掉，头像位置空一块。
改成**内联 SVG**（静态路径，不依赖网络）。

### 10.3 验证

| 断言 | dev(3000) | 生产构建(3001) |
|---|---|---|
| 图集缩略图首次可点 | **1815ms**（原 8339ms） | **708ms** |
| `<img>` error 事件 | **0** | **0** |
| JS 运行时错误 | **0** | **0** |
| 正文预览 / 缩略图 | 3 条 / 3 张（最新 3 条评价恰好 0/1/2 张图） | 同左 |
| 抽屉宽度 / 续页 | 840px / 10→84 条，到底显示「没有更多评价了」 | 840px / 同左 |
| 开抽屉时页面横向位移 | **0px** | **0px** |

> 说明：dev 下还有约 1.5s 的"水合地板"（Vite 要处理 ~1000 个模块），是开发模式固有成本，
> 与图片无关（屏蔽图片也只到 1.6s）。要在手机/外网验收，请用 `npm run build` + `node .output/server/index.mjs`。

## 11. 第六轮：全屏加载动画（并回答"图片能不能懒加载"）

### 11.1 先说清楚"为什么图片会堵住页面"

图片**本来就是懒加载**的（`ShopImage` 默认 `loading="lazy"`，买家秀还加了视口闸门）。真正堵住的不是浏览器的图片下载，而是两件别的事：

1. **按钮点不动 ≠ 图片在下载，而是"页面还没水合"**。SSR 出来的是静态 HTML，Vue 还没挂上事件监听；
   水合要等 JS 模块下载 + 执行完。
2. **服务端被图片转码占满了**。`/api/img` 的 sharp 转码跑在 libuv 线程池里，和 SSR 调后端的
   `dns.lookup`、Vite 读模块的 `fs` 抢同一个池子；首屏 27 张图一起转码就把池子占满 → 水合被拖到 8s。
   （详见 §10）

所以这轮做了两件事：**把首屏图片请求从 27 降到 5**（§10 已完成），以及**在水合完成前明确告诉用户"正在准备"**。

### 11.2 全屏加载遮罩 `AppPageLoader.vue`

迭代记录（七版；最后一版按用户指定的 Spiral Search 重做）：

| 版本 | 做法 | 结论 |
|---|---|---|
| v1 | 品牌圆 + 轨道光点 + 涟漪 + 山脊线 | ❌ 太丑 |
| v2 | 品牌行 + 进度条 + 假商品卡骨架 | ❌ 空且假 |
| v3 | 品牌圆 / 进度弧 / 字标 三选一 | ❌ 不要文字和 logo |
| v4 | 包裹沿山脊跳三跳 | ❌ 格局小 |
| v5 | 整屏视差山景 | ❌ 方向不对 |
| v6 | 复刻 mesh loader（4 点交织） | ❌ 换成螺旋 |
| **v7（当前）** | **Spiral Search：阿基米德螺旋 + 粒子拖尾** | ✅ 用户指定 |

**来源与取舍**
参考脚本（Spiral Search）里只保留动画本体，删掉与本站无关的内容：深色底 `#050505`、标题、`Archimedean Spiral` 标签、公式代码块、`View All` 按钮。
配色换成站内 token：奶油底 + `--color-brand-300` 螺旋线（低透明度）+ `--color-brand-500` 粒子。

**数学（与参考一致）**
```
θ(t) = 3t
r(t) = 8 + (1 - cos t)(10 + 4s)
x(t) = 50 + cos θ · r(t) · 0.70
y(t) = 50 + sin θ · r(t) · 0.70
```

**关键改动：不跑 requestAnimationFrame**
参考实现每帧重算 480 段路径 + 50 个粒子。这里：
- 螺旋曲线**固化成一条 `path`**（300 段，SSR 期算好，首帧就有）；
- 粒子用 CSS `offset-path: path('<同一条曲线>')` + `offset-distance: 0→100%` 匀速跑，36 个粒子用负延时错开形成拖尾（头部大而实、尾部小而淡，`r = 0.7 + fade^1.25 · 2.3`）；
- 参考里 4.5s 一次的 `detailScale` 脉动，用 `transform: scale(0.96 ↔ 1.045)` 近似（`transform-box: view-box`）。

为什么这点很重要：**加载遮罩存在的意义就是覆盖"水合之前"那段 JS 还没跑起来的时间**。rAF 版本在那段时间里是静止的（页面上什么都不动），纯 CSS 版本从第一帧就在动。附带收益：零 rAF、零字符串拼接、主线程不参与。

**无障碍 / 兜底**：`role="status"` + `aria-live` + sr-only「加载中」；`prefers-reduced-motion` 下粒子隐藏、只留静态螺旋（实测 0 个动画在跑）；`@supports` 之外的浏览器即使不支持 `offset-path`，螺旋线本身仍然可见。
尺寸：`min(70vmin, 420px)`，窄屏 `min(76vmin, 320px)`。
