## 0. 背景与已确认决策

### 现状（Lead 实测）

| 事实 | 证据 |
|---|---|
| 店铺端与管理端**共用** `sys_user` 表 | `LoginController` 只有 `/sys/login` 一个登录入口，管理端 `admin-client/src/api/sys/user.ts` 也打 `/sys/login` |
| 店铺端收货地址按 `sys_user.id` 共享 | `ShopStoreAddressController` 用 `contextResolver.currentUser().getId()`，类注释明确"地址不按店铺隔离" |
| `sys_user.username` **已有 UNIQUE 索引** | `uniq_sys_user_username` |
| `sys_user.email` **已有 UNIQUE 索引** | `uniq_sys_user_email` |
| `sys_user` 已有 `third_id` / `third_type` 字段 | 原本用于第三方登录 |
| 邮件基础设施已就绪 | `spring.mail` 已在各 profile 配置；`EmailSendMsgHandle` 已用 `JavaMailSender` |
| 人机验证 | CikVerify 验证码服务（`POST /api/captcha/challenge`、`/api/captcha/verify`；ticket 一次性） | `ck-server` 的 `captcha-client-spring-boot-starter:1.0.0`；BFF 代理 |
| 库存/订单来源字段已就绪 | `OrderRequestContextResolver` 已解析 storeId / IP / UA / orderSource |

### 用户确认的决策

1. **继续用 `sys_user`**，用「角色 + 部门」隔离前台买家。
2. 新建 **`shop_customer` 角色**，注册时自动赋予。
3. 店铺端用户注册后 **`sys_org_code` 留空**（不分配部门）。
4. 记录**注册来源店铺** + **每次登录来源店铺流水**。
5. Google 登录按**标准 OAuth2 授权码流程**实现；密钥写入**本地 `.env`**，不入仓库。
6. 一并实现**忘记密码**重置流程。
7. `username` 规则：**`u_` + 8 位小写字母数字**（共 10 字符），全局唯一，永不可改。
8. **人机验证改用 CikVerify 行为验证码**（2026-10-19 修订，取代原"保留图形验证码"决策），仅在**发送邮箱验证码**时校验；`appSecret` 只放后端环境变量。

## 2. 后端接口（Java）

新增 Controller：`org.jeecg.modules.shop.account.controller.ShopAccountController`
统一前缀：**`/shop/account`**

> ⚠️ 所有接口必须加入 Shiro 白名单（`jeecg.shiro.excludeUrls`），否则匿名注册会 401。
> 白名单在 `application-dev.yml` 的 `jeecg.shiro.excludeUrls`（以及 prod/docker profile）。

### 2.1 发送邮箱验证码

```
POST /shop/account/email/send-code
Body: {
  email:      string   必填
  scene:      string   必填, 取值: register | login | reset
  ticket:     string   必填  CikVerify 验证通过后签发的一次性 ticket
}
返回: Result<{ cooldownSeconds: number }>
```

规则：
- 先校验 **CikVerify ticket**（`CaptchaTicketService#consume`）：一次性、默认 120 秒、绑定客户端 IP + User-Agent；
  校验失败（含空/过期/重放/IP 或 UA 不符）统一返回「请先完成安全验证」，不做原因细分。
- ticket 由前端先调 `POST /api/captcha/challenge`、`POST /api/captcha/verify` 获得；
  BFF 只代理 Java，浏览器不直连验证码服务。
- 同一邮箱 **60 秒**内只能发一次（Redis key: `shop:email:code:cd:{email}`）。
- 同一邮箱 **每日 10 条**上限；同一 IP **每日 30 条**上限。
- 验证码 **6 位数字**，有效期 **5 分钟**（Redis key: `shop:email:code:{scene}:{email}`）。
- `scene=register` 时，若邮箱已被注册，返回业务错误「该邮箱已注册」。
- `scene=login` / `reset` 时，若邮箱**未**注册，返回业务错误「该邮箱尚未注册」。
- ⚠️ **防用户枚举**：错误文案统一为「邮箱或验证码不可用」级别的模糊提示是不够的——
  本需求明确要求可用性优先，因此保留明确文案，但**必须**配套限流（见上）。

### 2.2 注册

```
POST /shop/account/register
Body: {
  email:            string   必填
  emailCode:        string   必填  6 位邮箱验证码
  password:         string   必填
  confirmPassword:  string   必填  必须与 password 一致
}
返回: Result<{ token, userInfo, storeCode }>
```

行为：
- 校验两次密码一致 → 密码强度（**8-32 位，至少含字母和数字**）。
- 校验邮箱验证码（`scene=register`），成功后**立即删除**该验证码（一次性）。
- 邮箱唯一性检查（`sys_user.email` 已有唯一索引，仍需前置校验以给出友好文案）。
- **username 由系统生成**：`u_` + 8 位小写字母数字，生成后校验唯一性，冲突则重试（最多 10 次）。
- `salt` = 8 位随机串；`password` = `PasswordUtil.encrypt(username, 明文密码, salt)`。
- `realname` 默认取邮箱 `@` 前缀（用户后续可在个人中心改）。
- `status = 1`（正常），`del_flag = 0`。
- `org_code` **留空**（NULL）。
- `register_store_code` / `register_store_id` 从 `StoreResolver` 解析当前店铺写入。
- 自动绑定 **`shop_customer`** 角色（写 `sys_user_role`）。
- 注册成功后**直接签发 token 并登录**（免二次登录）。

### 2.3 邮箱 + 密码登录

```
POST /shop/account/login/password
Body: {
  email:     string  必填
  password:  string  必填（明文，服务端 AES 解密）
}
返回: Result<{ token, userInfo }>
```

行为：
- 按 `email` 查用户（`del_flag=0`）。
- 校验 `status`（冻结则拒绝）与密码。
- 登录失败次数限制**复用** `isLoginFailOvertimes` / `addLoginFailOvertimes` 机制（key 用 email）。
- ⚠️ **必须校验该用户拥有 `shop_customer` 角色**，否则管理端账号可通过店铺端接口登录（虽然无实际提权，但语义混乱）。
- 写入 `ck_shop_login_log`（`login_type=PASSWORD`）。
- ⚠️ **不加图形验证码**（需求 2 明确店铺端不再使用验证码登录）。

### 2.4 邮箱 + 邮箱验证码登录

```
POST /shop/account/login/email-code
Body: {
  email:      string  必填
  emailCode:  string  必填
}
返回: Result<{ token, userInfo }>
```

行为：
- 校验 `scene=login` 的验证码，成功后删除。
- ⚠️ **未注册邮箱不能走验证码登录**（用户已确认，2026-10-15）：
  发码时（`scene=login`）若邮箱不存在，直接返回「该邮箱尚未注册」。
  这与本契约早期草稿"未注册自动建号"的说法不同，**以实现为准**。
  理由：统一商城的邮箱验证码登录若自动建号，用户打错一个字符就会凭空多出一个账号，
  且无法与"注册"入口的意图区分；自动建号只保留给 Google 登录（外部身份已由 Google 验证）。
- 该场景需要 `password` 为空（`pwd_set=0`）的账号也能登录：这类账号由 Google 自动注册产生，
  用户可用邮箱验证码登录后再到个人中心设置密码。
- 写入 `ck_shop_login_log`（`login_type=EMAIL_CODE`）。

### 2.5 Google 登录

```
GET  /shop/account/google/auth-url?redirectUri={前端回调地址}
返回: Result<{ authUrl: string, state: string }>

POST /shop/account/google/callback
Body: { code: string, state: string, redirectUri: string }
返回: Result<{ token, userInfo, isNewUser: boolean }>
```

行为：
- `state` 写入 Redis（`shop:oauth:state:{state}`，TTL 10 分钟，**一次性**），防 CSRF。
- 后端用 `code` + `clientId` + `clientSecret` + `redirectUri` 换 `access_token`。
- 再用 `access_token` 调 Google `userinfo` 端点拿 `sub` / `email` / `name` / `picture`。
- **按 `google_sub` 查用户**：命中 → 直接登录。
- 未命中 → 按 `email` 查：
  - 命中 → **绑定** `google_sub` 到该账号后登录（不重复建号）。
  - 未命中 → **自动注册并登录**（`isNewUser=true`），username 系统生成、`shop_customer` 角色、记录注册来源店铺、`avatar` 存 Google 头像 URL。
- 写入 `ck_shop_login_log`（`login_type=GOOGLE`）。
- ⚠️ **未配置 `google.client-id/secret` 时**，`auth-url` 接口返回明确的业务错误，前端据此禁用按钮。

### 2.6 忘记密码（重置密码）

```
POST /shop/account/password/reset
Body: {
  email:            string  必填
  emailCode:        string  必填（scene=reset）
  newPassword:      string  必填
  confirmPassword:  string  必填
}
返回: Result<{ success: boolean }>
```

行为：
- 校验验证码（`scene=reset`）→ 删除。
- 校验密码强度与一致性。
- 重新生成 `salt`，更新 `password`，更新 `last_pwd_update_time`。
- **清除该用户所有登录态**（清 Redis 中该用户的 token / shiro 缓存）。

### 2.7 个人中心：设置 / 修改密码（已登录）

```
POST /shop/account/password/change
Body: {
  oldPassword:  string  必填（Google 注册用户无密码时可为空）
  newPassword:  string  必填
  confirmPassword: string 必填
}
Header: X-Access-Token（登录态）
返回: Result<{ success: boolean }>
```

> 用于「Google 自动注册」和「邮箱验证码首次登录自动注册」后补设密码的场景。

### 2.8 当前登录用户信息（店铺端专用）

```
GET /shop/account/profile
Header: X-Access-Token（登录态）
返回: Result<{
  id, username, realname, email, avatar, phone,
  hasPassword: boolean,        // 是否已设置密码（前端据此显示"设置密码"还是"修改密码"）
  registerStoreCode: string,   // 注册来源店铺
  createTime: string
}>
```

> ⚠️ 复用 `/sys/user/getUserInfo` 会带回 `sysAllDictItems` 等大量管理端数据，
> 且无法表达 `hasPassword`。店铺端用自己的轻量接口。

| `captcha/verify.post.ts` | POST | `/api/captcha/verify`（成功返回 `{code:200,data:{ticket}}`） |

### 3.1 token 存储（沿用现状，不变）

所有登录成功路径**统一**：
```ts
setCookie(event, 'access-token', result.token, {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  path: '/',
  maxAge: 60 * 60 * 24 * 7,
})
return { userInfo: result.userInfo }
```

### 3.2 `/api/auth/session` 变更

- 校验接口从 `/sys/user/getUserInfo` 改为 **`/shop/account/profile`**（`withAuth: true`）。
- 返回值形状 `AuthSession` **保持不变**（`{ authenticated, userInfo }`），
  中间件与页面不受影响。
- 必须继续保留"非鉴权错误不删 cookie、安全降级"的既有逻辑。

### 3.3 Google 回调

- 前端回调页：`/auth/google/callback`（**新增页面**）。
- BFF 的 `google-callback.post.ts` 接收 `{ code, state }`，
  **redirectUri 由 BFF 服务端根据当前站点 origin 拼接**，不信任前端传入。
- 成功后写 cookie 并返回 `{ userInfo }`。

### 3.4 验证码代理（BFF，2026-10-19 新增）

- `POST /api/captcha/challenge`：body `{ type?, data?: { type? } }`，转发 Java `/captcha/challenge`
  （Java context-path=`/api`，最终外部路径 `/api/captcha/challenge`）。
- `POST /api/captcha/verify`：body `{ id, data }`，转发 Java `/captcha/verify`；成功透传
  `{ code: 200, msg: "OK", data: { ticket } }`。
- 两条代理都必须把**浏览器原始 User-Agent** 与**单个真实客户端 IP**（`X-Forwarded-For`）
  转发给 Java：ticket 在签发时绑定这两项，发信时再次比对。
- body 上限 256KB（超限 413）；IP 限流 challenge 20 次/分、verify 60 次/分。
- Java 业务失败按 SDK 契约返回 HTTP 200 + `{code,msg}`（4000/4001/403/4290/5000），BFF 原样透传；
  Java 连不上/超时/非信封响应才返回 502 + `{code:5000,msg:"验证服务暂不可用"}`。
- 不使用浏览器直连验证码服务，`appSecret` 只存在于 Java 后端环境变量。

## 5.5 Lead 核实的集成事实（实现者必读，避免重复踩坑）

### 5.5.1 签发 token 的正确姿势

`LoginController#userInfo(...)` 是 **private**，且会做大量管理端专属动作
（设置登录租户、查部门、`multi_depart`、加载字典）。**店铺端不要复用、也不要复制它**。

店铺端只需最小集：

```java
String token = JwtUtil.sign(username, sysUser.getPassword(), CommonConstant.CLIENT_TYPE_PC);
redisUtil.set(CommonConstant.PREFIX_USER_TOKEN + token, token);
redisUtil.expire(CommonConstant.PREFIX_USER_TOKEN + token, JwtUtil.EXPIRE_TIME * 2 / 1000);
```

> ⚠️ `JwtUtil.sign(username, password, clientType)` 的第二个参数是**加密后的密码哈希**（不是明文），
> 它参与签名。因此**重置密码后旧 token 会自然失效**（哈希变了），这正是我们想要的副作用。

响应里返回 `obj.put("token", token)` + `obj.put("userInfo", sysUser)` 即可。

### 5.5.2 新用户的密码哈希问题（关键）

`JwtUtil.sign` 需要一个非空密码哈希。而「邮箱验证码首次登录自动注册」与
「Google 自动注册」的用户**没有设置密码**。处理方式：

- 自动注册时**也要生成一个随机密码哈希**（`PasswordUtil.encrypt(username, <随机32位串>, salt)`），
  保证 `password` 字段非空、token 可签发，且**无人知道该明文**（等于没有密码）。
- `hasPassword` 的判定**不能**只看 `password` 字段是否为空。
  正确做法：新增一列标记，或复用「密码是否为系统随机占位」的约定。
  → **契约裁决**：在 `sys_user` 再加一列
  ```sql
  ADD COLUMN `pwd_set` tinyint(1) NULL DEFAULT 1 COMMENT '是否由用户设置过密码: 1-是, 0-系统随机占位'
  ```
  自动注册时写 `0`；用户通过「注册/重置密码/修改密码」设置密码后写 `1`。
  `/shop/account/profile` 的 `hasPassword` 即读此列。
  （旧数据 `DEFAULT 1`，语义正确：老用户都有真实密码。）

### 5.5.3 图形验证码校验算法（逐字照抄）

`LoginController#validateCaptcha` 是 private。在 `ShopAccountController` 内自实现等价逻辑：

```java
String lowerCaseCaptcha = captcha.toLowerCase();
String keyPrefix = Md5Util.md5Encode(checkKey + jeecgBaseConfig.getSignatureSecret(), "utf-8");

Object checkCode = redisUtil.get(realKey);

```


## 5.6 ⚠️ Flyway 现状（Lead 实测后**修正**，以此节为准）

> **勘误说明**：本节最初写成"重启后端会被 Flyway 中断启动"的结论，**那是错的**。
> Lead 随后实读了 `FlywayConfig` 与各 profile 的 `autoconfigure.exclude`，结论如下。

### 实测事实

1. **`FlywayAutoConfiguration` 在 dev / prod / docker / test 四个 profile 里都被显式排除**
   （`spring.autoconfigure.exclude`），Flyway 改由项目自研的
   `org.jeecg.config.flyway.FlywayConfig`（`@PostConstruct`）手工驱动。
2. `FlywayConfig.migrate()` **把 `FlywayException` 捕获后只打 error 日志**（line 129-131），
   **不会中断应用启动**。所以"迁移失败导致后端起不来"这个担心不成立。
3. `spring.flyway.enabled`：dev=`true`、test=`true`、docker=`true`、prod=`false`。
4. `flyway_schema_history` 最后一条是 **`3.9.5.2`**，但 `V3.9.5_4`~`V3.9.5_11` 对应的表
   **已存在于库中**（手工执行过、元数据没跟上）。库里已有真实数据：3 店铺 / 6 订单 / 1 地址。
5. 这些脚本内部普遍使用 `CREATE TABLE IF NOT EXISTS`，因此重复执行**大多无害**，
   但含 `INSERT`（菜单/权限/角色）的脚本可能产生重复数据。

### 真正的风险（修正后）

**不是"启动失败"，而是"迁移静默不生效"**：若 `V3.9.5_4`~`V3.9.5_11` 中任一步失败，
`flyway.migrate()` 会在该点中止并抛异常 → 被 catch 掉 → 只留一条 error 日志 →
**`V3.9.5_12` 也不会被执行**，而应用照常启动。此时注册接口会报
"请先执行数据库迁移脚本 V3.9.5_12"（backend-account 已实现该友好提示）。

### 处置方案（Lead 决策）

直接**手工执行** `V3.9.5_12__shop_customer_account.sql`，并补写 `flyway_schema_history` 记录：
- 优点：完全可控、不依赖 Flyway 对历史状态的推断、不会被前面的脚本卡住；
- 已备份数据库（`mysqldump`，8.66 MB，含 `sys_user`/`sys_role`/`flyway_schema_history` 等全部关键表）
- 执行后校验：`sys_user` 新增 4 列（`register_store_code`/`register_store_id`/`google_sub`/`pwd_set`）、
  `uniq_sys_user_google_sub` 索引存在、`shop_customer` 角色存在、`ck_shop_login_log` 表存在

> 本节处置记录会在最终交付说明中同步给用户，作为"运维需知"。
