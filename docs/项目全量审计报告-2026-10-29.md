# ck-shop 项目全量审计报告

- 审计日期：2026-10-29
- 审计对象：当前工作区（包含尚未提交的地址与国家/地区级联改动）
- 审计方式：全工作区规则扫描 + 核心链路人工审查 + 依赖漏洞审计 + 可用的构建与脚本验证
- 代码变更：未修改任何项目源代码；本文件仅为审计报告

## 一、结论摘要

当前项目已经具备较完整的电商领域设计，订单、库存、支付回调、多店铺数据域、BFF 会话和 CSRF 等位置能看到明确的防护意识。但**按仓库现状，生产环境没有可用的真实支付渠道，且存在可绕过的图片代理 SSRF、同源 SVG 主动内容、退款库存虚增、生产高危配置和较多依赖漏洞**，不建议不经整改直接作为可收款的生产商城上线。

本次共记录 23 项问题与优化点：

| 级别 | 数量 | 含义 |
|---|---:|---|
| P0／阻断 | 1 | 核心生产流程无法完成 |
| P1／高 | 7 | 可直接或条件性造成较严重安全、资金、库存或主机风险 |
| P2／中 | 10 | 明确的逻辑缺陷、安全边界缺口或重要工程风险 |
| P3／优化 | 5 | 性能、并发边界、可维护性与交付可靠性改进 |

### 建议最先处理的五件事

1. 明确真实支付实现并完成端到端收款验证，不能只修改渠道配置。
2. 关闭或重构图片代理的 SSRF 与 SVG 同源输出风险。
3. 修正退款库存模型，区分“仅退款”和“退货退款后入库”。
4. 清理生产弱口令，关闭 AI 高危节点，升级 Nuxt／Vue／sharp 等依赖。
5. 为订单、支付、退款、账号和多店铺隔离补充自动化回归测试。

## 二、P0：阻断上线的问题

### P0-01　生产环境没有可用的真实支付闭环

**结论：已确认。**

- `PaymentGateway` 的唯一实现是 `MockPaymentGateway`，微信和支付宝只有预留常量，没有真实网关实现。
  - `ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/order/pay/impl/MockPaymentGateway.java:69`
  - `ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/order/constant/PayChannel.java:19-24`
- 生产配置将模拟支付关闭，并把默认渠道留空。
  - `ck-server/jeecg-module-system/jeecg-system-start/src/main/resources/application-prod.yml:421-427`
- 店铺支付页仍然把渠道硬编码为 `MOCK`，即使后续只增加真实网关，页面也仍会请求模拟渠道。
  - `nuxt-shop/app/pages/checkout/pay.vue:484-507`
- `prepay` 在没有默认渠道时会直接报错。
  - `ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/order/service/impl/ShopPaymentServiceImpl.java:181-192`

**影响：** 用户可创建订单，但无法在生产环境完成真实付款；整个收款业务不可用。

**建议：** 实现真实渠道的预支付、验签回调、主动查询、关闭和退款能力；让前端按后端可用渠道选择支付方式；用沙箱完成“下单→付款→回调→发货→退款→对账”的端到端验收后，再开放生产下单。

## 三、P1：高优先级问题

### P1-01　图片代理可通过重定向或 DNS 重绑定绕过 SSRF 防护

**结论：已确认代码路径成立。**

`nuxt-shop/server/api/img.get.ts` 只在 `assertPublicUrl()` 中检查初始 URL 的 DNS 结果，随后直接使用默认会自动跟随重定向的 `fetch(url)`：

- 初始地址检查：`img.get.ts:59-85`
- 实际抓取：`img.get.ts:180-184`

初始公网 URL 可返回 302 到 `127.0.0.1`、内网服务或云元数据地址，重定向目标没有再次校验。DNS 在检查与实际连接之间发生变化时，也没有“连接到已校验 IP”的约束。

**影响：** 未认证调用方可诱导 BFF 访问内网 HTTP 服务；若响应被当作图片返回，还可能造成内网内容泄露。

**建议：** 禁止自动重定向并逐跳重新校验；将 DNS 解析与连接目标绑定，覆盖全部非公开地址范围；最好只允许已配置的图床域名，而不是开放任意公网 URL。

### P1-02　外部 SVG 被原样同源返回，可形成主动内容／XSS 风险

**结论：已确认危险输出方式。**

图片代理对 SVG 不做清洗，直接以 `image/svg+xml` 返回：

- `nuxt-shop/server/api/img.get.ts:206-209`
- 同源响应及长期公开缓存：`img.get.ts:238-242,256-260`

全局 CSP 又允许 `'unsafe-inline'` 脚本：

- `nuxt-shop/server/middleware/security-headers.ts:52-69`

攻击者若能控制外部 SVG，可引导受害者直接打开商城同源 `/api/img?src=...` 地址。SVG 作为独立文档打开时可能执行主动内容；同源身份使其风险远高于普通第三方图片。

**影响：** 可能执行同源脚本、发起带用户身份的请求或展示伪造内容。`httpOnly` 只能防止直接读取 token，不能阻止同源操作。

**建议：** 不透传 SVG；可信场景下先使用成熟清洗器处理，或以附件、`Content-Disposition` 和严格 CSP 隔离；移除不必要的 `'unsafe-inline'`。

### P1-03　退款成功即回补库存，未区分退货是否实际入库

**结论：已确认业务逻辑。**

退款成功后无条件调用 `restoreStockByRefundLines()`：

- `ck-server/.../ShopRefundServiceImpl.java:590-597`
- 实际回补：`ShopRefundServiceImpl.java:611-650`

该逻辑不判断订单是否已发货、是否已完成，也没有“退货申请、退货收货、质检、入库”状态。退款类型只有全额／部分，不足以表达“仅退款”与“退货退款”。

**影响：** 商品未退回也会增加可售库存，造成库存虚增和后续超卖；属于资金与履约一致性问题。

**建议：** 仅对未发货取消场景自动释放库存；已发货订单应在仓库验收退货后再入库，并保留退货物流与质检记录。

### P1-04　生产环境显式启用 SQL、命令行和代码执行类 AI 节点

**结论：已确认高风险生产配置。**

- `application-prod.yml:244-248`：`jeecg.ai-rag.allow-sensitive-nodes: sql,stdio,code`
- 命令执行能力存在于 `CommandExecUtil.java:94-104`。

这些节点并非默认安全能力，而是可直接影响数据库和主机的高危能力。配置注释自身也说明其 RCE 风险。

**影响：** 一旦 AI 流程编辑／执行权限过宽、账号被盗或流程输入可被低信任用户控制，可能扩大为数据库破坏或服务器命令执行。

**建议：** 生产默认全部关闭；按独立服务、最小权限账号、节点白名单和人工审批逐项开放；不要把高危流程暴露给匿名分享应用。

### P1-05　生产及模块配置中仍有硬编码弱口令和明文凭据

**结论：已确认。**

- 生产数据库使用本机 `root` 账号和硬编码弱口令：`application-prod.yml:145-149`。
- AI 模块资源文件还包含 Druid 默认口令、数据库口令、Redis 地址与密码：
  - `ck-server/jeecg-boot-module/jeecg-boot-module-airag/src/main/resources/application.yml:11-17,52-71`
- 管理端签名密钥是浏览器可见的固定公开值：`admin-client/src/utils/encryption/signMd5Utils.js:1-3`。它不能作为真正的客户端身份凭证。

**影响：** 配置被直接使用时，数据库与缓存面临弱口令风险；仓库、镜像或历史泄露会扩大影响。前端签名可被任意访客复现，不应被当作安全边界。

**建议：** 全部改为部署环境或密钥管理注入；轮换已进入仓库的凭据；数据库使用最小权限账号；不要依赖浏览器内签名实现鉴权。

### P1-06　用户密码采用可逆、低成本的 legacy PBE 方案

**结论：已确认。**

`PasswordUtil` 使用 `PBEWithMD5AndDES`、固定 1000 次迭代，并同时提供加密与解密能力：

- `ck-server/jeecg-boot-base-core/src/main/java/org/jeecg/common/util/PasswordUtil.java:22-37,93-137`
- 商城注册、登录、改密均使用该实现：`ShopAccountServiceImpl.java:346-347,935-943,1236-1246`

**影响：** 数据库泄露后，密码可逆且离线破解成本低；用户在其他网站复用的密码也会受到威胁。

**建议：** 迁移到 Argon2id、bcrypt 或足够工作因子的 PBKDF2；采用“登录成功后渐进重哈希”的迁移方案，并配套旧 token 失效和口令轮换策略。

### P1-07　店铺端锁定依赖存在多项已知 critical／high 漏洞

**结论：已由本次 `npm audit` 确认；实际可利用性需按功能复核。**

店铺端审计结果为 **77 个受影响依赖条目：critical 5、high 26、moderate 41、low 5**。重点包括：

- `nuxt 4.4.8`：公告覆盖 Server Island 模板注入 RCE、跨用户 SSR 数据泄露、未认证 DoS 等；多个公告在 4.5.1／4.6.x 修复。
- `vue 3.5.39`：SSR 属性名 XSS 公告，修复版本为 3.5.42。
- `sharp 0.34.5`：libvips／libheif／librsvg 多个公告，当前审计建议 0.35.5；本项目公开图片代理和头像上传都实际使用该库。
- 另有 `@nuxt/devtools`、`seroval`、`vue-i18n`、`@tiptap/core` 等传递依赖公告。

**影响：** 既包含生产运行时风险，也包含开发机和构建链风险。公告数量不等于可在此项目全部直接利用的数量，但 Nuxt 与 sharp 属于实际核心链路，不能忽略。

**建议：** 先在隔离环境升级并跑完整回归，优先处理 Nuxt、Vue、sharp；明确哪些功能未使用（例如 Server Island、DevTools），记录剩余风险，不要简单以“传递依赖”为由全部关闭告警。管理端本次 `pnpm audit` 未返回已知漏洞，但仍需保持定期扫描。

## 四、P2：中优先级问题

### P2-01　同一订单可在不同渠道建立多笔有效支付，存在重复付款设计缺口

**结论：已确认代码路径；接入多个真实渠道前必须处理。**

- 查找待支付单使用 `orderId + channel`，而不是仅 `orderId`：`ShopPaymentServiceImpl.java:194-202,296-303`。
- 切换渠道后可创建另一笔有效支付单。
- 第二笔支付成功时，订单已不处于 `WAIT_PAY`，系统只记录“掉单告警”，不会自动退款：`ShopPaymentSettlementService.java:263-279`。

**影响：** 用户在微信和支付宝分别付款时会形成重复收款，只能人工处理。

**建议：** 每个订单全局只允许一笔有效支付单；换渠道前先查询并关闭旧渠道支付；以累计渠道实收为资金事实，明确超额支付自动退款策略。

### P2-02　下单与退款幂等键作用域不完整，且未校验请求内容一致性

**结论：已确认。**

- 下单只按全局 `idempotentKey` 查询，命中后只校验用户，不校验店铺或本次商品内容：`ShopOrderServiceImpl.java:340-351`。
- 退款只按全局 `requestId` 查询，命中后只校验用户，不校验订单：`ShopRefundServiceImpl.java:131-145`。
- 数据库同样使用全局单列唯一索引：`ck-server/db/ck-shop-order.sql:239,416`。

**影响：** 同一账号跨店铺或跨订单复用键时，会拿到旧订单／旧退款单；异常碰撞时还可能返回与本次意图不符的数据。

**建议：** 订单使用 `(user_id, store_id, idempotent_key)`，退款使用 `(user_id, order_id, request_id)` 的唯一约束；保存并比对请求指纹，键相同但内容不同必须拒绝。

### P2-03　邮箱验证码“一次性消费”不是原子操作

**结论：已确认。**

`consumeCode()` 先 `get` 校验，再单独 `del`：

- `ShopEmailCodeService.java:165-181`

两个并发请求都可能在删除前通过验证。注释所称“配合有效期已足够”并不能保证一次性语义。

**影响：** 同一验证码可被并发用于多次登录、注册或改密；虽然部分流程还有唯一索引和 Google code 限制，但基础安全契约已被破坏。

**建议：** 使用 Redis Lua 原子 `GET + compare + DEL`，或原子 `GETDEL` 后按结果处理；补充真实并发测试。OAuth state 的读取后删除也应采用同类原子实现。

### P2-04　Google 按邮箱绑定既有账号时未要求邮箱已验证

**结论：已确认。**

- `emailVerified` 会被解析：`ShopGoogleOAuthService.java:265-271`。
- 但绑定既有账号的分支完全不检查该值：`ShopAccountServiceImpl.java:463-481`。

**影响：** 在身份提供方返回未验证邮箱的场景下，可能把不安全的邮箱声明绑定到已有账号，形成账号接管边界。

**建议：** 只有 `sub` 已绑定或 `email_verified=true` 时才允许自动登录／绑定；其他情况要求先通过本站邮箱验证码证明所有权。

### P2-05　店铺端找回密码可重置管理端账号，角色隔离口径不一致

**结论：已确认，属于设计选择带来的边界风险。**

登录明确要求 `shop_customer`，但重置密码仅记录警告、并不拒绝非店铺角色：

- 登录角色限制：`ShopAccountServiceImpl.java:1097-1118`
- 重置放行：`ShopAccountServiceImpl.java:1120-1133`
- 匿名发码只判断邮箱是否存在，不判断角色：`ShopAccountServiceImpl.java:211-220`

**影响：** 店铺端成为管理端账号的备用改密入口，扩大管理账号攻击面，与“管理端账号不能走店铺端”的隔离目标不一致。

**建议：** 明确统一账号策略；若强调管理端隔离，发码和改密都应拒绝非 `shop_customer`，管理端改密走独立、更严格的流程。

### P2-06　公开图片处理存在内存与解码资源耗尽风险

**结论：已确认。**

- `response.arrayBuffer()` 会先把整个响应读入内存，之后才检查 12 MB 上限：`img.get.ts:196-204`。缺少 `Content-Length` 时，下载体积没有被提前约束。
- `sharp` 未限制输入像素数，也未做解码维度预检：`img.get.ts:211-216`。
- 接口无需登录，且可处理任意公网 URL。

**影响：** 大响应或压缩图片炸弹可消耗 BFF 内存、CPU 和线程池，造成拒绝服务。

**建议：** 流式下载并硬截断；限制像素、帧数和解码时间；设置队列上限与 per-IP 限流；超限时返回受控错误而非继续做昂贵处理。

### P2-07　管理端仍有未清洗的 `v-html` 输出，存储型 XSS 防线不统一

**结论：输出端风险已确认；具体利用性取决于写入权限。**

- 通知表单直接渲染模板内容：`admin-client/src/views/system/notice/NoticeForm.vue:7-9`。
- 部分系统消息直接渲染 `msgContent`：`admin-client/src/views/system/message/components/SysMessageList.vue:35-50`。

这些位置没有经过统一 HTML 清洗。项目其他位置已有清洗函数，说明当前是覆盖不一致，而不是没有可用方案。

**影响：** 若低权限用户、流程数据或被污染的模板能控制内容，可在管理端持久执行脚本；管理端 localStorage token 会进一步扩大后果。

**建议：** 所有富文本统一在输出端经过同一份白名单清洗；逐个核对写入权限；对公告、流程消息增加恶意 HTML 回归用例。

### P2-08　BFF 内联下单会丢弃国家／省州／城市编码

**结论：已确认当前未提交地址改动中的接口缺陷。**

Java 已支持 `receiverCountryCode`、`receiverProvinceCode`、`receiverCityId`、`receiverCountryName`：

- `ck-server/.../OrderSubmitDTO.java:58-94`

但 BFF 的 `SubmitBody` 和转发 payload 没有这些字段：

- `nuxt-shop/server/api/order/submit.post.ts:28-47,117-127`

**影响：** 通过 BFF 内联地址下单时，国家与地区编码被静默丢弃，无法按新契约生成完整订单快照。当前结算页主要使用地址簿，因此这是 API 路径缺陷，不应被页面主路径掩盖。

**建议：** 对齐 DTO、BFF 类型与 payload，增加“内联级联地址”和“手填国家”的契约测试。

### P2-09　管理端 token 长期保存在 Web Storage，XSS 后可直接窃取

**结论：已确认。**

- token 通过 Persistent／localStorage 体系读取：`admin-client/src/utils/auth/index.ts:28-35`。
- 项目自身注释也说明 token 有效期为 7 天，XSS 可直接读取：`admin-client/src/utils/idleLogout.ts:1-14`。
- 30 分钟空闲登出只清理本地状态，不会让已窃取 token 立即失效。

**影响：** 任一管理端 XSS 都可转化为持续的后台会话劫持。

**建议：** 优先改为管理端 BFF + `httpOnly + Secure + SameSite` cookie；短期缩短 token  TTL、支持按用户撤销全部会话，并先消除输出端 XSS。

### P2-10　商城核心模块没有自动化回归测试

**结论：已确认。**

- `ck-shop` 模块下没有 `src/test` 测试。
- `nuxt-shop` 没有单元／组件测试脚本。
- 管理端只有极少量既有测试，未覆盖商城核心流程。
- Maven 根配置默认 `skipTests=true`：`ck-server/pom.xml:42,659-665`。
- 未发现覆盖订单、支付、退款、账号、库存和多店铺隔离的 CI 检查。

**影响：** 当前大量并发、资金和权限不变量只能依赖人工阅读与手工验证，重构时极易回归。

**建议：** 优先建立以下测试矩阵：重复下单、跨店幂等键、双渠道付款、重复回调、最后一秒付款与关单竞争、部分退款、退货入库、越权访问、验证码并发消费、图片 SSRF 重定向。

## 五、P3：性能与工程优化项

### P3-01　分类翻译列表把分类全表读入内存，再构造超大 IN 条件

**位置：** `ShopCategoryTranslationController.java:67-77,113-121,205-217`。

每次列表和导出都先 `selectList(null)` 读取全部分类，在 Java 过滤后把所有可见 ID 放进 SQL `IN`。数据增长后会增加内存、网络和 SQL 长度压力。

**建议：** 改为数据库内 `JOIN` 或 `EXISTS` 加组织前缀条件；导出采用流式／分批处理。

### P3-02　默认地址唯一性只靠“先更新、后清理”，并发下可产生多个默认地址

**位置：** `ShopUserAddressServiceImpl.java:128-136,195-203,265-275,315-321`。

新增和设默认没有用户级锁，也没有数据库唯一约束。两个并发请求可能分别把不同地址设为默认，再互相清理，最终结果依赖时序。

**建议：** 使用用户级行锁或独立默认地址引用表，并补充并发测试；定期增加数据一致性修复任务。

### P3-03　前端样式与包体积已有明确预算失败和大包警告

- `npm run check:css`：当前产物 **243.3 KB，超过 240 KB 预算 3.3 KB**。
- 管理端构建虽成功，但出现多个大 chunk：SwaggerUI 约 1367 KB、TinyMCE 约 1069 KB、ECharts 约 760 KB（构建输出中的原始文件大小）。
- 管理端还有 `minify.compress` 配置类型、非 module 的 `_app.config.js`、`:deep` CSS 伪类等警告。

**建议：** 将预算检查接入 CI；按路由和真实使用场景拆包，避免首屏加载编辑器、Swagger 和图表；清理构建警告，避免未来升级后变成硬错误。

### P3-04　核心类过大且存在混合换行，维护成本较高

- `ShopProductServiceImpl.java` 约 2088 行，且工具检测到混合／孤立 CR 换行。
- `ShopOrderServiceImpl.java` 1767 行、`ShopAccountServiceImpl.java` 1330 行、`ShopRefundServiceImpl.java` 1104 行。

大量业务规则与长篇注释集中在单个类中，增加审查和修改时的遗漏风险。

**建议：** 按算价、快照、订单状态、支付协调、账号凭据、资料管理等职责拆分类；统一换行与静态检查。拆分应保持行为不变，并先补测试。

### P3-05　部署与构建可复现性仍需完善

- 根目录 `docker-compose.yml` 明确指向不存在的 `./jeecg-boot`、`./jeecgboot-vue3`，当前不可运行：`docker-compose.yml:1-6`。
- README 只要求 Node/npm，但本次店铺端 `nuxt build` 在当前环境直接报“缺少 Bun”，构建前置与实际工具链不一致。
- 后端本机缺少 JDK/Maven，无法仅凭仓库脚本完成验证；建议提供 Maven Wrapper 和统一工具链说明／容器构建。

**建议：** 删除或修复失效 Compose 文件；锁定并文档化构建运行时；提供可重复的容器化构建和一键检查脚本。
