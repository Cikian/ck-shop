## 2. 数据模型

新增一张表 `ck_shop_favorite`（Flyway：`V3.9.5_11__shop_favorite.sql`；手工执行版：`ck-server/db/ck-shop-favorite.sql`）。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | varchar(36) | 主键（`IdType.ASSIGN_ID`） |
| `user_id` | varchar(36) | 用户ID（`sys_user.id`） |
| `username` | varchar(50) | 账号冗余，后台统计直接展示 |
| `store_id` | varchar(36) | 店铺ID，收藏按店铺隔离 |
| `product_id` | varchar(36) | 商品ID |
| `org_code` | varchar(64) | 收藏时商品归属部门（快照，排查用） |
| `create_by/create_time/update_by/update_time` | — | 审计字段 |
| `del_flag` | tinyint(1) | 0-已收藏 / 1-已取消收藏（软删除） |

索引与唯一键：

- `uk_favorite_user_store_product (user_id, store_id, product_id)` —— **不含 `del_flag`**；
- `idx_favorite_user_store_time (user_id, store_id, del_flag, create_time)` —— 前台列表的驱动索引；
- `idx_favorite_product (product_id, del_flag)` —— 按商品反查（运营排查/统计）。

### 2.1 四个刻意的设计决定

1. **收藏的主体是商品，不是 SKU**。用户在详情页点收藏时往往还没选规格，把 SKU 塞进唯一键会逼前端"先选规格才能收藏"。
2. **唯一键不含 `del_flag`**：取消收藏是软删除，旧行仍占着键位；再次收藏时必须**复活旧行**，否则 `INSERT` 直接撞唯一键（与购物车的取舍完全一致）。
3. **只存关系、不存商品快照**：标题/封面/价格/库存/上下架一律在列表接口实时读取。存快照必然出现"收藏里还躺着一件三个月前下架、价格还是旧价的商品"。
4. **收藏数是冗余计数**：`ck_shop_product.favorite_count` 由收藏 Service 在**同一个事务**里增量维护（`+1` / `-1`，且下限夹到 0），与关系表同生共死；接口返回的计数是变更后**回读**出来的真实值，不做前端式心算。

## 3. 接口清单

### 3.1 前台（`/shop/favorite/store/**`，**需登录**）

| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| GET | `/shop/favorite/store/status` | `productId` | `FavoriteStatusVO` |
| POST | `/shop/favorite/store/toggle` | `{ productId }` | `FavoriteStatusVO`（**操作后**的最终状态） |
| GET | `/shop/favorite/store/list` | `pageNo`、`pageSize`、`lang` | `IPage<StoreProductCardVO>`（与商品列表**同构**） |

`FavoriteStatusVO = { productId, favorited, favoriteCount }`。

**刻意不加 `@IgnoreAuth`**：收藏必须知道"是谁收藏的"，匿名收藏没有地方存。未登录由 Shiro 直接 401，前端据此引导登录（与购物车接口同一口径）。

### 3.2 Nuxt BFF

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/favorite/status?productId=` | 归一化后返回收藏状态 |
| POST | `/api/favorite/toggle` | 取反并返回最终状态 |
| GET | `/api/favorite?pageNo=&pageSize=` | 我的收藏，复用 `normalizePage`（与 `/api/products` 同一套卡片结构） |

归一化收敛在 `nuxt-shop/types/shop-favorite.ts`：`favorited` 按"白名单为真"解析（`true` / `1` / `'1'` / `'true'` / `'Y'`），避免 Java `Boolean` 的多种序列化形态被误判。

## 4. 关键契约

### 4.1 幂等

`toggle` 是取反语义，但同一状态重复提交不会把关系表或计数搞乱：

- 已收藏 → 再收藏：**无操作**（不新增行、不加计数）；
- 未收藏 → 再取消：`softDeleteByProduct` 影响 0 行 → **计数不减**；
- 取消过 → 再收藏：走 `restoreFavorite` **复活原行**（`create_time` 保留首次收藏时间）。

`favorite_count` 只在"关系表确实发生变化"的那一次增减（靠 UPDATE 的受影响行数判断），因此连续点击不会把数字刷歪。

### 4.2 可见性（多店铺隔离）

所有读写都先经 `IShopProductService.getStoreCard(storeOrgCode, productId, lang)` 做准入：

- 商品存在且未软删除；
- 商品归属落在**当前店铺绑定部门**的前缀域内（`sys_org_code LIKE 'orgCode%'`）；
- 商品处于上架状态。

任一不满足直接抛业务异常（"商品在当前店铺不存在或已下架!"）。没有这一步，收藏接口就是一个能用任意 `productId` 探测别店商品的越权入口。

`storeOrgCode` 解析不到（店铺没绑部门）时：**读接口降级为空列表，写接口直接拒绝**，绝不退化成"不过滤店铺"。

### 4.3 列表口径

- 分页在**关系表**上做（按 `create_time DESC, id DESC`），商品信息随后批量实时查询并按收藏顺序重排；
  先分页商品再筛收藏会在"收藏了已下架商品"时出现空页，用户会以为收藏丢了。
- 已下架 / 已软删除的商品会自动从列表消失（与商品列表同一套过滤条件）。
- `total` 是关系表的收藏总数（含已下架），极端情况下可能出现"total=3 但只显示 2 件"——有意的取舍：与其把用户真实的收藏数藏起来，不如让列表诚实地少一行。

## 5. 前台交互

### 5.1 规格：同一规格直接切换

判定规则（`types/shop-product.ts`）：

```
规格值 V 可选 ⇔ ∃ 可售组合（saleable='Y' && stock>0）同时包含
              V 与"当前已选的**其它规格**的值"（按 specId 排除 V 所属规格的旧值）
```

- 点击同规格的另一个值 = **直接替换**，不需要先取消；前提是存在对应组合；
- 若「该值 + 其它规格已选值」没有可售组合，仍然置灰不可选（这是硬约束）；
- 点击当前已选值 = 取消选择（保留原来的显式清空路径）；
- 已选中的值永远可点，不参与置灰。

自测：`cd nuxt-shop && node temp/spec-availability.selfcheck.ts`（84 条断言，含真实演示商品的置灰矩阵与同规格切换矩阵）。

### 5.2 立即购买

- 与「加入购物车」共用同一套可用性判断（登录态 / 规格选全 / 组合可售），不会出现"能加购却买不了"；
- 写结算快照时 `cartItemId = ''`：后端 `submit` 对空 `cartItemIds` 的处理是"不清任何购物车条目"，因此**不会误删购物车里的同款商品**；
- 金额仍由结算页调 `/api/order/preview` 由服务端计算，前端不参与任何金额运算；
- 快照读写收敛在 `composables/useCheckoutSnapshot.ts`（购物车页 / 详情页 / 结算页三处共用一个 key 与一份归一化逻辑）。

### 5.3 收藏

- 详情页两处入口：图集右上角心形 + 操作区「加入收藏 / 已收藏」按钮，状态完全同步；
- 操作区布局（用户指定，两行两列）：
  - 第一行 = 数量输入框 + 立即购买（`flex`：数量框定宽，购买按钮占满剩余宽度）
  - 第二行 = 收藏 + 加入购物车（`grid-cols-2`：**严格等宽**；用 grid 而非 flex 是因为 flex 项的
    `min-width:auto` 会让两个文案长度不同的按钮一宽一窄）
  - `< 640px` 时退化为单列，顺序为 数量 → 购买 → 收藏 → 加购；
- 状态与收藏数**一律以接口返回值为准**，不做本地取反的乐观更新；
- 未登录时点击先引导登录（与加购同一套交互），收藏态在未登录/请求失败时静默降级为"未收藏"；
- 个人中心「我的收藏」标签页展示真实列表（封面 + 标题 + 价格 + 取消收藏），未登录时不发请求；顶部「收藏数」统计卡用接口返回的 `total`。

### 5.4 价格区间提示必须"占位"，不能 `v-if` 移除

价格块里的「价格可能随规格不同而变化」（`products.priceRangeHint`）只在**未命中具体 SKU** 时出现。
如果直接用 `v-if` 把它从 DOM 里删掉，价格块会矮一行，它下面的统计行、规格区、按钮区整体上移——
用户点规格时页面会明显"跳"一下。

因此改为**保留占位再隐藏**：

```html
<p v-if="hasPriceRange" class="mt-2 text-xs ..." :class="{ invisible: !showRangeHint }">
```

- `visibility: hidden` 保留元素盒模型（不绘制、不进无障碍树，但**仍占高度**），
  于是价格块高度在"未选规格 ↔ 已选规格"之间恒定不变（实测 128px → 128px，下方元素 Y 坐标完全一致）；
- 外层用 `hasPriceRange`（商品级，只跟 `minPrice/maxPrice` 有关）兜一道：
  本来就不跨价格区间的商品不预留这一行，避免长期多出一段空白。

验证脚本：`.probe/store-price-hint.probe.mjs`（zh/en/fr 三种语言各跑一遍，共 42 条断言）。

## 7. 已知边界与后续建议

1. **收藏列表没有分页器 UI**：个人中心一次展示第一页（12 件）。收藏超过 12 件后需要加分页/触底加载（后端已支持 `pageNo`/`pageSize`）。
2. **收藏数计数为冗余计数**：如果将来有人直接改 `ck_shop_favorite` 而不走 Service，计数会漂移；需要时可用 `SELECT COUNT(*)` 重算对齐。
3. **个人中心的「我的订单 / 收货地址」仍未接入**：订单模块有接口，但本页还是真实空态（本次未扩大范围）。
4. **商品详情页存在既有的 hydration mismatch 警告**：SSR 时未登录、客户端从 localStorage 恢复登录态后会改写按钮文案（`登录后加入购物车` → `请先选择完整规格`）。
   全站页眉也有同类警告（`/zh`、`/zh/cart` 同样出现）——属于**改造前既有现象**，本次新增的「立即购买」按钮沿用同一模式，未引入新类型的问题。
   要彻底消除，需要把登录态判断改成服务端可读（cookie）而不是 localStorage。
5. **`mvn package` 在 `jeecg-system-start` 的 testCompile 阶段会失败**（`MockControllerTest` / `SampleTest` 引用了仓库里不存在的 `org.jeecg.modules.shop.mock.MockController`）——既有问题，与本次改动无关；本地打包请加 `"-Dmaven.test.skip=true"`。
6. **本机的 Flyway 校验当前是失败的，DDL 必须手工执行**（既有问题，与本次改动无关，但会直接影响本表如何上线）：

   ```
   ERROR org.jeecg.config.flyway.FlywayConfig : 【数据库升级】flyway执行sql脚本失败
   org.flywaydb.core.api.exception.FlywayValidateException:
     Validate failed: Detected applied migration not resolved locally: 3.9.5.2.
   ```

   原因：开发库 `flyway_schema_history` 里记录着 `3.9.5.2`（`V3.9.5_2__add_shop_product_sku.sql`），
   但该脚本**没有提交到仓库**（`flyway/sql/mysql/` 里只有 `_0/_1/_4...`）。
   `validate-on-migrate=true` 时 Flyway 会在执行任何迁移前直接抛校验异常并被 `FlywayConfig` 捕获（只打日志），
   于是 `V3.9.5_4` 之后的所有脚本（含本表的 `V3.9.5_11`）都不会自动执行。
   这也解释了仓库里为什么同时维护 `ck-server/db/*.sql` 手工执行版（购物车、订单表都是这么建出来的）。

   本次交付时已用 `ck-server/db/ck-shop-favorite.sql` **在开发库手工建表**，功能可立即验证。
   要让 Flyway 重新接管，任选其一：补回缺失的 `V3.9.5_2__add_shop_product_sku.sql`（内容与历史一致）、
   或执行 `flyway repair`/删除 `flyway_schema_history` 中 3.9.5.2 那一行。
