## 二、Google Cloud「已获授权的重定向 URI」填写清单 ⭐

### 为什么要这么填

本项目 i18n 使用 **`prefix` 策略** —— **所有语言都带前缀**（`/zh`、`/en`、`/fr`），
所以 Google 回调地址形如 `/{语言}/auth/google/callback`，**不是** `/auth/google/callback`。
前缀漏掉、或某个语言没加，Google 都会回 **`redirect_uri_mismatch`（400）**。

### 操作路径

Google Cloud Console → **API 和服务** → **凭据** → 找到你的 OAuth 2.0 客户端 ID（Web 应用）→ 编辑 → **已获授权的重定向 URI** → 逐条粘贴下面这些地址。

### 本地开发环境（建议全部填上）

```
http://localhost:3000/zh/auth/google/callback
http://localhost:3000/en/auth/google/callback
http://localhost:3000/fr/auth/google/callback
http://127.0.0.1:3000/zh/auth/google/callback
http://127.0.0.1:3000/en/auth/google/callback
http://127.0.0.1:3000/fr/auth/google/callback
```

> 说明：`localhost` 与 `127.0.0.1` 在 Google 看来是**两个不同的值**，两个都加最省事。

### 生产环境

把 `your-domain.com` 换成你的真实域名，端口与协议按实际填（示例按 https + 默认端口）：

```
https://your-domain.com/zh/auth/google/callback
https://your-domain.com/en/auth/google/callback
https://your-domain.com/fr/auth/google/callback
```

> **多店铺提示**：如果你有多个前台域名（一店一域名），**每个域名都要加**，
> 且每个域名都要加 3 种语言。例如两个店铺就是 6 条。

### 同时需要确认的「已获授权的 JavaScript 来源」

```
http://localhost:3000
http://127.0.0.1:3000
https://your-domain.com
```

### 已配置的凭据位置（密钥不入仓库）

| 配置项 | 位置 | 值 |
|---|---|---|
| `GOOGLE_CLIENT_ID` | `ck-server/.env` | 已写入（`.env` 被 gitignore） |
| `GOOGLE_CLIENT_SECRET` | `ck-server/.env` | 已写入（`.env` 被 gitignore） |
| 模板（可提交） | `ck-server/.env.example` | 留空 + 填写说明 |
| 后端绑定 | `application-{dev,prod,docker,test}.yml` 的 `google.*` | 通过 `${GOOGLE_CLIENT_ID:}` 注入 |

> ⚠️ **未配置时的行为**：后端**不会**启动失败（避免一个可选功能绑架整站），
> 而是让 `/shop/account/google/auth-url` 返回明确错误，前端据此**禁用 Google 按钮并提示**。

## 三、关键设计决策

### 1. 为什么继续用 `sys_user` 而不新建表

- 店铺端与管理端**本来就共用** `sys_user`（店铺端走 `/sys/login`，地址按 `sys_user.id` 共享）
- `sys_user` 已有 `UNIQUE(username)`、`UNIQUE(email)`、`third_id/third_type` 等现成能力
- 拆新表会把**收货地址、订单、购物车、收藏**的 `user_id` 语义全部割裂，改动面成倍放大
- 隔离方式：新建 **`shop_customer` 角色**标识前台买家，`sys_org_code` **留空**（不属于任何店铺部门）
  - 后台可按角色一键筛出全部前台用户
  - 不影响既有的店铺数据隔离逻辑（`ShopOrgScopeResolver`）

### 2. 新增数据库结构（Flyway `V3.9.5_12__shop_customer_account.sql`）

| 变更 | 说明 |
|---|---|
| `sys_user.register_store_code/id` | 注册来源店铺（营销归因） |
| `sys_user.google_sub` + UNIQUE | Google 账号唯一标识；独立于 `third_id`，避免与原生第三方登录抢列 |
| `sys_user.pwd_set` | **是否由用户自己设置过密码**（1=是，0=系统随机占位） |
| `sys_role` 新增 `shop_customer` | 前台买家角色，注册/自动建号时自动赋予 |
| `ck_shop_login_log` 新表 | 登录来源流水：`login_type`、来源店铺、IP、UA、成功/失败与原因 |

**为什么需要 `pwd_set`**：Google 自动注册的用户没有真实密码，但 `JwtUtil.sign` 需要一个非空密码哈希才能签发 token。
所以自动注册时会写一个**无人知道明文**的随机哈希，此时 `password` 非空但用户并没有密码 ——
必须靠 `pwd_set` 区分，否则个人中心会把"设置密码"错显示成"修改密码"。

### 3. 邮箱验证码登录**不会**自动建号（已与用户确认）

- `scene=login` 时若邮箱未注册，直接返回「该邮箱尚未注册，请先注册」
- **只有 Google 登录**才自动建号（外部身份已由 Google 验证过）
- 理由：统一商城的邮箱验证码登录若自动建号，用户**打错一个字符就会凭空多出一个账号**

### 4. 安全设计

| 项 | 做法 |
|---|---|
| 图形验证码 | 保留，**仅在发送邮箱验证码时校验**（登录本身不需要） |
| 发码限流 | 同邮箱 60 秒冷却 + 每日 10 条；同 IP 每日 30 条；验证码 6 位 / 5 分钟 / **一次性消费** |
| 密码强度 | 8–32 位，至少含字母和数字 |
| 密码传输 | 浏览器传明文 → BFF 用 AES 加密 → 后端 `AesEncryptUtil.resolvePassword` 解密（兼容明文回退） |
| 登录失败锁定 | 复用 JeecgBoot `LOGIN_FAIL` 机制（按 email 计） |
| 水平越权防护 | `change-password` 的**用户 ID 只从登录态取**，绝不接受请求体传入 |
| 开放重定向防护 | Google 的 `redirectUri` **由服务端自拼**，忽略前端传入；拒绝绝对 URL、`//evil.com`、含 `\` 的绕过 |
| CSRF | Google `state` 存 Redis，10 分钟一次性（读到即删，防重放） |
| Token 存储 | 仍为 httpOnly cookie（JS 读不到），未引入任何前端 token 存储 |
| 重置密码后旧 token 失效 | `JwtUtil.sign` 把密码哈希纳入签名，改密后旧 token 自然失效 |

### 缺陷 6 的详细说明（用户上报：无论哪个语言登录都回到中文）

**根因**：不是 Google Cloud 的配置问题（6 条 URI 都配对），而是**前端调 BFF 时漏传了 `lang`**。

Google 流程是**两段式**，两段都必须用**同一个语言**拼 `redirectUri`，且 Google 会**逐字节比对**：

```
① 授权阶段   login.vue → /api/auth/google/auth-url?redirectUri=/zh/...
             BFF 内部 lang 回退 'en'（前端没传），但 redirectUri 用的是前端传的相对路径，
             侥幸仍是 /zh/... → 交给 Google 的地址是对的
                        ↓
② 回调阶段   callback.vue → /api/auth/google/callback { code, state }   ← 同样没带 lang
             BFF 用 lang='en' 重算 → http://host/en/auth/google/callback
                        ↓
             Google 比对：授权时 /zh/... vs 换 token 时 /en/... → redirect_uri_mismatch
```

同时因为 BFF 侧 `lang` 恒为 `'en'`，返回的文案与后续跳转也走默认语言 —— 这就是"总是回到中文/英文"的观感来源。

**验证结果**：三种语言下，**授权阶段交给 Google 的 `redirect_uri` 与回调阶段重算的值逐字相同**（zh/en/fr 全部 MATCH）。

> `redirectTarget`（登录后跳哪一页）本来就使用 `localePath()`，天然带语言前缀，这部分无需改动。

### 缺陷 7 + 8 的详细说明（用户上报：点击报 `Must be called at the top of a setup function`）

**这是修缺陷 6 时我自己引入的回归**，感谢截图定位。

**根因**：缺陷 6 的修法是"让 `useAuth` 自己取当前语言"，于是我在 `useAuth()` 里写了 `const { locale } = useI18n()`。
但 `useAuth()` 的使用者**不只是组件**：

```
app/plugins/init-auth.client.ts   →  defineNuxtPlugin(() => { useAuth() })   ← 不是组件！
app/pages/**/*.vue                →  组件 setup()                          ← 是组件
```

`useI18n()` 是 Vue composable，**只能在组件 `setup()` 顶层同步调用**。
在 Nuxt 插件里调用会直接抛 `Must be called at the top of a setup function`，
而该插件负责"恢复登录态"，它一挂就**连累整个应用初始化失败** —— 表现为所有页面 500 / 白屏。

**修复思路（关键决策）**：不是"把 `useI18n` 挪个位置"，而是**让 `useAuth` 彻底不依赖 i18n**：

| 文件 | 改动 |
|---|---|
| `nuxt-shop/composables/useAuth.ts` | 移除 `useI18n()`；`fetchGoogleAuthUrl(redirectUri, lang?)`、`loginByGoogle({ code, state, lang? })` 改为**接收 lang 参数** |
| `nuxt-shop/app/pages/login.vue` | 组件 setup 内 `const { t, locale } = useI18n()`，调用时传 `locale.value` |
| `nuxt-shop/app/pages/auth/google/callback.vue` | 同上，`loginByGoogle({ code, state, lang: locale.value })` |

**为什么这样更对**：`useAuth` 是被插件、中间件、组件**共用**的基础 composable，
它一旦依赖 i18n，就把"调用者必须有组件上下文"这个隐式约束传染给了所有使用方。
把语言作为**显式参数**，职责边界就清楚了：谁在组件里，谁负责提供语言。

**验证方式（这次用了真浏览器）**：
HTTP 层检查**无法**发现这类错误（HTML 渲染正常、接口 200，错误只发生在浏览器执行 JS 时）。
因此改用 **headless Edge + CDP** 实测，脚本见 `.probe/browser-page-health.mjs`：

```
12 个认证页面（3 语言 × 登录/注册/忘记密码/Google 回调）全部 PASS
  - 无 "Must be called at the top of a setup function"
  - 无任何 console / page error
  - body 非空、内容正常渲染
```

并单独验证过：探活请求 200 且带 `lang=zh`，**Google 按钮在 t≈4s 由 disabled 变为 enabled**（不再误报"本站暂未开通"）。

> 教训：这类"只在浏览器执行期暴露"的 composable 错误，必须用**真实浏览器**回归，
> 不能只靠 `curl` 看 HTML —— 这也是为什么本项目的验证脚本里现在多了 3 个 CDP 探针。

---

**根因**：不是 Google Cloud 的配置问题（6 条 URI 都配对），而是**前端调 BFF 时漏传了 `lang`**。

Google 流程是**两段式**，两段都必须用**同一个语言**拼 `redirectUri`，且 Google 会**逐字节比对**：

```
① 授权阶段   login.vue → /api/auth/google/auth-url?redirectUri=/zh/...
             BFF 内部 lang 回退 'en'（前端没传），但 redirectUri 用的是前端传的相对路径，
             侥幸仍是 /zh/... → 交给 Google 的地址是对的
                        ↓
② 回调阶段   callback.vue → /api/auth/google/callback { code, state }   ← 同样没带 lang
             BFF 用 lang='en' 重算 → http://host/en/auth/google/callback
                        ↓
             Google 比对：授权时 /zh/... vs 换 token 时 /en/... → redirect_uri_mismatch
```

同时因为 BFF 侧 `lang` 恒为 `'en'`，返回的文案与后续跳转也走默认语言 —— 这就是"总是回到中文/英文"的观感来源。

**修复**（3 个文件）：

| 文件 | 改动 |
|---|---|
| `nuxt-shop/composables/useAuth.ts` | `fetchGoogleAuthUrl` 与 `loginByGoogle` 均从 `useI18n()` 取当前 `locale`，作为 `lang` 传给 BFF |
| `nuxt-shop/app/pages/auth/google/callback.vue` | 显式 `loginByGoogle({ code, state, lang: locale.value })`；补 `locale` 解构 |

**验证结果**：三种语言下，**授权阶段交给 Google 的 `redirect_uri` 与回调阶段重算的值逐字相同**（zh/en/fr 全部 MATCH），
回调页三种语言均返回 200，`npm run build` exit 0。

> `redirectTarget`（登录后跳哪一页）本来就使用 `localePath()`，天然带语言前缀，这部分无需改动。
