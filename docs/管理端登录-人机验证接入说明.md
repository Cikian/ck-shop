# 管理端登录 - CikVerify 人机验证接入说明

> 范围：`admin-client/` 登录页（含会话超时重新登录）+ `ck-server` 登录接口。
> 依据：[CikVerify 用户接入手册](../../CikVerify/docs/接入与使用/用户接入手册.md)（本仓库外）。
> 结论：登录页的**字符图形验证码**换成 **CikVerify 工作量证明（POW）** 弹窗；前端拿到一次性 ticket，后端消费成功才允许登录。

---

## 1. 接入方式（只走线上正式版）

| 项 | 取值 | 说明 |
|---|---|---|
| 前端依赖 | `@cikian/captcha-web@1.0.0`（npm 正式版，精确锁版本） | 代码里**不复制、不改写** SDK |
| tac 资源 | 官方 CDN `https://cdn.cap.cikian.cn/assets/tac` | 不设置 `assetBaseUrl`，不使用包内 `tac/` 目录，不自托管 |
| 后端依赖 | `cn.cikian:captcha-client-spring-boot-starter:${ck.captcha.version}`（CikianMaven） | 不允许本地 jar / 本地源码 / system scope |
| 验证码服务 | `https://cap.cikian.cn` | 只由后端访问，浏览器不直连 |

浏览器只访问同源的 `/api/captcha/challenge`、`/api/captcha/verify`；`appSecret` 只在后端。

## 3. 上线前置条件（缺一不可）

- [x] 验证码平台为 `appId=ck-shop` **开通 POW 类型**（2026-10-22 已开通并实测 `code=200`）。未开通时 challenge 返回 `4000`，弹窗会持续失败、登录无法完成。
- [ ] 后端环境变量 `CK_SHOP_CAPTCHA_SECRET` 已注入（缺失时 SDK fail-fast，启动失败）。
- [ ] `ck.captcha.service-url` 为 `https://cap.cikian.cn`、`ticket-store=redis`、`ck.crydis.enable=false`（沿用现状）。
- [ ] Shiro `excludeUrls` 含 `/captcha/challenge,/captcha/verify`（各 profile 已配）。
- [ ] 前端 CSP 放行 `https://cdn.cap.cikian.cn`（本次已改；若日后改为自托管需同步替换）。
- [ ] **前端构建时注入 `VITE_AES_KEY` / `VITE_AES_IV`**，取值与后端 `JEECG_AES_KEY` / `JEECG_AES_IV` 完全一致。
      漏配的后果很隐蔽：验证码能过，但登录一直提示「用户名或密码错误」（后端解出的口令是乱码）。
- [ ] 服务器 NTP 正常（签名带时间戳，偏差过大会 4010）。

## 4. 联调与验收

1. 打开 `http://<host>:6002/login`（`MiniLogin.vue`），账号密码下方出现「人机验证」行，初始为「点击完成安全验证 / 去验证」，页面上**不再有**字符图形验证码。
2. 点「登录」或「去验证」→ 出现 POW 弹窗（POW 无需交互，自动完成）→ 状态变「安全验证已通过 / 重新验证」。
3. 浏览器网络面板：`POST /api/captcha/challenge`、`POST /api/captcha/verify` 均 200，verify 返回 `data.ticket`。
4. `POST /api/sys/login` 携带 `captchaTicket` → 登录成功（`code=200`，返回 token）。
5. 同一 ticket 再提交一次 → 后端返回「安全验证已失效，请重新验证」（HTTP 412），前端清空 ticket 要求重新验证。
6. 关闭弹窗 / 刷新页面 / 断网：关闭不报错；断网与 CDN 加载失败给出「安全验证未通过」提示，可重试。
7. 不带 ticket 直接调 `/sys/login`（老客户端/脚本）→ 仍走图形验证码校验，行为与改造前一致。

> 已实测（2026-10-22，无头 Edge）：challenge 200(POW) → verify 200 发 ticket → `/api/sys/login` 带 ticket 返回「登录成功」。

错误码：`4000/4001` 重新验证；`4010` 检查 secret 与时间同步；`4030` 应用禁用或 IP 白名单；`4290` 配额超限；`5000` 服务端 Redis/内部错误（fail-closed，不放行）。

## 5. 应急手段

| 场景 | 做法 |
|---|---|
| 平台未开通 POW，需临时换成滑块 | 改发布产物 `dist/_app.config.js` 里 `VITE_GLOB_CAPTCHA_TYPE` 为 `SLIDER`（或其它已开通类型），刷新即生效，无需重新打包 |
| 验证码服务整体不可用 | 前端与后端需**同时**回滚（前端去掉弹窗、后端去掉 ticket 分支）。只回滚一侧会导致：前端仍弹窗但后端拒绝，或后端要求 ticket 而页面没有验证入口 |
| 只想让后端停止校验 ticket | 不要用 `ck.captcha.enabled=false`（ticket 分支会因 Bean 缺失而 fail-closed 拒绝登录）；应回滚 `LoginController` 的 ticket 分支 |

## 6. 已知限制

- ticket 一次性、默认 120 秒、绑定客户端 IP 与 UA；登录失败后必须重新验证。
- 已纳入：**账号密码登录**（`/login` → `views/system/loginmini/MiniLogin.vue`）与会话超时重新登录（`views/sys/login/LoginForm.vue`）。
- 未纳入（仍是旧图形验证码 / `CaptchaModal`）：手机登录、注册、找回密码、在线表单分享登录。
- 账号登录**不再预选部门**：`/sys/loginGetUserDeparts` 的后端实现仍强制校验旧图形码（`inputCode + checkKey`），
  换成 CikVerify 后再调它只会得到「验证码无效」，所以 `MiniLogin.vue` 只在手机验证码登录时查部门；
  多机构用户账号登录时后端按 `sys_user.org_code` 默认机构登录。若必须保留账号登录选部门，需要给该接口补 ticket 支持。
- 后端 `mLogin`（APP 登录）与二维码/第三方登录不经过本验证码。
