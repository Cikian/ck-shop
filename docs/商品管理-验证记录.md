## 二、后端编译验证（本机可行的一步）

Maven 无法构建整个工程：`jeecg-boot-base-core` 依赖私服制品 `cn.cikian:cik-oss:0.2.9`、`cn.cikian:log3:1.5.34`、`cn.cikian:crydis:0.2.5`，
本地 `~/.m2` 只有 `.lastUpdated` 占位文件，三处公开仓库均无此制品。

**替代方案（已验证可行）**：仓库里已有 IDE 编译好的各模块 `target/classes`，
把它们连同本地仓库已缓存的 jar 拼成 classpath，用 JDK 17 的 `javac` 直接编译。

```powershell
$jdk = 'D:\Develop\jdk\jdk-17.0.14'

# 1) classpath = 各模块 target/classes + ~/.m2 下全部 jar（排除 -sources）
$cpParts  = Get-ChildItem 'ck-server' -Recurse -Directory -Filter classes |
              Where-Object { $_.FullName -match '\\target\\classes$' } |
              ForEach-Object { $_.FullName }
$cpParts += Get-ChildItem "$env:USERPROFILE\.m2\repository" -Recurse -File -Filter *.jar |
              Where-Object { $_.Name -notmatch '-sources\.jar$' } |
              ForEach-Object { $_.FullName }
$env:CLASSPATH = ($cpParts -join ';')

# 2) 编译本次新增的商品模块（54 个文件）
#    注意：不要用 @argfile —— javac 按平台默认字符集（GBK）读 argfile，中文路径会解析失败
$files = Get-ChildItem 'ck-server\jeecg-boot-module\ck-shop\src\main\java\org\jeecg\modules\shop' `
           -Recurse -File -Filter *.java |
         Where-Object { $_.FullName -match '\\shop\\(product|brand|tag|options|common)\\' } |
         ForEach-Object { $_.FullName }

& "$jdk\bin\javac.exe" -encoding UTF-8 -nowarn -d "$env:TEMP\ck-shop-javac-out" $files
# 期望：exit 0，生成 55 个 class（含 Lombok 生成器产生的内部类不计）
```

该步骤曾捕获一个真实缺陷：`ProductDetailVO` 缺少 `coverUrl` 字段（`ShopProductServiceImpl.getDetailById` 调用 `setCoverUrl`），已修复。

> 说明：全量编译整个 `ck-server`（843 个源文件）不可行，airag 等模块缺少 Tika 等未缓存依赖，
> 报错 7239 处，与本次改动无关。

## 六、第三轮：保存后"未找到数据"与抽屉卡死

**现象**：点保存 → 先提示成功 → 紧接着两条「未找到数据」→ 抽屉卡在加载态（页面可点但无法刷新）。

**根因（前后端契约不匹配）**：

`ShopProductController.add` 返回的是 `Result.OK("添加成功！")`，即 `res.result === "添加成功！"`（一句提示语）；
而前端「保存并继续编辑」用

```js
const newId = res?.result?.id || res?.result;   // ← 旧代码
```

把**提示语字符串当成了商品 id**，接着 `queryById({ id: '添加成功！' })`，
后端 `getById('添加成功！')` 返回 null → `getDetailById` 抛「未找到数据!」。
两次错误提示来自这一次错误查询产生的两次弹窗路径（`edit()` 内部 catch 与 defHttp 的失败提示）。

**修复**：

1. 后端改为返回新主键：`Result.OK("添加成功！", shopProductService.saveProduct(product))`，
   `IShopProductService.saveProduct` 返回值由 `boolean` 改为 `String`（新商品ID）。
2. 前端只接受字符串形态的 id，拿不到就关闭抽屉并刷新列表，绝不把提示语当 id：
   ```js
   const result = res?.result;
   const newId = typeof result === 'string' && result ? result : formData.id || null;
   ```
3. 保存后的回填失败改为**关闭抽屉 + 刷新列表**（信息已经保存成功），不再让抽屉卡在 loading：
   ```js
   } catch (err) { createMessage.warning('已保存，但回填详情失败，请重新打开该商品查看'); ... }
   ```
4. 详情查询失败时也一并关闭抽屉，避免用户对着空表单继续操作。

## 七、第三轮：「保存后提示未找到数据」的真正根因

前一轮只修了 `add`，**漏改了 `edit`**。用真实 token 直连后端复现后拿到确凿证据：

```
POST /shop/product/add   →  result = "2109311229710741505"   ✅ 商品ID
POST /shop/product/edit  →  result = "编辑成功!"             ❌ 仍是提示语
```

前端虽写了兜底 `formData.id`，但判断条件是 `typeof result === 'string'`，
而 `"编辑成功!"` 恰好是字符串 —— 于是又被当成 id 去查详情：

```
GET /shop/product/queryById?id=编辑成功!
→ HTTP 200  success=false  code=500  message="未找到数据!"
```

**所以"编辑已存在的商品再保存"必然复现**，这也解释了为什么前一轮的修复看起来无效。

**修复（两侧同时收紧）**

1. 后端 `edit` 与 `add` 统一契约：`result` 恒为商品ID，绝不放提示语
   （`IShopProductService.updateProduct` 返回值 `boolean` → `String`）。
2. 前端 id 取值规则收紧为"**只在新建时采用服务端返回的 id，编辑时一律用表单已有的 id**"，
   从根上避免再把提示语当 id：
   ```js
   const isCreate = !formData.id;
   const newId = isCreate ? (typeof result === 'string' && result ? result : null) : formData.id;
   ```

**复现证据（真实 HTTP，非推断）**

| 请求 | 结果 |
|------|------|
| `POST /shop/product/add` | 200，`result` = 新商品ID |
| `GET /shop/product/queryById?id=<新id>` | 200，specs=1、skus=2、stock=12、价格区间 1234.56~2234.56 |
| `POST /shop/product/edit`（同商品二次保存） | 200（**唯一键无冲突**，证明 purge 修复有效） |
| 编辑后再次 `queryById` | 200，skus=2，汇总值未变 |
| `DELETE /shop/product/delete` | 200，软删除成功 |

同时也验证了此前几轮修复确实生效：

- `GET /shop/product/list` 的 `categoryName` 返回本地化名「测试」（`selectBatchIds` 修复生效）
- `GET /shop/product/skuList` 返回 18 行
- 二次保存无 `Duplicate entry`（组合表 purge 修复生效）

**新增诊断工具**：`.probe/` 目录下的 Node 探针脚本，可在没有 Maven / 没有浏览器的情况下
直接构造签名请求打后端，本次正是靠它定位到上述根因。用法见 `.probe/README.md`。

## 八、第四轮：编辑时多语言/规格回填为空

**现象**：编辑商品时，「多语言内容」与「规格配置」显示为空，但保存仍提示成功。

**先确认真相（用 DBX + 真实 HTTP 查证，而不是看界面）**：

```
ck_shop_product_translation  : 3 行，en/zh/fr 标题均为 "IPhone17"，均带封面
ck_shop_product_spec         : 3 行存活（颜色/内存/存储），del_flag=0
ck_shop_product_spec_value   : 8 行存活
ck_shop_product_sku_combination: 18 行存活
GET /shop/product/queryById   : translations=3（含 title/coverUrl）、specs=3（含 values）、skus=18
```

**结论：数据其实保存成功了，也没有丢。**问题在**前端回填显示**这一环——
`queryById` 把数据取回来了，但表单没有渲染出来。所以"提示编辑成功"是真实的，
而"没保存成功"是界面给人的错觉。这个区分很关键：如果照着错觉去改保存逻辑，会越改越偏。

### 定位到的两个真实缺陷

**缺陷 1：`LangTabs` 的"清空"与"回填"是两条异步路径，中间会被 props 监听清掉**

`ProductForm.edit()` 原本依次调用 `refresh()`（清空 + 重新加载语言）与 `mergeFrom()`（写入数据），
两者之间要经过若干 tick，期间 `props.translations` 的深层 watch 可能把刚写进去的本地数据清掉。
修复：在 `LangTabs` 中新增**原子方法 `setAll(translations)`**，把"重置 + 回填"放进同一个去重窗口，
并用 `suppressPropsWatchFor` 计数器在整个窗口内抑制外部 watch 干扰；`add()` 与 `edit()` 都改用它。

**缺陷 2（同类隐患）：`ProductSpecEditor` 用引用比较判断是否需要重建本地状态**

```js
if (val !== localSpecs.value) { localSpecs.value = normalize(val); }
```

父组件 `Object.assign` 或复用响应式代理时引用可能不变，引用比较会判定"没变化"，
于是规格不刷新——正是"编辑时规格显示为空"。修复：改用**内容签名**比较
（`signature()` 序列化 id/name/values），并与 `sync()` 联动记住刚同步出去的内容，
避免父级回传同一份数据时又把本地状态重建一遍。

### 新增诊断能力

在 `ProductForm.edit / submitForm`、`LangTabs.loadLanguages / mergeFrom / setAll`、
`ProductSpecEditor` 的 watch 上都加了临时 `console.warn`，一次复现即可看出数据在哪一环丢失。
定位完成后应移除这些日志。

## 九、第五轮：多语言回填彻底重构 + 去掉规格值配图

### 9.1 多语言回填：不再使用共享组件 LangTabs

前几轮在 `LangTabs` 内部反复修（补 `setAll` 原子方法、抑制 props watch），但现象依旧：
数据库有数据、`queryById` 也返回了数据，界面就是不显示。

**决策：换掉它，而不是继续修它。**

`LangTabs` 同时服务分类/品牌/标签，内部维护"外部 props ↔ 本地副本"两套状态，
在商品这种"编辑时一次性整表回填"的场景下反复出问题。
商品表单本来就只维护**一个商品**的文案，直接自己持有语言状态最简单、也最可控：

- `/sys/lang` 拿启用语言（实测返回 `[{code:'en',name:'English'},...]`，仅 enabled='Y'）
- 模板用 `a-tabs` + `v-for="lang in languages"`，字段直接 `v-model` 到
  `formData.translations`，**表单自己就是唯一数据源**，不存在副本同步问题
- 新增 `syncTranslations()`（按启用语言对齐/重建）与 `cleanTranslations()`（提交前清理）
- `langFormKey` 在每次打开商品时自增，强制重建语言表单，避免上一份校验状态残留

### 9.2 去掉规格值配图

理由（用户提出，判断正确）：**规格值配图与 SKU 配图语义重复**，
图片配在具体 SKU 上才准确（`ck_shop_product_sku_combination.image_url` 保留）。

清理范围（前后端 + 数据库一起收干净，不留孤儿字段）：

| 层 | 改动 |

## 十一、第七轮：宽度/页签/保存丢数据/SKU 全量覆盖

于是出现横向滚动。修法：**限宽只加在"表单"上，不加在表格上**——
`.panel` 放宽到 1360px，`.panel-form`（基本信息）、`.lang-pane`、`.lang-seo` 各自限制在 ~1010px。
这样输入框保持可读行宽，表格拿到完整宽度。

### 11.2 保存后跳回"基本信息"页签

`resetForm()` 无条件把 `activeTab` 置为 `basic`，而保存后的回填会调用它。
修法：`resetForm(keepTab = false)`，回填路径传 `keepTab=true`，用户停留在当前页签。

### 11.3 保存后商品信息丢失 + SKU 编辑无效（两个独立缺陷）

**缺陷 A：保存后 `edit()` 回填把表单清空。**
保存后走 `edit({id})` → 先 `resetForm()` 清空 → 再 `queryById`。
一旦这次请求失败（例如后端未重启、`res.result` 仍是提示语导致 id 不合法），
用户看到的就是"提示保存成功、但商品信息全空，关掉重开才恢复"。

修法：**保存后不再回填**。页面需要的汇总值（总库存、价格区间）本来就由 `formData` 本地算出，
不依赖服务端回传，这次请求没有必须存在的理由。
新建时若 `res.result` 形如主键（`/^[A-Za-z0-9_-]{8,}$/`）则写回 `formData.id`，
否则关闭抽屉并提示"已保存，请重新打开该商品继续编辑"（避免再次保存时重复创建）。

**缺陷 B（核心）：SKU 表格的内联编辑从未回传给父组件。**
`ProductSkuEditor` 的表格绑定的是组件内部的 `rows`，父组件只通过 `sync()` 的
`emit('update:combinations')` 拿到数据。而 `sync()` 只在**生成/批量填充/单条新增/改规格下拉/全部可售**
这些离散操作里调用——**直接在单元格里改 SKU 编码、售价、库存、配图、售卖状态，改动永远到不了父组件**，
所以保存时提交的是旧值，数据库自然"没有更新"。

修法：
- 所有可编辑单元格加 `@change="onCellChange"`（内部调 `sync()`）；
- 同时加 `syncingLocal` 标记：本地 emit 后父组件会回传新数组，`props` 监听在此期间跳过 `rebuildRowsFromProps()`，
  否则会打断正在输入的内容、严重时往复循环。

### 11.4 取消"全量覆盖"，改为增量 upsert（保住 SKU 主键）

原实现每次保存都 `clearChildren()` 删掉全部子表再重建，两个后果：

1. **SKU 主键每次都变**——订单会关联 SKU 主键，历史订单会指向失效记录；
2. 每保存一次就产生一整批软删行，只增不减。

新 `saveChildren()` 改为按业务身份匹配后 `update` / `insert`，只删本次确实移除的行：

| 子表 | 匹配身份 | 移除时 |
|------|----------|--------|
| 多语言 | `languageCode` | 物理删除（该表无 `del_flag`） |
| 图集 | 主键 → URL | 软删除 |
| 标签关联 | `tagId` 集合差异 | 软删除 |
| 规格 | 主键 → 规格名 | 软删除 |
| 规格值 | 主键 → (规格, 值文本) | 软删除 |
| SKU 组合 | 主键 → `combinationKey`（唯一索引） | 软删除，保住订单引用 |
| 组合明细 | 纯内部数据 | 物理删除后重建 |

配套：`reclaimDeletedRows(productId)` 在每次保存开头**回收上一轮已软删除的行**
（`purgeDeletedByProductIds`），既保留历史，又不让 `del_flag=1` 的行无限堆积。

实测当前开发库中待回收的垃圾行：**组合 18 条、规格 3 条、规格值 8 条、图片 3 条**——
下次保存会被物理清理。

**关键收益**：反复保存同一商品时，规格值与 SKU 组合的主键**保持不变**。

## 十二、第八轮：SKU 页签空白（TDZ）+ 基本信息宽度不一致

### 12.1 SKU 组合页签整页空白：暂时性死区（TDZ）

上一轮为修"内联编辑不回传"引入了 `syncingLocal` 标记，但我把它用 `let` 声明在了
`watch(() => props.combinations, ..., { immediate: true })` **之后**。
`immediate: true` 的回调在 setup 期间**同步执行**，此时访问尚未初始化的 `let` 会抛：

```
ReferenceError: Cannot access 'syncingLocal' before initialization
```

组件 setup 直接失败 → 该页签渲染为完全空白（连"请先配置规格"的提示都没有）。

**修法**：把 `syncingLocal` 的声明移到那个 immediate watch **之前**，并在注释里写明原因。

**教训**：`immediate` 的 watch / `onMounted` 之外在 setup 期间同步执行的代码，
引用的 `let`/`const` 必须在使用点之前声明；函数声明（`function`）有提升，不受影响。
本轮顺手复查了 `ProductSpecEditor`（`lastIncomingSignature` 在 immediate watch 之前 ✅）
与 `ProductSkuEditor` 的其余声明顺序（`rebuildRowsFromProps` / `describe` / `valueId` 均为函数声明 ✅）。

## 十三、第九轮：SKU 表格分页失效 / 横向滚动条 / 配图上传

### 13.1 改了每页条数却不能翻页

原实现把"手动分页"和"a-table 分页"两套机制并用了：


AntD 依据 data-source 的长度算总数，而 slice 后的数组只有一页的条数，

"第 X-Y 条 / 共 N 个组合"的提示。

修法：去掉 `scroll.x`，把列宽压紧到合计约 1028px
（规格列 118×3 + 组合 150 + 编码 140 + 售价 116 + 库存 88 + 配图 84 + 状态 96），
并给"组合"列加 `ellipsis`，让表格在容器内自适应、永不横向溢出。

### 13.3 SKU 配图改为上传组件（且不撑高行）

原来是一个"图片URL"输入框，用户需要手填链接。

修法：行内只放一个 **26px 高的小按钮**（有图时显示 22px 缩略图，无图时显示"上传"），

## 十五、第十一轮：新增规格导致 SKU 全部消失（数据丢失，真 bug）

### 15.1 现象与根因

现象：打开一个已有 18 条组合的商品，**新增一个规格**（版本：国行/美版）后，
SKU 组合页签里的 SKU **全部消失**。

根因在 `ProductSkuEditor.sync()` 的那行过滤：

```js
.filter((item) => item.specValueRefs.every(Boolean) && new Set(...).size === ...)
//                       ^^^^^^^^^^^^^^^^^^^^ 关键
```

`specValueRefs` 是 `specs.map((spec) => row.__refs[spec.id || spec.name])`。
新增一个规格后，已有行的 `__refs` 里**没有这一维的值** → 该项为 `undefined`
→ `every(Boolean)` 为 `false` → **每一行都被过滤掉** → 向父组件上报空数组
→ `formData.combinations = []` → 界面上 SKU 集体消失。

叠加因素：`normalizedSpecs` 的 watch 只调用 `sync()`，没有任何"补齐新维度"的动作，
所以这个过程是静默的、用户完全无感。

### 15.2 修复（两处，缺一不可）

**① `sync()` 不再静默丢行。**
去掉"任一分量为空就丢整行"的过滤，一律原样上报；
不完整的行改由**提交前校验**拦下并给出可执行提示，
而不是在同步环节被无声抹掉。

**② 规格"增长"时自动补齐维度（笛卡尔积扩展）。**
新增 `buildStructure()` + `expandForNewStructure(before)`：

| 场景 | 行为 |
|------|------|
| 新增了一个规格 | 每一条已有组合按该规格的取值展开（18 条 × 2 个取值 = 36 条） |
| 已有规格新增了可选值 | 为每一行补出新增取值对应的组合，价格/库存等照抄该行 |
| 重命名规格 / 删除规格值 / 删除规格 | **不扩展**，只重算行键并去重 |

"只在增长时扩展"这条边界很重要：否则用户把规格改个名字，被他主动删掉的组合会被重新"复活"。

扩展时**主键只保留在第一个分支**上——它对应数据库里已有的那行，
后端按主键匹配后原地更新，从而**保住 SKU 主键**（订单可能引用它）；其余分支是新增组合。

**③ 追加防御：空数组不上报。**
`sync()` 增加前置判断：本地 `rows` 为空但父级 `combinations` 非空时直接 return。
这属于"规格/组合尚未装载完成"的中间态，此时上报空数组会造成与本次完全同类的事故。

**④ 提交前校验。**
保存时若存在"分量缺失"的组合，切到 SKU 页签并提示
「有 N 个组合缺少规格值（多因新增了规格）。请补齐这些行，或删除它们后重新生成」，
不再让数据静默进入后端。

### 15.3 同步调整

规格页签的说明文案与 SKU 页签的警告文案已对齐新的行为：
新增规格会自动补出组合，用户只需删掉不存在的那些。

## 十七、第十三轮：删除 SKU 时物理删除历史行（严重数据损失，我的设计缺陷）

### 17.1 现象与根因

用户实测：删除 SKU A → 保存（A 的 `del_flag=1`）→ 再删除 SKU B → 保存。
结果 **A 的记录被物理删除**，只剩 B 的软删行。

根因是我在第七轮引入的 `reclaimDeletedRows(productId)`：每次保存开头会
"回收上一轮已软删除的行"（`purgeDeletedByProductIds` → 真正的 `DELETE`）。
当时的动机是避免 `del_flag=1` 的行无限堆积，**但这是完全错误的取舍**：
订单会引用 SKU 主键，物理删除后这条 SKU 永久无法追溯。

### 17.2 修复：保存路径上不再有任何物理删除

| 动作 | 改动 |
|------|------|
| 删除 `reclaimDeletedRows()` | 方法与其全部 purge 调用一并移除 |
| `clearChildren()`（商品删除路径） | 去掉全部 purge，只保留逻辑删除 |
| `ShopProductSkuCombinationMapper` | 删除 `purgeDeletedByProductIds` |
| `ShopProductImageMapper` / `SpecMapper` / `SpecValueMapper` | 删除各自的 `purgeDeletedByProductIds` |
| `ShopProductSkuCombinationValueMapper` | `deleteByCombinationId`（物理）→ `softDeleteByCombinationId`（逻辑）；删除已无调用点的 `deleteByProductId` |
| `ShopTagMapper` | `deleteProductRelationsByProductIds`（物理）→ `softDeleteProductRelationsByProductIds`（逻辑） |

**唯一的例外**是 `ck_shop_product_translation`：该表**没有 del_flag 列**，
且带唯一索引 `(product_id, language_code)`——做逻辑删除的话同名语言无法再次添加。
文案不属于订单追溯所需的关联数据（订单会快照自己需要的文本），因此这里仍物理删除。
这一例外已在代码注释里写明理由。

### 17.3 去掉 purge 后必须解决的连带问题

**问题：唯一索引 `uk_ck_shop_product_sku_combo` 是 `(product_id, combination_key)`，不含 `del_flag`。**
软删行仍然占着组合键，所以用户"删掉某 SKU 之后又把它加回来"时，
直接 INSERT 会报 `Duplicate entry`。以前靠 purge 绕过，现在必须正面解决：

1. **复活旧行**：新增 `reviveById(id)` —— 裸 SQL `UPDATE ... SET del_flag = 0 WHERE id = ? AND del_flag = 1`。
   必须用裸 SQL，因为 `@TableLogic` 会给 `updateById` / `update(wrapper)` 自动追加
   `AND del_flag = 0`，对已软删的行普通更新永远匹配不到。
   该操作**幂等**，因此代码里无条件调用，不必先判断是否已删除（少一层对字段映射的依赖）。
2. **组合键优先匹配**：匹配顺序由"主键 → 组合键"改为 **"组合键 → 主键"**。
   `combination_key` 才是 SKU 的业务身份，主键只是订单引用的存储标识。
   这样还能顺带解决另一个冲突：若某行的规格值被改成与一条已软删记录完全相同的组合，
   按主键更新会把该行的键改成软删行占用的键 → 撞唯一索引。
   改成组合键优先后会直接复活并复用那条已删记录，主键一并保留。
3. **存活行由数据库过滤**：新增 `selectLiveIdsByProductId`，
   不再把"是否已删除"的判断寄托在实体 `delFlag` 字段的映射上。

顺带修掉一个隐性缺陷：组合更新从 `updateById` 改为**显式 `set` 的 `LambdaUpdateWrapper`**。
`updateById` 默认跳过 null 字段，导致"把售价 / 配图清空"的操作存不进去（前端传 null，旧值被保留）。

### 17.4 验证（真实数据库 + 事务回滚）

在真实库上用**事务**验证了复活链条，跑完 `ROLLBACK`，未改动任何数据：

| 步骤 | 结果 |
|------|------|
| 软删行 `UPDATE ... SET del_flag=0 WHERE id=? AND del_flag=1` | **1 行受影响**（复活生效） |
| 复活后执行带 `del_flag=0` 条件的更新 | **1 行 matched + changed**（证明 `@TableLogic` 的追加条件不再挡住更新） |
| `ROLLBACK` 后复查 | `del_flag` 恢复为 1、`sku_code` 保持原值 `SKU-X1-05` ✅ |

| 其它检查 | 结果 |
|----------|------|
| 后端 javac 全量编译 | 98 文件 / 103 class，**exit 0** |
| SKU / 规格 / 图片 / 明细表的物理删除 | **0 处**（全模块 grep 确认） |
| 前端 | **无需改动**（删除行后 payload 自然不含该组合，后端负责逻辑删除） |

### 17.5 顺带发现：108 行孤儿明细（我上一轮 purge 造成的）

上一轮的 `purgeDeletedByProductIds` 清掉了软删的**父组合**，但其明细行 `del_flag=0` 没被清理，
于是变成孤儿。实测：

| 项 | 数量 |
|----|------|
| 明细总行数(del_flag=0) | 144 |
| 其中父组合存活 | 32 |
| 其中父组合软删（合法历史） | 4 |
| **其中父组合已不存在（孤儿）** | **108**（涉及 27 个已消失的父组合） |

**我没有擅自清理这 108 行**。它们已不可能被任何订单引用（父记录已被我物理删除、无法恢复），
但按你的原则，我不会在未经确认的情况下动数据。如需清理，一条可逆的语句即可：

```sql
-- 仅标记为已删除（可逆），不物理删除
UPDATE ck_shop_product_sku_combination_value cv
SET cv.del_flag = 1
WHERE cv.del_flag = 0
  AND NOT EXISTS (SELECT 1 FROM ck_shop_product_sku_combination c WHERE c.id = cv.combination_id);
```

### 17.6 需要你知晓的取舍

不做物理删除后，`del_flag=1` 的行会**长期累积**（这与你在第七轮担心的"大量无用数据"是一对矛盾）。
现在的取向是：**订单可追溯 > 表体积**。
如果以后确实需要清理，正确做法是**显式运维任务**而不是保存时静默清理，且必须同时满足两个条件：

1. 该行**确定不被任何订单/售后引用**（用关联查询证明，而不是假设）；
2. 超过约定的保留期（例如 1 年以上）。

这需要你确认保留策略后我再实现，不会自作主张。
