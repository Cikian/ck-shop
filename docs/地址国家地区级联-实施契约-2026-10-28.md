# 地址「国家—州省—城市」级联：实施契约

> 这是后端与前端并行开发的**唯一依据**。任何一方要改契约，先改这份文件并通知对方。
> 数据层已于 2026-10-28 准备好（见 `docs/国家地区级联数据-导入与维护-2026-10-28.md`）。

---

## 0. 前提（已确认，不要再讨论）

1. 店铺**不做国内生意**，不需要中国省市区三级；`pca.json` 那套不接入。
2. 目标市场：东南亚 + 中亚（各种斯坦）+ 一带一路国家 → 必须有国家级全量，城市级到全球。
3. **地名译文要全部语言**（`translations` 表已含 34 种语言 / 290 万行），未来店铺加语言不能改代码、不能重灌数据。
4. **落库的地址必须是当地语言**（快递员只看当地文字）。界面显示才按访客语言翻译，且**不落库**——展示时用 code 反查译文现算。

## 1. 数据层（已就绪，只读，不要写）

| 表 | 行数 | 关键列 |
|---|---:|---|
| `countries` | 250 | `iso2`（权威码）、`name`、`native`、`phonecode`、`postal_code_regex`、`postal_code_format`、`translations`(JSON) |
| `states` | 5,327 | `id`、`country_id`、`country_code`、`iso3166_2`、`name`、`native`、`type`、`translations`(JSON) |
| `cities` | 152,378 | `id`、`country_code`、`state_id`、`state_code`、`name`、`native`、`population`、`type` |
| `translations` | 2,906,879 | `place_type`(country/state/county/city/region/subregion)、`place_id`、`language`、`translation` |

**三条使用纪律：**

- `cities` **不是纯城市**，混了 `adm1/adm2/adm3/locality/village/section`。任何面向用户的下拉都必须
  `AND type IN ('city','municipality','town','adm2')`，否则省级记录会混进"城市"里。
- `name` = 拉丁/英文名；`native` = **当地文字**。落库取 `native`，缺失才退 `name`。
- 业务表**不要**对这三张表建外键（上游更新是整表 DROP 重灌）。

## 2. 语言解析规则（前后端必须一致）

访客语言以店铺 locale code 传入（`x-language` 头，BFF 已经在发；也接受 `?lang=`），取值是 `en`/`zh`/`fr`/未来更多。

映射到 region 译文的查表语言：

| 访客 locale | 查 `translations.language` |
|---|---|
| `zh` | `zh-CN` |
| `zh-TW` | `zh-TW` |
| `en` | **不查**（`en` 译文只有 0.6%，没有意义，直接用 `name`） |
| `fr` / `th` / `vi` / `id` / `ja` / `ko` / `ru` / `ar` / `hi` / … | 同名（`fr`→`fr`，`th`→`th`…） |

**显示回退链（唯一正确顺序，不许反过来）：**

```
译文(映射后的语言)  →  name（拉丁名）  →  native（当地文字）
```

理由：缺失时给一个拉丁名，用户至少能读；给当地文字（如 `กรุงเทพฯ`）等于没给。
历史坑：法语译文缺失时如果退回 `native`，法国用户会看到一堆泰文。

## 3. 后端接口（新增，`org.jeecg.modules.shop.region`）

全部 **GET、公开访问**（方法上加 `@IgnoreAuth`，参考现有 `/home/slide/store` 的做法），
统一返回 `Result<T>`（`org.jeecg.common.api.vo.Result`）。语言从 `x-language` 头或 `?lang=` 取。

### 3.1 `GET /shop/region/countries`

```json
{ "success": true, "result": [
  { "code": "TH", "name": "泰国", "nameLocal": "ประเทศไทย",
    "phoneCode": "66", "currency": "THB",
    "postalCodeFormat": "#####", "postalCodeRegex": "^(\\d{5})$" }
] }
```

- `name` = 按访客语言解析后的名字；`nameLocal` = `countries.native`。
- 排序 `ORDER BY countries.name`（前端如需按译名重排，自己排，别在 SQL 里折腾排序规则）。

### 3.2 `GET /shop/region/states?country=TH`

```json
{ "result": [ { "id": 3901, "code": "TH-10", "name": "曼谷", "nameLocal": "กรุงเทพมหานคร", "type": "province" } ] }
```

- `code` 取 `states.iso3166_2`；**为空时回退** `"S" + id`（保证前端一定能拿到标识）。
- 排序 `ORDER BY states.name`。
- `country` 为 ISO alpha-2，必填；非法/空返回空数组而不是报错（前端首次进页面时还不知道选哪个国家）。

### 3.3 `GET /shop/region/cities?country=TH&stateCode=TH-10&keyword=&limit=200`

```json
{ "result": [ { "id": 105140, "name": "曼谷", "nameLocal": "กรุงเทพฯ", "population": 5104476 } ] }
```

- `stateCode` 可选（部分国家无州级，见 `cities.state_id IS NULL`）；传了就按 `states.iso3166_2` 过滤。
- `keyword` 可选：同时模糊匹配 `cities.name`、`cities.native`、以及该城市任意语言的译文。
- `limit` 默认 200，**硬上限 500**。
- 过滤 `type IN ('city','municipality','town','adm2')`；排序 `population DESC, name`。
- 关键词搜索时 `limit` 生效于排序后的结果，不做分页（下拉框场景，越简单越好）。

### 3.4 地址侧改造（改造现有，不是新建）

**`AddressDTO` 新增 3 个字段**（都可空，保持对旧客户端向后兼容）：

```java
private String countryCode;   // ISO alpha-2，新数据必填（服务端校验）
private String provinceCode;  // states.iso3166_2
private Integer cityId;       // cities.id
```

**服务端在 create/update 里必须做的事**（顺序即校验顺序）：

1. `countryCode` 非空 → 必须能在 `countries.iso2` 找到，否则 `JeecgBootException("国家/地区不合法")`；
2. `provinceCode` 非空 → 必须属于该国家，否则报错；
3. `cityId` 非空 → 必须属于该国家（且若 `provinceCode` 有值，`cities.state_code` 必须等于它），否则报错；
4. **名称以服务端解析结果为准，覆盖前端传来的文字**：
   - `province` 列 ← `states.native ?: states.name`
   - `city` 列 ← `cities.native ?: cities.name`
   - `country_name` 列 ← `countries.native ?: countries.name`
   - 前端传的 `province/city` 文字**只在 `cityId` 为空时**才采信（手填兜底场景）。
5. `countryCode` 为空（老客户端 / 未改造的入口）→ 完全按旧逻辑走，不报错、不覆盖。

**`AddressVO` 新增 7 个出参**：

```java
private String countryCode;      // 权威码
private String countryName;      // 当地语言国名快照（落库值）
private String provinceCode;
private Integer cityId;
private String countryDisplay;    // 当前访客语言的国名（展示用）
private String provinceDisplay;   // 当前访客语言的省名
private String cityDisplay;       // 当前访客语言的城市名
private String fullAddressLocalized; // 当前访客语言的整串（屏幕展示）
```

- `province`/`city`/`fullAddress` **保持现有语义**：当地语言 + 面单格式，**不要动**。
- `fullAddressLocalized` 与 `fullAddress` 只有名称语言不同、顺序相同。

**整串拼接规则：**

- `country_code` 为 NULL（老数据）→ 沿用现有 `joinAddress()` 逻辑，一个字都不要改；
- 有 `country_code` → **国际顺序**：
  `detailAddress, district, city, province, postalCode, country`（逗号 + 空格，跳过空段）。

**订单快照（必须一起改，否则订单和地址簿会不一致）：**

- `OrderSubmitDTO` 内联地址加 `receiverCountryCode` / `receiverCountryName` / `receiverProvinceCode` / `receiverCityId`
  （`receiverCountryName` 用于"手填国名"的直接下单场景——BFF `order/submit.post.ts` 支持内联地址，这条路径真的能走到；优先级与 `AddressDTO.countryName` 完全一致）；
- 下单时：来自 `addressId` 就整份拷贝（含新字段），来自内联地址就走与地址簿同一套解析逻辑；
- `ShopOrder` 实体 + 订单详情 VO 补上 `receiverCountryCode`、`receiverCountry`、`receiverProvinceCode`、`receiverCityId`。
  （`ck_shop_order` 的列已经加好了，见 `ck-server/db/ck-shop-address-region.sql`）

## 4. BFF（`nuxt-shop/server/api/region/`）

三个透传路由，作用是把 Java 的 `Result` 拆包（与现有 `server/api/address/*` 保持同样的写法与错误处理）：

| 路由 | 转发 | 缓存 |
|---|---|---|
| `GET /api/region/countries?lang=` | `/shop/region/countries` | `Cache-Control: public, max-age=86400` |
| `GET /api/region/states?country=&lang=` | `/shop/region/states` | 同上 |
| `GET /api/region/cities?country=&stateCode=&keyword=&limit=&lang=` | `/shop/region/cities` | `public, max-age=60` |

- `lang` 走 `createApiClient(event, { lang })`，与现有 BFF 一致；
- **不需要登录**（与国家/地区数据无关的东西不要拉进来）；
- 上游报错 → `createError`，与 `server/api/address/add.post.ts` 的写法一致。

| `app/components/address/AddressRegionCascader.vue` | 国家 → 州省 → 城市 三段级联 + 每段可搜索 + "手动输入"兜底 |

### 5.2 级联组件的交互要求

- **国家**：一次加载全量 250 条，`USelectMenu` 可搜索（中文用户搜"泰"、英文用户搜"Thai"都要命中 → 搜索要同时匹配 `name` 和 `nameLocal`）。
- **州省**：选中国家后拉取；该国无州级（返回空）→ **跳过这一级**，直接进入城市。
- **城市**：`stateCode` 变化后拉取；超过 200 条的国家（菲律宾 4,374、泰国 1,012）必须支持**输入关键词搜索**，不能一次性铺开。
- **手动输入兜底**：每一级都要有"找不到我的城市，手动填写"入口，切到纯文本框。
  自贸区、工业园、军事基地这类地址任何数据集都没有，**没有这个入口就是功能倒退**。
- **邮编**：跟随国家的 `postalCodeRegex` 做前端预校验，不匹配只提示不阻断（后端才是权威）。
- 已选中项要能在编辑时正确回显（用 `cityId`/`provinceCode` 反查）。

## 6. 验收标准（我会按这个验收）

1. `mvn -q -pl jeecg-boot-module/ck-shop -am compile` 通过（JDK 17）。
2. `nuxt-shop` 能起来，`pnpm --dir nuxt-shop exec nuxi typecheck` 或 `npm run build` 无新增错误。
3. 手工链路：选 `TH → 曼谷 → 曼谷市` 保存地址 → 库里 `country_code='TH'`、`province='กรุงเทพมหานคร'`（**泰文**）、
   `city_id` 有值 → 地址列表在中文界面显示"曼谷"、法语界面显示"Bangkok"、`fullAddress` 始终是泰文/拉丁原件。
4. 下单后 `ck_shop_order` 的 `receiver_country_code` / `receiver_province` / `receiver_city_id` 与地址簿一致。
5. 全部接口在**未登录**状态下可访问（用 curl 直接打，不带 token）。
6. 老数据（`country_code IS NULL` 的 6 条地址）渲染与改造前**完全一致**。
