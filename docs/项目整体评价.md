### 三、请求的完整流程（从浏览器到 Java 后端再回来）

以登录为例，完整走一遍：

```
1. 浏览器 login.vue
   ↓ 用户填完表单，调用 login({ username, password, captcha, checkKey })

2. composables/useAuth.ts 的 login()
   ↓ $fetch('/api/auth/login', { method: 'POST', body: params })
   （这是浏览器发出的 HTTP 请求，目标是 Nuxt 自己的 server，不是 Java）

3. Nuxt Nitro 路由匹配
   ↓ 请求路径 /api/auth/login → 自动匹配到 server/api/auth/login.post.ts
   （这一步是 Nitro 基于文件名做的路由映射，不需要手写路由表）

4. server/api/auth/login.post.ts 执行
   ├─ readBody(event) 拿到前端传来的明文密码等参数
   ├─ encryptPassword(明文密码) —— 调用 server/utils/crypto.ts，用 AES-CBC 加密
   │   （这一步只在 server 端发生，浏览器全程看不到 key）
   └─ createApiClient(event) —— 调用 server/utils/apiClient.ts 拿到一个 $fetch 实例

5. apiClient.ts 里的 $fetch.create() 配置生效
   ├─ baseURL: config.apiBaseUrl（即 http://127.0.0.1:9951/api）
   ├─ 组装通用 headers：Accept-Language、x-language
   ├─ 如果 withAuth，从 httpOnly cookie 读 token，加 x-access-token 等头
   ├─ onRequest 钩子触发：
   │    - signMd5Utils.getSign() 用 url+params+body+密钥算出 sign
   │    - 加上 timestamp、sign、version 三个头
   │    （这是防篡改/防重放的签名机制，Java 后端会校验这个 sign）
   └─ 真正发起请求：POST http://127.0.0.1:9951/api/sys/login

6. Java 后端处理
   ↓ 校验 sign、timestamp，验证账号密码、验证码
   ↓ 返回 { code, message, result: {...}, success, timestamp } 这种统一格式

7. apiClient.ts 的 onResponse 钩子拦截响应
   ├─ 判断 body.success
   │    - 失败 → createError 抛 400，流程中断，直接进 5xx/4xx 分支
   │    - 成功 → response._data = body.result（把外层 envelope 剥掉）
   └── createApiClient 返回的 api() 函数最终 resolve 出 result 内部的数据

8. 回到 server/api/auth/login.post.ts
   ├─ setCookie(event, 'access-token', result.token, { httpOnly: true, ... })
   │   （token 写进 httpOnly cookie，随这次 HTTP 响应的 Set-Cookie 头返回给浏览器）
   └─ return { userInfo, tenantList }（只返回非敏感数据）

9. Nitro 把 8 的返回值序列化成 JSON，连同 Set-Cookie 头一起返回给浏览器

10. 浏览器收到响应
    ├─ 浏览器自动把 Set-Cookie 里的 access-token 存起来（httpOnly，JS 读不到）
    └─ useAuth.ts 里 login() 拿到 { userInfo, tenantList }
         ├─ userInfo.value = data.userInfo（写入响应式状态）
         └─ localStorage.setItem('user-info', ...)（只是缓存，用来刷新页面后回显）

11. login.vue 收到 login() 的 resolve，navigateTo('/profile')
```

**关键点：**

- 步骤 2→3 是“浏览器 → Nuxt server”这一段，走的是相对路径 ，同源不用担心跨域`/api/xxx`
- 步骤 4→6 是“Nuxt server → Java 后端”这一段，走的是 绝对地址，因为是 server-toserver，不受浏览器跨域限制`config.apiBaseUrl`
- 中间 apiClient 的 onRequest/onResponse 是全局拦截器，所有走 的请求都会自动带上签名、自动解包 result、自动处理错误——这是这套架构的核心价值`createApiClient`

### 五、 /  /  的区别`$fetch``useFetch``useAsyncData`

这是 Nuxt 里最容易搞混的三个概念，核心区别在于**“是否和 SSR/组件生命周期挂钩”**。

#### `$fetch`

- 底层是 ofetch，就是个普通的“发请求”函数，跟 Vue 组件、SSR 完全没关系
- **不会**自动处理 loading 状态，**不会**自动去重（同一个请求多次调用就是发多次），**不会**在 SSR 阶段把数据序列化传给客户端（也就是说如果在 setup 顶层直接用 而不包一层，会导致服务端请求一次、客户端 hydration 又重复请求一次）`$fetch`
- **适用场景**：事件处理函数里（点击按钮、表单提交），比如你项目里  的 、， 的 ——这些都是"用户主动触发一次性动作"，不需要 SSR 参与，也不需要和页面渲染绑定`useAuth.ts``login()``logout()``useCaptcha.ts``refreshCaptcha()`

TS

```ts
async function handleLogin() {
  await login(...) // 内部用的就是 $fetch，用户点一下按钮触发一次，天经地义
}
```

#### `useFetch`

- 是  +  的语法糖，专门为"发一个请求拿数据"这个场景设计`useAsyncData``$fetch`
- 自动处理：SSR 时发一次请求→结果序列化进 HTML→客户端 hydration 直接复用，不会重复请求
- 自带 、、、,而且默认基于 URL +参数生成请求 key，自动做请求去重`data``pending``error``refresh`
- **适用场景**：页面加载时需要展示的数据，比如你项目里 、`products/index.vue``products/[slug].vue`

```ts
const { data: products } = await useFetch('/api/products', {
  query: { lang: locale.value },
})
```

#### `useAsyncData`

- 比 更底层、更灵活，你自己提供一个“获取数据的函数”（不一定是 fetch，可以是任何异步逻辑、多个请求合并、或者调用某个 composable 方法）`useFetch`
- `useFetch('/api/xxx')`本质上等价于：

```ts
useAsyncData('xxx', () => $fetch('/api/xxx'))
```

- **适用场景**：
  1. 需要自定义请求 key（比如你的 里 ）`HomeHeroBanner.vue``useAsyncData('home-slideshow', ...)`
  2. 需要监听某个响应式变量变化并自动重新请求（，你项目里正是这么用的）`watch: [locale]`
  3. 请求逻辑不是简单的一次 fetch，比如要合并多个接口、要用某个复杂的处理函数

```ts
const { data: slides, pending, refresh } = await useAsyncData<SlideItem[]>(
  'home-slideshow',
  () => $fetch('/api/home/slide'),
  { default: () => [], watch: [locale] }
)
```

#### 一张表总结怎么选

| 场景                                                         | 用哪个                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 页面加载时要展示的数据，普通 GET                             | `useFetch`                                                   |
| 页面加载时要展示的数据，但要自定义 key / 监听变量 / 合并多接口 | `useAsyncData`                                               |
| 用户点击按钮、提交表单等一次性动作                           | `$fetch`                                                     |
| 在 composable 里封装的方法内部                               | `$fetch`（因为 composable 本身不在组件 setup 顶层同步执行，用 useFetch 反而麻烦） |

TS

```ts
export function createApiClient(event, options) {
  const instance = $fetch.create({ ...上面的配置，去掉 onResponse 里解包逻辑... })

  return async function callApi<T>(url: string, opts?: any): Promise<T> {
    const res = await instance<BackendEnvelope<T>>(url, opts)
    if (!res.success) {
      throw createError({ statusCode: 400, statusMessage: res.message })
    }
    return res.result
  }
}
```

这样类型链路更清晰，也不用依赖修改 response._data这种“side effect”式写法。

1. `products.get.ts`和 现在还是纯 mock 数据，写死在文件里，等接 Java 后端时记得把这两个文件也走 ，跟其他接口保持一致的错误处理和签名逻辑，不要用注释里写的 方式（那样就绕过了签名和统一错误处理）。`[slug].get.ts``createApiClient``$fetch('http://localhost:8080/...')`
2. `crypto.ts`用的是 CBC + 固定 IV（ 是写死的常量）。CBC 模式下 IV 理论上应该per-request随机生成、再连同密文一起传给对方解密，固定 IV 会削弱 CBC 的安全性（相同明文重复加密会得到相同密文，可能被观察到规律）。这个具体要看 Java 后端的加密实现是不是也用固定 IV，如果双方约定就是这样倒也能工作，只是安全性上不是最佳实践，可以跟后端确认一下。`AES_IV`
