# 店铺端登录失效（token 过期）未退出登录 —— 根因与修复

> 2026-10-27。用户实测反馈，属于"账号体系"级别的严重问题。
> 本文取代 `nuxt-shop/docs/auth-guard-contract.md` 第 3 节里
> 「`authChecked === true` 就直接复用上次判定」这一条 —— 该做法本身正是本次故障的根因之一。

## 一、现象（用户原话）

> 我现在处于 token 失效的状态，但是依然能够进入到个人中心，甚至能打开地址管理，
> 但是新增地址时，会报 token 失效，但是并不会退出登录，目前为止，右上角依然显示着登录状态，
> 这是个很严重的问题。

拆成三个可观测事实：

1. **能进私有页**：token 已失效，`/profile`、`/address` 照常打开并渲染"已登录"的界面。
2. **操作才暴露**：点「新增地址」时接口返回 401，页面只弹一条红色错误提示。
3. **状态不收敛**：右上角一直显示头像 / 已登录，`localStorage.user-info` 仍在，
   刷新页面还是"已登录"—— 用户没有被告知要重新登录，也没有被引导去登录。

## 二、根因（三层，缺一层都不会出这个问题）

### 1）前端"是否已登录"的显示源与真实凭证脱钩

`useAuth().isLoggedIn` 是 `computed(() => !!userInfo.value)`，而 `userInfo` 只是
`localStorage` 里的一份**展示用缓存**。真正的凭证 `access-token` 在 httpOnly cookie 里，
JS 读不到、也不会因为过期而消失。
→ 这是既定设计（见 `docs/店铺端账号体系改造-接口契约.md`），本身没问题；
问题在于下面两层没有把"权威判定"贯彻到每一次导航和每一个接口。

### 2）受保护页的导航守卫把"查过一次"当成"永远有效"

`app/middleware/auth.ts` 旧逻辑：

```ts
if (authChecked.value) {          // ← 只要曾经查过一次
  authenticated = !!userInfo.value // ← 就永远复用缓存里的结论
}
```

`authChecked` 只表示"查过"，不表示"结果还作数"。token 会在两次校验之间失效
（TTL 到点、管理员踢人、别处登录挤掉、后端重启换了签名密钥……），
于是「先登录 → 过一阵 token 过期 → 点进个人中心」一路放行。

### 3）接口 401 分散处理，且**没有任何一处**去清前端登录态

20+ 个调用点的 catch 各写各的：

| 写法 | 出现位置 | 后果 |
|---|---|---|
| `unauthorized.value = true` 显示"请先登录" | `app/pages/address/index.vue` | 页面自己说未登录，右上角说已登录，自相矛盾 |
| `if (isUnauthorizedError(err)) return` 静默 | `useAddressBook.load`、`useProfileAccount.load`、`useOrderList.load` | 什么都不发生 |
| 把 401 当业务错误弹提示 | `useAddressBook.save`、各面板的 catch | 「新增地址失败：未登录或登录已过期」——用户看到的是"地址存不上"，而不是"你要重新登录" |

三种写法都漏掉了同一件事：**清空前端登录态并引导重新登录**。

## 三、修复（六处，各自负责一段，缺一处就有缝隙）

### 1）`composables/useAuth.ts`：给登录态加"新鲜度"

- 新增 `AUTH_VERIFIED_AT_KEY = 'auth-verified-at'`（原 `auth-seeded-at` 改名，语义扩展为
  "最近一次**服务端权威校验**的时间"）。
- `markVerified()` 把 `authChecked = true` 与时间戳**成对**写入（只有这一个写入口，
  避免出现"查过了但不知道多旧"）。
- `isSessionCheckFresh()`：`authChecked && 时间戳在 AUTH_SEED_FRESH_MS（60s）内`。
- `clearSession()`：清 `userInfo` + `localStorage.user-info` + `markVerified()`。
  **不清 cookie**（前端删不掉 httpOnly cookie，作废走服务端）。

### 2）`app/middleware/auth.ts`：按新鲜度重校验，失效即清缓存

```
新鲜（60s 内）→ 复用上次结论（保持原有的"不重复请求"优化）
不新鲜       → 重新问 /api/auth/session
               ├─ 服务端认 → 种 userInfo + markVerified
               └─ 服务端不认 → clearSession()（连 localStorage 一起删）+ 提示 + 跳登录
网络异常     → fail-closed 拦下，但**不清缓存**（可能只是后端抖了一下）
```

"服务端不认"这条分支里，如果前端原本认为自己已登录，会调
`notifySessionExpired()` 弹一句「登录已过期，请重新登录」——
否则用户只看到"点一下就突然让我登录"，不知道发生了什么。

跳转改成 `navigateTo(..., { replace: true })`：被拦下的页面不该留在历史里，
否则用户按"后退"会反复撞回同一个跳转。

### 3）`composables/useSessionExpiry.ts`（新增）：401 的唯一处理出口

`handleSessionExpired()` 的动作顺序（前两步必须同步，先于任何 `await`）：

1. 清态：`clearSession()` + 购物车角标归零 + 清 `store-cart` / 勾选；
2. 服务端作废：`POST /api/auth/logout`（不 await；失败也无所谓，BFF 无论如何都清 cookie）；
3. 提示：`auth.sessionExpired` / `auth.sessionExpiredDesc`（zh / en / fr 三语）；
4. 跳登录：**只有当前路由声明了 `definePageMeta({ middleware: 'auth' })` 才跳**，
   并带 `redirect` 回跳参数；公开页（首页/商品页）只静默掉线 —— 不能把正在逛商品的人踹去登录页。

另外两个设计点：

- **只处理"已登录"的用户**（`userInfo` 非空）。匿名用户点加购/收藏时的 401 是"没登录"，
  归口到各页面自己的"请先登录"引导，不能弹"登录已过期"。
- **并发闸门**：一屏上常有多个请求同时 401（个人中心一次拉资料/地址/订单/收藏），
  闸门保证只提示一次、只跳一次、只发一次 logout。

### 4）`app/plugins/api-session-guard.client.ts`（新增）：全局 `$fetch` 兜底

把 `globalThis.$fetch` 包一层（**只包、不替换默认值**，`create`/`raw` 原样保留）：

```
任意 /api/* 请求 → 401 且本地认为已登录 → handleSessionExpired()
```

- 逐个 catch 补是补不完的（以后还会加调用点），所以从唯一入口兜底：
  **只要请求 401，登录态就一定被清掉**。
- **不吞异常**：调用方该拿到的错误照旧抛出，控制流不变。
- 只认 **401**，不认 403：403 是"已登录但没权限"，把人踢下线是错的。
- 白名单跳过：`/api/auth/login|register|send-code|reset-password|google|logout|session`、
  `/api/captcha` —— 这些接口的 401 不代表"会话过期"。
- 为什么不用 `$fetch.create({ onResponseError })`：那会丢掉 Nuxt 给全局实例配好的默认值；
  包一层能 100% 保持请求/响应行为。

### 4.5）`app/plugins/init-auth.client.ts`：冷启动时以权威结论为准，不再无条件相信缓存

原实现是"先 `restoreUser()` 读 localStorage，再按需 `refreshSession()`"，
于是**服务端刚说完"未登录"，客户端又把死缓存读回来**——表现为"被踢到 `/login` 之后
右上角过一会儿又变回已登录"（实测存在的矛盾态，也是本文开头第 3 个现象的一部分）。

现在的顺序：

```
SSR 结论新鲜 → 只认 useState 里的 userInfo；它是空的就把 localStorage 一起清掉
否则         → restoreUser() 回显 + refreshSession() 问服务端
```

`restoreUser()` 的本意是"SSR 无法判定时别闪"，而不是"缓存优先于服务端"；
这条改动把这个本意落到了代码上。

### 5）收敛各处 401 分支（不再重复/误导性提示）

- `composables/useAddressBook.ts`：`load / fetchOne / save / setDefault / remove` 的 401
  一律交给 `handleSessionExpired`，**不再弹「新增地址失败」**，也不再吞掉 `fetchOne` 的 401。
- `app/pages/address/index.vue`：401 时保留本地 `unauthorized`（SSR 直出要用它渲染
  "登录后查看"），同时调用统一处理（客户端会跳登录）。
- 其余 11 个文件（`FavoritesPanel`、`OrdersPanel`、`SettingsPanel`、`OrderCancelModal`、
  `RefundApplyModal`、`StoreProductCard`、`orders/index`、`useCartPage`、`useOrderDetail`、
  `useFavorites`、`useReviews`）在"弹错误提示"之前加
  `if (isUnauthorizedError(err)) return` —— 提示与跳转由统一处理负责，
  这里再弹一条只会让用户同时看到两条互相矛盾的提示。

### 6）i18n

`auth.sessionExpired` / `auth.sessionExpiredDesc` 三语言包齐备（zh/en/fr，595 键对齐）。

## 四、行为对照

| 场景 | 改前 | 改后 |
|---|---|---|
| token 失效后点进个人中心 | 正常进入，显示"已登录" | 60s 内复用缓存进入，但页面首个接口 401 立刻清态并跳登录（带 redirect） |
| token 失效后打开地址管理 | 正常进入 | 同上；页面不再显示"右上角已登录 + 地址簿说未登录"的矛盾态 |
| token 失效后点「新增地址」 | 弹「新增地址失败：未登录或登录已过期」，仍显示已登录 | 清态 + 弹「登录已过期，请重新登录」+ 跳登录页回跳 |
| token 失效后停在首页（购物车角标请求 401） | 什么都不发生，头像继续显示 | 静默掉线：头像→登录入口、角标归零、弹一次提示，**不跳转** |
| 匿名用户点「加入购物车」（401） | 页面引导登录 | 不变（不会误报"登录已过期"） |
| 已登录但无权限（403） | 页面提示 | 不变（**不**强制下线） |
| 后端抖动 / 断网（非鉴权 5xx） | 可能把人踢下线 | 不清缓存、不跳登录（fail-closed 只拦页面，不销毁会话） |

## 五、验证证据

### 1）SSR 侧（curl 打真实 dev server，端口 3100）

```
/zh                                -> 200
/zh/address   （无 cookie）         -> 302  http://127.0.0.1:3100/zh/login?redirect=/zh/address
/zh/address   （伪造/失效 token）   -> 302  http://127.0.0.1:3100/zh/login?redirect=/zh/address
/zh/profile   （伪造/失效 token）   -> 302  http://127.0.0.1:3100/zh/login?redirect=/zh/profile
/zh/login                          -> 200
```

改造前 "伪造 token + localStorage 有 user-info" 的组合是能停在私有页上的，现在一律落到登录页。

### 2）客户端侧（真实浏览器端到端，`node .probe/session-expiry.probe.mjs http://127.0.0.1:3100`）

复现手法：把前端**登录态状态**置成"已登录且结论新鲜"（等价于用户刚登录过），
但浏览器里没有任何有效 token —— 页面显示已登录，任何需要登录的接口都是真 401。
这正是用户报的场景。全部走真实路由跳转 / 真实接口 / 真实 toast。

```
=== 场景 A1：受保护页（购物车）里接口 401 ===
  ✅ 前提：页面按登录态显示已登录
  ✅ URL 落到登录页                              (/zh/login)
  ✅ redirect 指回 /zh/cart                       (?redirect=/zh/cart)
  ✅ localStorage 的 user-info 已被删除
  ✅ 右上角不再显示已登录
  ✅ 弹出了「登录已过期」提示

=== 场景 A2：用户报的原路径 /profile、/address ===
  ✅ /zh/profile → 落到登录页 / redirect 指回原页 / 本地登录态已清 / 弹出「登录已过期」
  ✅ /zh/address → 落到登录页 / redirect 指回原页 / 本地登录态已清 / 弹出「登录已过期」

=== 场景 A3：结论已过期 → 进受保护页时重新校验 → 判定未登录并清缓存 ===
  ✅ 前提：页面仍按缓存显示已登录
  ✅ 中间件重新校验后拦下私有页
  ✅ 定时校验把死缓存一起清掉（刷新也不会复活）
  ✅ 告知用户为什么被拦下（「登录已过期」）

=== 场景 B：公开页（首页）接口 401 → 静默掉线，不跳转 ===
  ✅ 接口返回 401
  ✅ 仍停留在首页（没被踹去登录页）
  ✅ localStorage 的 user-info 已被删除
  ✅ 右上角已回到未登录
  ✅ 弹出了「登录已过期」提示

=== 场景 C：登录页输错密码（真请求）→ 不能被当成"登录过期" ===
  ✅ 仍停留在登录页
  ✅ 没有误弹「登录已过期」

=== 场景 D：localStorage 死缓存 vs 服务端权威结论 ===
  ✅ 服务端说未登录时，localStorage 的死缓存被清掉
  ✅ 右上角没有"又变回已登录"
```

改造前的对应行为（用户实测）：A1/A2 不会跳转、不会清态、只弹一句「新增地址失败」；
B 什么都不发生；A3 只显示登录引导而右上角仍是已登录。

## 六、已知边界（有意为之）

1. **60 秒新鲜期**：`AUTH_SEED_FRESH_MS` 内导航守卫会复用上次结论（清单 S20 要求的"不重复请求"）。
   这 60 秒内 token 恰好过期的用户会被放行进入，但页面首批接口（个人中心会同时拉
   资料/地址/订单/收藏）必然 401 → 兜底立刻生效。若把新鲜期调成 0，就退回到"每次切页都多一次
   `/api/auth/session`"，属于体验与开销的取舍，需要时可改这一个常量。
2. **403 不强制下线**：403 语义是"已登录但无权限"，静默交给页面处理。
3. **SSR 阶段不做提示与跳转**：那一层的保护由 `auth-seed` + `app/middleware/auth.ts` 负责，
   toast 与服务端路由跳转在 SSR 里没有意义。
4. **服务端令牌作废依赖 `/api/auth/logout`**：后端不可达时会话在 Redis 里残留到自然过期；
   本地 cookie 与前端状态不受影响（BFF 无论成败都清 cookie）。
5. **`isUnauthorizedError()` 仍把 401/403 一起当"引导登录"**（页面级语义），
   与"强制下线只看 401"（会话级语义）是两件事，不要合并。
