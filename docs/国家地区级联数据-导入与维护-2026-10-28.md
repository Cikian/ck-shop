## 二、表结构与关系

```
regions(6)          大洲
  └ subregions(22)  次区域（东南亚 / 中亚 / 西亚…）
      └ countries(250)          iso2=ISO 3166-1、phonecode、postal_code_regex、emoji、translations(JSON 19 语言)
          ├ states(5,327)       一级行政区：省 / 州 / 府 / 大区，含 iso3166_2、type_local、translations(JSON)
          │   ├ counties(14,058) 二级行政区（不是每个国家都有）
          │   │   └ county_states(16)  横跨多州的 county 映射
          │   └ cities(152,378)  城市层，可挂 state 或 county
          └ postcodes(0)         邮编（未灌）
translations(304,346)  ← 与上面各表通过 (place_type, place_id) 关联的地名译文长表
```

**三条硬约定**（维护时最容易踩）：

1. **表名不改、不加前缀**。上游每次更新是整表 `DROP + CREATE + INSERT`，改名就断了"重灌即升级"这条路。
2. **业务表不要建外键指向这些表**。整表 DROP 会被外键顶住；业务侧存字符串编码（`country_code` / `iso3166_2` / `cities.id`）即可。
3. **`cities` 不是纯城市**。它混了 `adm1`/`adm2`/`adm3`/`locality`/`village`/`section` 等层级，做下拉必须过滤 `type`，否则省名会出现在"城市"里（详见 §六.1）。

## 三、这次是怎么灌进去的（以及为什么大表不能走 MCP）

| 环节 | 工具 | 说明 |
|---|---|---|
| 建 9 张表 | **DBX MCP** `dbx_execute_batch` | 执行 `tools/schema-applied.sql` |
| 数据装载 | `mysql.exe` + `LOAD DATA LOCAL INFILE` | 执行 `tools/load-data.sql` |
| 校验 | **DBX MCP** + `tools/verify.sql` | 行数 / 孤儿 / 中文覆盖率 |

大表（`cities` 15 万行、`translations` 30 万行）为什么没走 MCP：

- MCP 的 SQL 是一个**字符串参数**，几十 MB 的 `INSERT` 传不动；本机 MySQL 的 `max_allowed_packet` 只有 **4 MB**，超了直接断。
- 退路本来是 MySQL 服务端的 `LOAD DATA INFILE`（服务端读文件，语句只有几十字节），
  但本机 `secure_file_priv` 是**空值** —— MySQL 把这种配置视为"禁止服务端读文件"，直接抛 `ERROR 1290`。
- 于是只剩客户端读文件的 `LOCAL` 变体：`mysql.exe --local-infile=1`。它才是唯一能一次灌完 15 万行的通道。

> 所以流程是"**结构和校验走 MCP，海量数据走本地客户端**"，不是绕开 MCP，而是 MCP 传不动数据本身。
> 想彻底走 MCP 只有两条路：把 `my.ini` 的 `secure-file-priv` 设成一个目录并重启 MySQL（之后服务端
> `LOAD DATA INFILE` 可用，语句仍走 MCP）；或者按 2 万行一批拆成上百次调用。都不划算。

## 四、以后怎么更新（三步，可复制粘贴）

### 0. 什么时候更新

上游大致每月发一次导出、每周补录数据。**建议半年跟一次**，或遇到"某个国家行政区划变了"时临时跟。
小版本号（`v5.0.0-export.2`）通常是数据修正，直接跟；大版本号（`v5.1.0`）可能改表结构，要先 diff `schema.sql`。

### 1. 拉新版本并生成 TSV

```powershell
# 版本号在 https://github.com/dr5hn/countries-states-cities-database/releases
# 改 tools/build-tsv.py 里的 TAG，然后：
$env:PYTHONIOENCODING='utf-8'
python docs\countries-states-cities-database\tools\build-tsv.py
```

脚本会：下载缺失的源文件（仓库小表用 JSON，大表用 release 的 `csv-*.gz`）→ 输出 `tools/tsv/*.tsv`。
**改版本时记得先删旧的 `*.gz` / `*.json`**，否则脚本会认为文件已存在而跳过下载。

### 2. 备份 + 重灌

```powershell
$env:MYSQL_PWD='<密码>'
$B  = "D:\Develop\phpstudy_pro\Extensions\MySQL5.7.26\bin"
$M  = "$B\mysql.exe"
$D  = "$B\mysqldump.exe"
$T  = "E:/CProject/ck-shop/docs/countries-states-cities-database/tools"

# 备份（只备这 9 张表，别整库 dump）
& $D --host=127.0.0.1 --port=3306 --user=root --default-character-set=utf8mb4 `
     --single-transaction ck-shop regions subregions countries states counties `
     county_states cities postcodes translations > D:\backup\region-20261028.sql

# 重建 + 装载（schema-applied.sql 里每张表都是 DROP IF EXISTS，可反复执行）
& $M --host=127.0.0.1 --port=3306 --user=root --default-character-set=utf8mb4 --local-infile=1 ck-shop `
     -e "source $T/schema-applied.sql"
& $M --host=127.0.0.1 --port=3306 --user=root --default-character-set=utf8mb4 --local-infile=1 ck-shop `
     -e "source $T/load-data.sql"

# ⚠️ 必跑：重灌会连索引一起丢掉，不补这两个索引城市搜索会从 5ms 退化到 495ms
& $M --host=127.0.0.1 --port=3306 --user=root --default-character-set=utf8mb4 ck-shop `
     -e "source $T/post-load-index.sql"
```

### 3. 自检（每次必跑）

```powershell
& $M --host=127.0.0.1 --port=3306 --user=root --default-character-set=utf8mb4 ck-shop `
     -e "source $T/verify.sql"
```

四条判定线：

1. **行数**量级对不对（城市 15 万、州 5 千、县 1.4 万，小幅漂移正常）；
2. **孤儿必须是 0**（`orphan_*` 四项全 0），否则说明父表没灌完就灌了子表——检查 `load-data.sql` 的顺序；
3. **中文覆盖率**国家/州应 >99%、城市全球约 90%；
4. **抽查**能一把查出"国家→州→城市"的中英当地名。

回滚：这 9 张表全是**只读参考数据**、没有任何业务表依赖它们（§二 约定2），所以最坏情况直接重新灌一遍旧版本即可，不影响订单和用户数据。

## 五、语言到底够不够用（实测，别再靠猜）

> **已全量导入 34 种语言**（`translations` 2,906,879 行）。店铺现在是 en/zh/fr 三门界面语言，
> 但那只是开发阶段的测试语言 —— 以后**新增界面语言不需要重灌数据，也不需要改导入脚本**，
> 直接用新的 locale code 去查 `translations` 即可（映射规则见
> `docs/地址国家地区级联-实施契约-2026-10-28.md` §2）。

数据里**每个地名都有三个来源**：

| 字段 | 内容 | 覆盖 |
|---|---|---|
| `name` | 主名（英文 / 拉丁转写） | 100% |
| `native` | 当地文字原名（ไทย / Việt / قازاق…） | ~100% |
| `translations` / 译文表 | 19–34 种语言的译名（含 `zh-CN`） | 见下 |

实测中文（`zh-CN`）覆盖率：

| 层级 | 覆盖 |
|---|---|
| 国家 | **250 / 250 = 100%** |
| 一级行政区（省/州） | **5,254 / 5,327 = 98.6%** |
| 城市（全球） | **138,038 / 152,378 = 90.6%** |

城市级分国差异很大——**你的目标市场恰恰是中文缺口最大的地方**：

| 国家 | 城市数 | 有中文名 | 中文覆盖率 |
|---|---:|---:|---:|
| 🇸🇬 新加坡 | 26 | 26 | 100% |
| 🇧🇳 文莱 | 9 | 9 | 100% |
| 🇵🇭 菲律宾 | 4,374 | 4,256 | 97.3% |
| 🇰🇭 柬埔寨 | 111 | 106 | 95.5% |
| 🇰🇿 哈萨克斯坦 | 270 | 255 | 94.4% |
| 🇱🇦 老挝 | 81 | 76 | 93.8% |
| 🇹🇯 塔吉克斯坦 | 79 | 71 | 89.9% |
| 🇰🇬 吉尔吉斯斯坦 | 59 | 53 | 89.8% |
| 🇺🇿 乌兹别克斯坦 | 162 | 135 | 83.3% |
| 🇹🇲 土库曼斯坦 | 37 | 30 | 81.1% |
| 🇲🇾 马来西亚 | 250 | 180 | 72.0% |
| 🇲🇲 缅甸 | 116 | 74 | 63.8% |
| 🇮🇩 印尼 | 710 | 451 | 63.5% |
| 🇹🇭 泰国 | 1,012 | 609 | **60.2%** |
| 🇻🇳 越南 | 480 | 235 | **49.0%** |

**结论：当地语言够"能选"，但不够"看得懂"。**
`name`+`native` 保证 100% 可选（越南用户看到 `Hà Nội` 完全认得），
但中文用户切到简体时，泰国/越南/印尼有 4–5 成的城市会**退回外文显示**。
所以这门数据不是"要不要中文"的问题，而是"缺口怎么兜"的问题——见 §五 末尾。

⚠️ 还有一个比覆盖率更麻烦的问题：**已覆盖的那部分，中文名质量参差**。实测样例：

- 正确：`Bangkok → 曼谷`、`Surabaya → 泗水`、`Bekasi → 勿加泗`、`Almaty → 阿拉木图`
- 生硬音译：`Jawa Barat → 爪哇巴拉特`（常见的正确译法是**西爪哇**）、`Jawa Timur → 东爪哇省`（这个又是对的）
- 缺失但明显该有：`Hanoi` 中文为空（而它下属的 `Hai Bà Trưng` 有"二征夫人郡"）

→ 社区数据的中文名是机器/半自动产出，**不能当"官方译名"用**。做客服地址核对时以原文为准。

**兜底策略（建议，未实现）**：
1. 显示优先级 `zh-CN 译名 → native → name`，绝不留空；
2. 缺中文的地方**不显示"（未翻译）"**，直接给当地文字——用户在地名场景下认当地字比认英文强；
3. 真要对目标市场补中文，缺口总量只有约 **1,300 条**（泰 403 + 越 245 + 印尼 259 + 马 70 + 缅 42），
   完全可以用 Wikidata（`cities.wikiDataId` 就是 Q-ID）批量补，或人工维护一张 `ck_shop_region_alias` 补丁表覆盖在上面。

## 六、已知坑（都踩过一遍了）

### 1. `cities` 混了多个行政层级 —— 做级联必须过滤

`type` 分布（前几位）：`city` 2.26 万、`municipality` 4.6 万、`locality` 1.9 万、`village` 0.8 万、`town` 0.5 万、
`adm2` 4,679、`adm3` 2,486、**`adm1` 2,211**、`section` 3,073。

`adm1` 是**省级记录**混进了城市表（例：阿富汗 Fayzabad 的 `type=adm1`）。不过滤的话，
"城市"下拉里会出现省名，用户选了就得到一个没有具体地点的地址。

建议的城市查询（按人口排序，只取真正的居民点）：

```sql
SELECT id, name, native, population
FROM cities
WHERE state_id = ? AND type IN ('city','municipality','town','adm2')
ORDER BY population DESC, name;
```

### 2. 有 3 条城市没有 `state_id`

v5 的设计（"国家本身没有州级"的情况）。前端级联要能容忍"该国有州 → 显示州；没有 → 直接跳城市"。

### 3. `postcodes` 是空表

上游 `csv-postcodes.csv.gz` 有 72 万行、约 +80 MB。只有"输入邮编反查城市"这种需求才值得灌。
**邮编校验不需要它** —— `countries.postal_code_regex`（如泰国 `^(\d{5})$`、越南 `^[0-9]{5,6}$`）现成可用。
要灌就按 §四 的流程加一条 `LOAD DATA` 即可。

### 4. 上游 JSON 里没有 `created_at` / `updated_at` / `flag`

官方 JSON 导出压根不带这三个键（全是 `null`），而 `flag` 是 `NOT NULL`。
`build-tsv.py` 因此**主动不输出**这三列，让建表默认值兜底。
**后果**：别指望用上游时间戳做增量同步 —— 每次更新都是全量重灌。

### 5. 中国数据在库里，但业务上用不到

数据集含中国 31 个省级 + 城市，但**没有区县**。按"不做国内销售"的前提，这块直接忽略，
不要再引入 jeecg 的 `pca.json` 那套三级数据（两套数据混在一个级联里，只会让"广东-深圳-南山区"这种
路径和海外路径打架）。

### 6. 国旗 emoji 在 Windows 上会退化成两个方框字母

`countries.emoji` 存的是 `🇹🇭` 这种区域指示符序列，Windows 没国旗字体。
店铺端已有前车之鉴（见 `types/store-locale.ts` 注释），**前端不要直接用 emoji 当国旗**，
继续走内联 SVG（`app/utils/locale-flag.ts` 那套）。
