### 2.2 四个刻意的设计决定

**① 订单 / 支付单 / 退款单三单分离。**
一笔订单可能有多笔支付尝试（第一次超时关闭、第二次成功），
退款也有独立的审核与渠道流转状态。把支付信息塞进订单表，
在"多次支付、部分退款"时就无处安放，对账也无从下手。

**② 账本类表不设 `del_flag`。**
`order_event`、`payment_notify_log`、`stock_log`、`fund_flow` 四张表故意没有删除标记：
账本条目被"删除"本身就是数据完整性问题——恰好是出问题的那条被删掉了，
事后什么都查不出来。要纠错只能追加一条反向流水。

**③ 订单表的 `del_flag` 是"归档"而不是"删除"。**
归档限制写在 SQL 的 `WHERE` 里（`AND order_status IN ('CANCELLED','CLOSED')`），
任何调用路径都绕不过去。有效订单（待支付/待发货/已发货/已完成）
**在接口层与 SQL 层都不存在删除能力**——不是"忘了加权限"，而是这个能力不存在。
Java 层也刻意不加 `@TableLogic`：加了之后 `selectById` 会静默返回 null，
客服按单号查一张归档订单会得到"订单不存在"，对交易系统而言"查不到"比"查得到"危险得多。

**④ 库存用"预占 + 实扣 + 释放"而非"下单直扣"。**
`可售量 = stock − frozen_stock`。所有预占都是带条件的原子 UPDATE：
```sql
UPDATE ck_shop_product SET frozen_stock = frozen_stock + #{qty}
 WHERE id = ? AND del_flag = 0 AND status = 'Y' AND stock - frozen_stock >= #{qty}
```
判断与修改在同一条语句里完成，影响 0 行即"没抢到"。不存在"先查再判断"的超卖窗口。

### 2.3 金额口径（混用必然产生对账差异）

```
total_amount     吊牌价合计        Σ original_price × qty       仅用于展示"省了多少"
product_amount   成交金额合计      Σ price × qty                优惠前
discount_amount  优惠合计          促销 + 券 + 积分 + 会员
freight_amount   运费
pay_amount       应付 = product_amount − discount_amount + freight_amount + other_fee
paid_amount      实收（以支付单成功金额回写，**不由前端传**）
refund_amount    累计已退（退款成功时累加）
```

- 全部 `decimal(12,2)` + Java `BigDecimal`，**禁止 double**；
- 舍入统一 `HALF_UP` 2 位（`MoneyUtils`），与 MySQL 的舍入行为一致；
- 多行分摊优惠用**最大余额法**（`MoneyUtils.allocate`），保证"各行之和 == 总额"，不会出现几分钱差异；
- `pay_amount` 与 `paid_amount` **必须分开**：未支付时前者已确定、后者为 0；
  组合支付时两者不等。合并成一个字段就表达不了"要收 100、实收 80"。

## 3. 订单状态机

```
WAIT_PAY ──PAY_SUCCESS──► WAIT_SHIP
   │
   ├──USER_CANCEL─────► CANCELLED
   ├──ADMIN_CANCEL────► CANCELLED
   └──TIMEOUT_CLOSE───► CLOSED

WAIT_SHIP ──SHIP────────► SHIPPED
   └──────ADMIN_CANCEL► CANCELLED   （前置：已全额退款）

SHIPPED ───CONFIRM_RECEIVE─► COMPLETED
   └──────ADMIN_CANCEL────► CANCELLED（前置：已全额退款）

COMPLETED / CANCELLED / CLOSED = 终态，不接受任何流转
```

- 唯一权威实现：`OrderStateMachine`。非法流转**直接抛异常**，不存在"警告一下继续"。
- 三个并行状态字段：`order_status`（履约）、`pay_status`（资金）、`refund_status`（售后）。
  退款只改后两者，**不回退订单状态**（货已发出，用 refund_status 表达）。
- 所有状态变更都是 CAS：`WHERE id=? AND order_status=? AND version=?`，影响 0 行即失败。

**掉单（超时关单 vs 最后一秒支付）的处理方式：**
关单走 CAS，支付成功也走 CAS，两者只有一个能成功。
若支付成功时发现订单已 `CLOSED`，**绝不丢弃这笔钱**：
支付单照常置为 SUCCESS、资金流水照常入账、写一条 `PAY_SUCCESS` 异常事件，
统计接口单独暴露 `closedButPaidOrders`（**正常应恒为 0**）交人工介入。

## 5. 关键契约

### 5.1 幂等键（防重复下单 / 重复退款）

- `POST .../submit` 的 `idempotentKey`、`POST .../refund/apply` 的 `requestId` **均为必填**，长度 ≤64。
- 前端约定：**进入结算页时生成一次**（`crypto.randomUUID()`），此后所有重试复用同一个值；
  下单成功后再进结算页要重新生成。
- 后端不提供"没传就自动生成"的兜底——那等于永远不幂等，用户连点两次就会真的下两单。
- 数据库唯一索引 `uk_order_idempotent` / `uk_refund_request` 是最后一道防线：
  并发重复提交时后一个请求撞唯一键，服务端捕获后返回**已存在的那笔订单**而不是报错。

### 5.2 结算价格令牌（防价格篡改 / 防挂旧价）

- `preview` 返回 `priceToken`：`HMAC-SHA256` 签名，内容为
  `userId | storeId | payAmount | itemsDigest | issuedAt | expireAt`。
- `submit` 必须回传，服务端：
  1. 验签 + 校验有效期（默认 15 分钟）+ 校验 userId/storeId 归属；
  2. 用服务端重算结果与令牌里的金额比对，**不一致就拒绝**，要求用户回结算页重新确认。
- **请求体里没有任何金额字段**：改价的入口在接口层面就不存在。
- `itemsDigest` 基于"按 productId|skuId 升序拼接"的规范化串，因此勾选顺序不同不影响，
  改数量/换 SKU 一定失效。
- 密钥配置项 `ck.shop.order.price-token-secret`。**生产必须显式配置**：
  未配置时用进程内随机密钥（仅开发可用），多实例部署会导致 A 实例签发的令牌在 B 实例验签失败。

### 5.3 支付链路（四层兜底）

| 层 | 实现 |
|---|---|
| ① 异步回调 | `POST /shop/pay/notify/{channel}` → 验签 → 落回调流水（唯一去重键）→ 状态机 → 资金流水 → 库存实扣 |
| ② 主动查询 | `POST /shop/order/store/pay/query`（用户点"我已支付"）、退款重试 |
| ③ 定时补单 | `ShopPaymentCompensateJob`，默认 `30 * * * * ?`，扫 INIT/PENDING 且创建 >2min 的支付单 |
| ④ 人工补偿 | `POST /shop/order/admin/compensate?orderNo=`（写 `COMPENSATE` 操作流水） |

**重复回调的三道防线**：回调流水唯一去重键 → 支付单状态 CAS（`WHERE status IN ('INIT','PENDING')`）
→ 资金流水唯一索引。任何一道单独都不够可靠。

**回调去重键的组成**：`channel + 事件类型 + 渠道流水号 + 事件状态 + 事件时间 + 我方单号`。
必须包含事件状态/时间——同一笔交易会推"支付成功""支付关闭""退款成功"多条**合法**回调，
只用流水号去重会把后面那些当成重复丢掉，后果是"钱退了但系统不知道"。

### 5.4 时间参数格式（**踩过坑，务必按此实现**）

查询条件里的时间字段在 DTO 中是 **`String`**，不是 `java.util.Date`。

> Spring 的 `DateFormatterRegistrar` 默认只给 `Date` 注册与 `Long`/`Calendar` 的转换器，
> **不会**注册 String→Date 格式化器。DTO 里写 `Date` 时，前端传
> `2026-10-14 18:30:00` 会抛 `TypeMismatchException` → 400，
> 而且**只有带时间筛选的请求才会 400**，不带筛选一切正常——极难在联调前发现。

解析收口在 `QueryDateUtils` / `OrderTimeRange`：

| 传入 | 作为开始时间 | 作为结束时间 |
|---|---|---|
| `2026-10-14` / `20261014` | `2026-10-14 00:00:00` | `< 2026-10-15 00:00:00`（覆盖整天） |
| `2026-10-14 18:30` | `2026-10-14 18:30:00` | `< 2026-10-14 18:31:00` |
| `2026-10-14 18:30:25` | `2026-10-14 18:30:25` | `< 2026-10-14 18:30:26` |
| `2026-10-14 00:00:00` | `2026-10-14 00:00:00` | `< 2026-10-15 00:00:00`（**推断为按天粒度**） |
| ISO（`T`/`Z`/`+08:00`/毫秒） | 正确解析 | 正确解析 |

要点：
- **结束时间按给定精度包含**，前端不要自己 +1 天或 +1 秒；
- 按天粒度的选择器常把日期格式化成 `yyyy-MM-dd 00:00:00`，后端会把这种"整点零点"
  **补成次日**——不补会把这一天整段漏掉，而静默漏数据会导致对账短款、客诉查不到单。
  交易系统里宁可多算，不可少算；
- 格式错误会返回中文业务异常，**不会静默当成 null**（那会变成"查全量"）。

### 5.5 敏感信息脱敏

| 场景 | 手机号 |
|---|---|
| 买家看自己的地址簿 / 自己的订单 | **完整**（他自己填的，脱敏只会让他无法核对） |
| 后台订单**列表** | 掩码 `138****8000`（列表会投屏、截图、多人查看） |
| 后台订单**详情** | **完整**（商家发货要打电话；此路径有权限校验 `shop-order:detail` + 操作流水）。**注意与列表的区别**：详情复用列表 VO，因此服务层必须显式回填明文（`ShopOrderServiceImpl.adminDetail`） |
| 操作流水、日志、回调报文 | 掩码（`ShopMaskUtils`） |

回归测试时应断言"前台订单详情响应体中**不含** `costAmount`、`grossProfit`"——
这两个字段只应出现在后台接口里（前后台用两个不同的 VO 类型隔离，
而不是靠服务层记得手动抹字段）。

### 5.6 数据可见域

- 前台：强制 `user_id + store_id` 过滤（`OrderRequestContextResolver` 统一构建上下文）。
- 后台：`ShopOrgScopeResolver` 求可见域（`shop-store:manage-all` 或 `admin` 角色 = 不限部门），
  按 `store_org_code` 前缀过滤；**按 id 操作的接口会额外做一次归属校验**，
  因为列表过滤挡不住"直接按单号调接口"。
- 可见域与店铺筛选域**取交集**，无交集时映射为恒假条件（fail-closed），
  **绝不把"没有交集"当成"不过滤"**。
- 订单同时存 `store_id`（业务归属）与 `store_org_code`（数据权限维度），
  明细行也冗余一份，避免统计时回表 join 造成跨店串数据。

## 6. 定时任务

编程式注册（`ShopOrderQuartzConfig`，`ApplicationRunner`），Cron 来自配置：

| 任务 | 默认 Cron | 配置项 |
|---|---|---|
| 超时关单 `ShopOrderTimeoutCloseJob` | `0 * * * * ?` | `ck.shop.order.job.timeout-close-cron` |
| 支付补单 `ShopPaymentCompensateJob` | `30 * * * * ?` | `ck.shop.order.job.compensate-cron` |

**为什么不用 `sys_quartz_job` 表注册**（这也是本项目其它模块的做法）：
平台的任务管理是"往表里插一行 + 到后台点【启动】"，对交易系统有两个硬伤——
容易被漏掉（脚本跑完没提示，超时关单不跑的后果是库存被未付款订单永久占用）、
环境不可复现（测试点了启动、生产忘了点）。
因此改为启动时幂等注册：`--add-job`/delete + `storeDurably()`，重复启动不会产生新旧两个触发器。

其它保护：
- `@DisallowConcurrentExecution` 防止上一轮未结束时并起来第二轮；
- 跨节点互斥由 Quartz 的 JDBC JobStore（集群模式）保证；
- 所有变更都做 CAS + 幂等，**多跑几次最多白跑，不会重复扣库存/重复入账**；
- 关单前会先向渠道确认支付结果（`ck.shop.order.timeout-close.require-query=true`），
  渠道说已成功就转为支付成功而**不关单**——这是"最后一秒支付"掉单的正面防线；
- 定时任务失败**不阻断应用启动**（定时任务失效可控，整站打不开是灾难），但会打 ERROR 日志。

## 7. 配置项

```yaml
ck:
  shop:
    order:
      pay-timeout-minutes: 30                  # 支付超时（分钟），同时是订单 pay_deadline
      price-token-secret: ""                   # 生产必须配置！
      price-token-ttl-seconds: 900             # 结算令牌有效期
      default-freight: 0                       # 默认运费（无运费模板时的兜底）
      stats.default-days: 30                   # 统计默认区间
      compensate.min-age-minutes: 2            # 补单只处理创建超过该时长的支付单
      timeout-close.require-query: true        # 关单前先查渠道（渠道查询故障时可临时关）
      job.enabled: true
      job.timeout-close-cron: "0 * * * * ?"
      job.compensate-cron: "30 * * * * ?"
    pay:
      default-channel: MOCK                    # 接入真实渠道后改 WECHAT/ALIPAY
      mock:
        enabled: true                          # 生产必须 false（关掉后 MOCK 渠道直接报错）
        secret: ck-shop-mock-pay-secret
        fail-rate: 0                           # 模拟渠道拒绝概率(%)，用于验证失败分支
        delay-seconds: 0                       # 模拟渠道延迟，用于构造"回调未到"
        notify-tolerance-seconds: 300          # 回调时间戳容差（防重放）
        query-not-found: true                  # 模拟"主动查询返回查无此单"
```

## 8. 接入真实支付渠道的步骤

1. 实现 `PaymentGateway`（`channel()` / `prepay` / `parseNotify` / `query` / `refund` / `close`），
   并为 `successAck()` / `failAck()` 提供渠道要求的应答格式；
2. 放在 `org.jeecg.` 包下并加 `@Component`（`PaymentGatewayRegistry` 自动注册；
   渠道编码重复会在**启动期**直接抛异常，避免"复制微信实现忘了改 channel"上线才发现）；
3. 把 `ck.shop.pay.default-channel` 改成新渠道；把 `ck.shop.pay.mock.enabled` 设为 `false`；
4. 在**渠道后台配置回调地址** `/jeecg-boot/shop/pay/notify/{channel}`；
5. 订单侧代码**一行都不用改**——回调处理、验签、幂等、状态机、资金流水、库存实扣全部复用。

接入检查清单（写在 `PaymentGateway` 接口注释里）：
- `parseNotify` 必须先验签再解析，并校验时间戳窗口；
- `query` 必须能区分 `NOT_FOUND`（可关单）与 `PENDING`（只能继续等），混为一谈就是掉单的开始；
- `refund` 的"受理中"（`PROCESSING`）不能当失败——很多渠道是异步退款的；
- 元↔分换算只在本实现类里做，且必须有单元测试。

## 11. 环境相关的既有问题（**与本次改动无关，但会拦住启动**）

启动打包后的 jar 时，Flyway 校验失败：

```
FlywayValidateException: Detected applied migration not resolved locally: 3.9.5.2
```

`flyway_schema_history` 里存在 `3.9.5.2 / V3.9.5_2__add_shop_product_sku.sql`（2026-10-11 应用成功），
但该脚本文件已不在仓库中——这是**本次改动之前就存在**的历史遗留状态，
叠加 `spring.flyway.validate-on-migrate=true` 会导致应用直接启动失败。

三种处理方式（任选其一）：
1. **恢复/重建该脚本文件**（最稳：保留历史可审计性）；
2. 确认该迁移内容已被基线 SQL 合并后，执行
   `DELETE FROM flyway_schema_history WHERE version = '3.9.5.2';`
   （这是 Flyway 对"本地已删除但历史仍有记录"的标准处置）；
3. 临时 `--spring.flyway.enabled=false` 启动（本次验证即采用此方式，仅用于冒烟，不建议常态化）。

> 本次验证时，`V3.9.5_9` 与 `V3.9.5_10` 已用 mysql 客户端**手工执行并验证幂等**，
> 因此即使 Flyway 被临时关闭，订单模块的表结构与菜单权限也已在开发库就位。
> 恢复正常 Flyway 后这两条迁移会因幂等而安全地重跑一次。
