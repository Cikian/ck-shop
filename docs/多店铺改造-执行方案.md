## 一、目标与已确认决策

| # | 决策 | 说明 |
|---|------|------|
| 1 | **删除"品牌"概念** | 品牌无业务意义，整块移除 |
| 2 | **一商品只在一个店铺上架** | 不再有"多渠道"，删掉 `ck_shop_product_store` 那套 |
| 3 | **用 JeecgBoot 部门作为店铺的数据隔离维度** | `sys_org_code` 为归属列；店铺 ↔ 部门 1:1 |
| 4 | **店铺管理中关联部门** | `ck_shop_store.depart_id` |
| 5 | **标签、预设规格（`ck_shop_options`）共享** | 保持全局，不加归属 |
| 6 | **分类按店独立** | 归属列统一为 `sys_org_code`（替换现有的 `store_id`） |
| 7 | **运营只能管本部门商品** | 可见域 `sys_org_code LIKE '当前部门org_code%'`；**运营不能改商品归属**；管理员/总部（`shop-store:manage-all`）不限 |
| 8 | **`spu_code` 唯一性按部门** | `uk(sys_org_code, spu_code)`，各店可重复（不影响前台路由：店铺身份来自域名/请求头） |

## 二、现状（已验证的事实，勿重复调研）

### 2.1 部门与店铺（数据库实际值）

```
sys_depart:
  Cikian.ltd       org_code=A06      org_type=1(公司)  id=2109513616048173058
    数码部          org_code=A06A01   org_type=2(部门)  id=2109513754053357569
    户外部          org_code=A06A02   org_type=2(部门)  id=2109513973277044738

ck_shop_store（已绑定部门）:
  default  默认店铺    depart_id=数码部   ← 前端 .env 的 STORE_CODE=default 指向它
  test     测试店铺    depart_id=NULL
  outdoor  户外专卖店   depart_id=户外部   ← 为空店铺，可直接用于多店验证
```

**`org_code` 是前缀式编码**（`A06` → `A06A01`），因此 `LIKE 'A06%'` 天然实现"本部门及以下"，上级部门可管下级。

### 2.2 已具备的框架能力（不用自己写）

- **`sys_org_code` 自动填充**：`MybatisInterceptor` 检测实体有 `sysOrgCode` 字段且值为空时，自动写入 `loginUser.getOrgCode()`。**新增商品自动归到操作人当前部门，零代码**。
- **部门切换**：`PUT /sys/selectDepart`，已带越权校验（只能切到自己所属部门），选择持久化到 `sys_user.org_code`。前端已有"切换租户和部门"对话框。
- **`LoginUser` 自带 `orgCode` / `orgId`**，业务层用 `SecurityUtils.getSubject().getPrincipal()` 取当前部门。

### 2.3 已知限制（不要踩）

- **JeecgBoot 原生数据规则套不上我们的商品接口**：它挂在 `QueryGenerator` 上，而商品列表走 `ProductQuery` DTO + 自定义 service。`QueryGenerator` 注释也明确"不支持在自定义 SQL 中写 `in #{sys_org_code}`"。
  → **做法：列名沿用 jeecg 规范，过滤在服务层显式实现。**
- **仓库里没有品牌表的建表脚本**（当初手工建的）。若需要回滚，DDL 见文末附录。

## 四、执行纪律（上一轮的教训，务必遵守）

1. **先改引用，最后删文件**；删除与引用更新必须在同一次原子改动里，不要分两次。
2. **大文件不要按行脚本手术**：注释块、跨行表达式、泛型会让大括号配平算错。要整体重写方法。
3. **`sys_org_code` 判定失败要报错**：无法确定当前部门时，拒绝保存，而不是写入 NULL（否则产生无归属的脏数据）。
4. **业务数据一律逻辑删除**，不物理删除；软删行占用唯一键时用"复活"（`UPDATE ... SET del_flag=0`）而不是先删再插。
5. **关系表/唯一键的 null 语义要写清**，不要留"好像是这样"的约定。
6. **schema 变更走迁移脚本**（`flyway/sql/mysql/` + `ck-server/db/`），保证代码与库同步演进。

### 7.3 与方案的刻意偏差（需知悉）

1. **可见域用前缀匹配**（`LIKE 'orgCode%'`）而非等值：依据方案 §一.7 与 §二.1（"前缀式编码天然实现本部门及以下"）。§3.2 里写的 `=` 按前缀实现，语义更一致（子部门商品不会被前台漏掉）。现有数据 `A06A01`/`A06A02` 互不为前缀，两种写法结果完全相同。
2. **`ShopStore` 多了一个只读派生字段 `departOrgCode`**（`@TableField(exist=false)`，由列表 join `sys_depart` 带出）。方案只写了加 `departId`，但前端"所属店铺"下拉需要 store → org_code 的映射；否则要么再开一个部门接口、要么让前端自己拼部门树。
3. **后台分类列表也加了同款可见域**（方案只要求前台分类树过滤）。否则运营在后台仍能看到别店分类，与"分类按店独立"矛盾。
4. **归属写入的"必须绑定店铺"校验只在归属发生变化（含新增）时执行**；编辑且归属原地不动时不校验——否则历史数据会因为后来解绑了店铺而变得不可编辑。
5. **"运营不能改归属"的具体语义**：编辑时归属必须原地不动（想改即报错）；新增时归属必须落在自己的可见域内。越权一律由后端拒绝，前端置灰只是体验配合。

### 7.7 首页轮播图分店铺管理（补充需求，2026-10-12）

**数据模型**：MongoDB `ck-saas.slideshow` 每篇文档加 `sys_org_code`（与商品/分类同一套隔离维度）。归属用**等值**匹配而不是前缀匹配——轮播图是"每店一份配置"的文档型数据，没有"本部门及以下"的下钻语义。

**存量迁移**：[ck-shop-slideshow-org-scope.js](ck-server/db/ck-shop-slideshow-org-scope.js)（已执行）把 2 篇存量文档（改造前是全局共享的）归入 `A06A01`（default 店铺绑定的数码部），并建了复合索引 `sys_org_code_1_enabled_1`。

**后端**：`CommonMongoService` 全部方法增加 `orgCode` 参数；店铺端读走新路径 `GET /home/slide/store`（方法级 `@IgnoreAuth`，免登录），由 `StoreResolver` → 店铺绑定部门 → 只读本店；管理端 `GET /home/slide/all?sysOrgCode=` 走可见域（运营被限定到本部门，总部可不限）；写接口用 `resolveWritableOrgCode` 判权，删除/排序按**文档自身归属**分组执行，跨店读写一律拒绝。

> ⚠️ **顺手修掉一个匿名写漏洞**：Shiro 里原本是 `filterChainDefinitionMap.put("/home/slide", "anon")`，**按路径**放行会连 POST/PUT 一起放行——任何人都能改写首页轮播图。现改为方法级 `@IgnoreAuth`（只放行店铺端 GET），写接口一律要求登录。实测无 token `POST /home/slide` 返回 **401「token为空!」**。

> ⚠️ **踩坑（值得记住）**：`@IgnoreAuth` 由 `IgnoreAuthPostProcessor` 在启动时扫描**方法级 mapping 的 `value()`** 生成免登录 URL 表；`@GetMapping` 不写路径时 `value()` 是**空数组**，扫出来是空的 —— 注解形同没加（实测 `GET /home/slide` 返回 401「token为空!」）。所以店铺端读必须给显式路径。现为 `/home/slide/store`，nuxt BFF 已同步（浏览器侧仍是 `/api/home/slide`，对页面无影响）。

**前端**：轮播图配置页顶部加「所属店铺」下拉（值 = 店铺的 `departOrgCode`；无 `shop-store:manage-all` 时禁用并固定为本部门），列表/新增/编辑/删除/排序全部落在所选店铺上；`SlideEditor` 提交时携带 `sysOrgCode`。

**刻意不做"全局默认轮播图回退"**：没有配置的店铺，前台就是空的（严格隔离，避免"忘了带店铺条件"那类事故）。若要"各店共用一份默认"，属于产品决策，需另行确认。

**运营要用这个页面还需要授权**：`ck:shop:slideshow:add / :edit / :delete / :deleteBatch` 目前只授给了 `admin`；`shop_operator_probe` 只有菜单没有按钮权限，因此运营能打开页面但存不了。

**验收**：[slideshow-scope.probe.mjs](.probe/slideshow-scope.probe.mjs) → **15/15 PASS**：default 前台 2 张 / outdoor 前台 0 张；未知店铺编码报错；无 token 写 → 401；运营不传店铺被限定本部门、跨店读/写被拒；运营在户外部新增后**只有户外前台能看到（1 张）**、数码部前台仍是 2 张不受影响。

## 八、代码评审发现（2026-10-12，只读审计，**未改动代码**）

评审范围：`ck-server/jeecg-boot-module/ck-shop`（含其依赖的 base-core 相关机制）、`admin-client/src/views/ck/shop/**`、`nuxt-shop/server/**` 与 `nuxt-shop/app/**`。按严重程度分组，均附文件:行号证据。

### 8.1 高

1. **店铺管理的导入/导出没有权限注解**
   [ShopStoreController.java:144](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/store/controller/ShopStoreController.java#L144) `exportXls` 与 [:152](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/store/controller/ShopStoreController.java#L152) `importExcel` 都没有 `@RequiresPermissions`（而 `shop-store:exportXls` / `shop-store:importExcel` 权限码在 `sys_permission` 里是存在且已授给 admin 的——只是代码里没用）。JeecgBoot **没有任何 URL 级权限过滤器**（`ResourceCheckFilter` 有定义但从未注册），因此**任何登录用户**都能调到这两个接口。
   实测影响有限：`ShopStore` 实体没有任何 `@Excel` 字段，导入会因 `code/name` 非空约束失败、导出是空表。但这是"靠运气"而不是靠设计，注解必须补上。

2. **店铺 ↔ 部门绑定没有归属限制**
   [ShopStoreServiceImpl.java:55](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/store/service/impl/ShopStoreServiceImpl.java#L55) `checkDepart` 只校验"部门存在 + 1:1"，不校验"只能绑自己所属的部门"。拿到 `shop-store:edit` 的运营可以：先把别的店铺解绑（`departId` 传空会被放行），再把自己的店铺绑到那个部门 → **直接把前台串店**（例：把 `default` 改绑 `A06A02`，主站就变成户外部的商品，数码部商品整体消失）。
   建议：改绑部门要求 `shop-store:manage-all`，或至少限定为本人可见域内的部门。

### 8.2 中

3. **导出绕过可见域**
   [JeecgController.java:52-64](ck-server/jeecg-boot-base-core/src/main/java/org/jeecg/common/system/base/controller/JeecgController.java#L52) 的 `exportXls` 只用 `QueryGenerator` 拼条件，**没有 `sys_org_code` 过滤**（商品/分类导出同理）。商品实体有 `@Excel` 字段，所以导出是真实可用的：一旦把 `shop-product:exportXls` 授给运营，导出文件里就是**全部部门**的商品。当前该权限只授给 `admin`，所以尚不可利用，但这是"授权即越权"的结构性风险。

4. **轮播图写接口缺权限注解**
   [SlideshowController.java:72](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/home/controller/SlideshowController.java#L72) `save`、[:81](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/home/controller/SlideshowController.java#L81) `edit`、[:100](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/home/controller/SlideshowController.java#L100) `replaceAll` 都没有权限注解（只有 delete/deleteBatch/sort 有）。归属是硬校验的，所以不会越权写别店；但"没有轮播图菜单权限的人也能改首页"。

5. **商品的 `categoryId` 不校验归属**
   `ShopProductServiceImpl` 全文没有任何校验 `product.category_id` 所属部门的逻辑。而管理员在商品表单能看到**所有店铺**的分类（分类列表对管理员不限），把 A 店商品挂到 B 店分类后：前台详情显示 B 的分类名，但 A 的分类树里没有这个分类 → 该商品在"按分类浏览"里永远找不到。
   建议在 `saveProduct/updateProduct` 里校验分类归属与商品归属一致。

6. **店铺未绑定部门 → 前台整站报错**
   `requireStoreOrgCode` 解析不到直接抛异常，于是 `/api/products`、`/api/categories`、`/api/home/slide` 全部 400，站点直接挂；而店铺表单又允许"暂不绑定部门"。建议二选一：保存店铺时校验（未绑部门的店铺不允许启用），或前台解析不到时返回空列表 + 错误日志（页面仍可访问）。

7. **软删除商品的 SPU 不能复用**
   [ShopProductServiceImpl.java:1103-1106](ck-server/jeecg-boot-module/ck-shop/src/main/java/org/jeecg/modules/shop/product/service/impl/ShopProductServiceImpl.java#L1103) 的唯一性预检**显式包含软删行**，所以删掉商品后重建同 SPU 会报"本店铺内商品SPU编码已存在"。方案 §四.4 明确要求这种情况用"复活"而不是拒绝，这里与纪律不符。

8. **"清除归属"是静默无操作**
   三个表单都把空值转成 `undefined`/`null`：商品 [ProductForm.vue](admin-client/src/views/ck/shop/product/components/ProductForm.vue) 的 `sysOrgCode: formData.sysOrgCode || undefined`、分类 ShopCategoryForm 的 `model.sysOrgCode || null`、店铺 [ShopStoreList.vue:67](admin-client/src/views/ck/shop/store/ShopStoreList.vue#L67) 绑部门下拉的 `allow-clear`。后端对空值一律"沿用库中现值"（且 MyBatis-Plus `updateById` 跳过 null），所以**用户点掉 ×、保存、提示"保存成功"，但归属其实没变**。要么去掉清除入口，要么在 UI 上明确"归属不可置空"。

### 8.4 已核查、确认没问题（避免重复怀疑）

- `ShopStore.departOrgCode` 这个 `@TableField(exist=false)` 只读派生字段是安全的：`QueryGenerator` 对 `exist=false` 的字段会跳过（[QueryGenerator.java:165-167](ck-server/jeecg-boot-base-core/src/main/java/org/jeecg/common/system/query/QueryGenerator.java#L165)），不会拼出不存在的列；`@Excel` 也不受影响。
- nuxt BFF 会统一透传 `x-language`（[apiClient.ts:33-52](nuxt-shop/server/utils/apiClient.ts#L33)），所以轮播图/商品/分类的语言兜底正常，中文站点不会只显示英文。
- 店铺端商品列表/详情、分类树、轮播图三处都做到了"解析不到店铺就报错、绝不回退全量"；跨店按 id 与按 `spuCode` 取详情均被拒（36 + 15 项冒烟已覆盖）。
- 归属写入的越权校验（运营不能改归属、按 id 操作也要过可见域）在商品/分类/轮播图三处都生效（冒烟已覆盖）。

**实测推翻的结论（不要照抄，会误导）**

| 审计结论 | 核验结果 |
|---|---|
| "编辑时 `targetUrl` 会被静默清空" | **方向相反**。实测：PUT 不传 `targetUrl` → 原值**保留**；PUT 传空串 → **也保留**。真正的缺陷是**链接清不掉**（空串被后端 `isNotEmpty` 判断忽略），不是被清空 |
| "新建轮播图会连发多条重复文档" | API 层不会重复：实测一次 POST 只产生一条，PUT 不插入副本。真实缺陷在前端：首次自动保存后 `handleSaved` → `loadData(payload.id='')` → `nextId` 取空、列表刷新后 `active` 落到 `listData[0]`（排序最靠前的那条），**草稿被丢弃且编辑器静默切到另一条**，用户继续输入就会误改已有轮播图 |
| "导入 Excel 能把 `sys_org_code` 写成别店/NULL" | **不成立**：`ShopProduct.sysOrgCode` 与 `ShopCategory.sysOrgCode` 都**没有 `@Excel`**，导入模板里根本没有这一列，归属只能由 `MybatisInterceptor` 按登录人部门兜底。残留问题只是"导入绕过 `validateOrgCodeBoundToStore` 与 SPU 预检" |
| "`SlideshowController` 关于 `@IgnoreAuth` 的注释推理是错的" | **注释是对的**：`IgnoreAuthPostProcessor.rebuildUrl` 在方法级 `value()` 为空数组时，内层 `for` 不执行 → 什么都不登记（我实测就是 401「token为空!」）。类级前缀只在方法级有值时才会拼上 |
| "轮播图语言兜底反了 → 中文站首页横幅整块空白" | **机制成立、后果不成立**。机制：`slide.get.ts` 确实不读 `?lang=`（`HomeHeroBanner` 传了但没人用），语言只来自 `x-language`（`middleware/locale.ts` 无 cookie 时默认 `en`）。但我实测 `x-language=zh/en/fr` 三种都返回了各自语言的 `pic_url`（素材都配了），不会空白。**风险是**：若某店只配了部分语言素材，而访客 locale 解析成没素材的语言，就会没有横幅图 → 建议 BFF 读 `?lang=`，后端改成"目标语言 → zh → en → 任一非空"兜底 |
| "`SlideEditor.vue:62` 里是商品文案" | 该文案实际在 [ProductForm.vue:62](admin-client/src/views/ck/shop/product/components/ProductForm.vue#L62)（商品表单），轮播图编辑器里没有。顺带：这句"切换后该商品将从前一个店铺下架"在新模型下措辞也不准（没有"上架到某店"这回事了），建议改成"切换后该商品只在新的店铺可见" |

**另外核实为"无问题"的两条**：`ShopStore.departOrgCode` 不会拼出不存在的列（`QueryGenerator` 跳过 `exist=false`）；`ShiroRealm` 的 `"cikian"` 后门分支**当前不可利用**（其后有一段无条件的 `checkUserTokenIsEffect(token)` 会覆盖），但仍应删除。

## 十一、敏感配置外置到 .env（spring.config.import）

### 11.1 做法

用 **Spring Boot 原生的 `spring.config.import`**，不引任何额外依赖：

```yaml
# jeecg-module-system/jeecg-system-start/src/main/resources/application.yml
spring:
  config:
    import:
      - optional:classpath:config/application-liteflow.yml
      - optional:file:./.env[.properties]              # 工作目录 = ck-server/
      - optional:file:../.env[.properties]             # 工作目录 = jeecg-module-system/
      - optional:file:../../.env[.properties]          # 工作目录 = jeecg-system-start（IDE/mvn 默认）
      - optional:file:../../../.env[.properties]       # 工作目录 = jeecg-system-start/target
      - optional:file:./ck-server/.env[.properties]    # 工作目录 = 仓库根目录
      - optional:classpath:.env[.properties]           # 万一放进了 resources（会被打进 jar，不推荐）
```

两个关键点，缺一不可：

1. **`[.properties]` 后缀提示是必须的**。`.env` 这种文件名没有内置的 `PropertySourceLoader`，
   Spring 会按"扩展名 env"去找 loader 并直接报 `Unable to load config data`。加上扩展名提示后，
   Spring 就按 **properties** 语法解析它（KEY=VALUE，不加引号、不写 export）。
2. **`file:` 路径是相对"启动时的工作目录"**，不是相对 jar/classpath。所以上面列了多个候选位置，
   每个都带 `optional:`。**推荐把 `.env` 放在 `ck-server/.env`**（与后端根 pom 同级），并且只放一处——
   多份同时存在时按导入顺序互相覆盖，排查起来很费劲。

### 11.2 文件

| 文件 | 是否提交 | 内容 |
|---|---|---|
| `ck-server/.env` | **不提交**（`.gitignore` 已加 `ck-server/.env`、`ck-server/**/.env`） | 真实密码/密钥，从 `application-dev.yml` 原样搬过来 |
| `ck-server/.env.example` | 提交 | 同名变量的模板（值留空/占位），顶部写明语法与复制方式 |

`application-dev.yml` 里原来的真实值全部换成 `${VAR}`（**敏感项不设默认值**：缺失时启动直接失败并
指名变量，例如 `Could not resolve placeholder 'MINIO_URL'`，这是刻意的——宁可起不来，也不要静默连错库）。
非敏感的 host/port 也一并外置，便于换环境。

### 11.4 验证证据（实测，不是"应该能行"）

| 场景 | 命令 | 结果 |
|---|---|---|
| **没有 .env** | 在 `%TEMP%` 下 `java -jar …`（任何候选路径都不存在） | 启动**失败**：`PlaceholderResolutionException: Could not resolve placeholder 'MINIO_URL'` —— 明确指名缺哪个变量 |
| **有 .env（IDE/mvn 默认目录）** | 在 `jeecg-system-start/` 下启动 | `Started JeecgSystemApplication in 42.6s`；MySQL 查询正常、Redis 鉴权通过、Mongo 连上并返回数据（`mongodb://***:***@127.0.0.1:27017/ck-saas`，日志里密码已打码） |
| **有 .env（仓库根目录）** | 在仓库根 `java -jar …` | `Started JeecgSystemApplication in 33.6s`（命中 `./ck-server/.env` 候选路径） |
| **yml 里已无密钥** | 用真实密码/密钥的值逐个 grep `application-dev.yml`（含 MySQL/Mongo/又拍云/GitHub/签名密钥等） | 全部无命中；仅剩 `allowed-packages: - cn.cikian.`（Java 包名前缀，非密钥） |

### 11.5 注意事项

1. **只放一个 .env**，并确保启动工作目录能命中它（见 11.1 的候选表）；不确定时用
   `mvn spring-boot:run` 或 `java -jar` 都从 `ck-server/` 或 `jeecg-system-start/` 启动即可。
2. `.env` 是 **properties 语法**：`KEY=VALUE`，不要加引号、不要 `export`、不要 YAML 缩进；注释要**独占一行**
   （`KEY=值  # 说明` 会把说明算成值的一部分）；值里的 `@`、`!` 等符号原样写即可。
3. **换环境只改 .env**，yml 不用动；新增敏感项时同步更新 `.env.example`（那份要提交，别写真实值）。
4. `test` / `prod` / `docker` / `oracle` 等其它 profile 的 yml **本次未改**（它们本来就是 `??` 模板占位），
   所以只有 dev profile 依赖 `.env`。要上线时，把那几个 profile 里的真实值也按同样方式抽出来即可。
5. Docker 部署：把 `.env` 挂载到容器的工作目录（或 `working_dir` 对应的相对位置），不要打进镜像。
6. **另一个遗留**：`jeecg-boot-module-airag/src/main/resources/application.yml` 里还硬编码着 MySQL、Redis（指向一个内网地址）
   与 pgvector 的账号密码明文（都是模板遗留的弱口令）。它是 AI 模块**独立启动**时用的配置（主程序用的是 start 模块的同名文件，
   不受影响），但同属"密钥进仓库"，建议一并按同套路抽走。
