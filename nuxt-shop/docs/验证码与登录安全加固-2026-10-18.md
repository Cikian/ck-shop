# 验证码与登录安全加固（2026-10-18）

> **已被 CikVerify 接入取代（2026-10-19）**：店铺端已删除自建图形验证码与 `captcha`/`checkKey`，
> 改由 CikVerify 行为验证码服务签发一次性 ticket；登录/注册/找回密码三条链路的现行实现见
> [CikVerify 验证码接入](./CikVerify验证码接入-2026-10-19.md)。
> 本文保留作为历史加固记录（其中的 Redis 限流、邮箱验证码失败锁定等仍然有效）。
>
> 回答四个问题：① 后端必须校验验证码 + 按 IP 限制；② 当前图形码 OCR 太容易；(3) 更合理的方案；④ 发信后图形码刷新造成的用户误解。
>
> 本文记录**已实施**的加固与**仍需决策**的方案，所有结论按"线上可被攻击"的标准写。

## 一、已实施（后端 = 权威，BFF = 边缘减速带）

### 1. 图形验证码：店铺端强制校验，不再受全局开关影响

- 之前 `ShopAccountServiceImpl#validateCaptcha` 里有一段 `jeecg.firewall.enableLoginCaptcha=false` 就直接放行；
  所有 profile 恰好都是 false → **图形码形同虚设**，脚本可以无限发信。
- 现在店铺端发信接口**无条件校验收到的 captcha + checkKey**，与 `LoginController#validateCaptcha`
  算法逐字一致（`md5(checkKey + signatureSecret) + 输入的code`）。
- 该开关仍然只影响**管理端**登录，店铺端与它解耦。

### 2. 图形码防爆破（Redis，多实例共享）

| 限制 | 阈值 | Redis key |
|---|---|---|
| 同一张图输错次数 | 5 次后该图作废 | `shop:rl:captcha:fail:key:{md5前缀}` |
| 同一 IP 输错次数 | 20 次 / 10 分钟 | `shop:rl:captcha:fail:ip:{ip}` |
| 校验通过 | 立即删除该图（一次性） | — |

> 说明：「同一张图 5 次」只有在**多个 IP 共享同一张图**时才会自然触发（单 IP 会先被发信限流拦住）；
> 已用 Redis 预置计数的方式验证过该分支确实返回"错误次数过多"。

### 3. 按 IP 的限流（Redis 固定窗口，fail-closed）

| 动作 | 单 IP 限制 | Redis key 前缀 |
|---|---|---|
| 发送邮箱验证码 | 5 次/分钟、20 次/小时 | `shop:rl:send-code:ip:*` |
| 密码登录 | 10 次/分钟、60 次/小时（另有账号级 5 次失败锁 10 分钟） | `shop:rl:login-pwd:ip:*` |
| 邮箱验证码登录 | 10 次/分钟 | `shop:rl:login-code:ip:*` |
| 注册 | 3 次/分钟、10 次/小时 | `shop:rl:register:ip:*` |
| 重置密码 | 5 次/分钟 | `shop:rl:reset:ip:*` |
| 生成图形码（BFF 边缘） | 10 次/分钟（原 60） | 进程内计数（见"局限"） |

发信本身还有**邮箱维度**限制：同邮箱 60 秒冷却、每日 10 条；同 IP 每日 30 条（`ShopEmailCodeService`）。

Redis 异常时这些消费型接口一律 **fail-closed**（返回"系统繁忙"），不会因为缓存故障把闸门放开。

### 4. 邮箱验证码防爆破

- 同一邮箱同一场景最多输错 **5 次**，达到后该验证码立即作废并锁定 15 分钟，必须重新获取；
- 错误提示会显示剩余次数（"邮箱验证码错误，还可尝试 4 次"），兼顾可用性；
- 验证码 5 分钟有效、一次性消费；发信有冷却 + 每日配额。

### 5. 客户端 IP 的可信链（限流的前提）

之前无论谁发请求都优先采信 `X-Forwarded-For` —— 攻击者直连后端时伪造该头即可让所有 IP 限流失效。

现在：

```
浏览器 --X-Forwarded-For(可选)--> Nginx/frp --> Nuxt BFF --X-Client-IP--> Java 后端
```

- BFF 用 `server/utils/clientIp.ts` 计算真实 IP：**只有 TCP 对端是回环/内网地址时**才采信代理头；
- BFF 把自己算出的 IP 强制写入 `X-Client-IP`（浏览器伪造的值被覆盖）；
- Java `ShopAccountSupport#resolveClientIp` 同样只在请求来自回环/内网时相信 `X-Client-IP`，
  公网直连只认 `remoteAddr`。

### 6. 图形码本身的加固（临时措施）

- 4 位 → **5 位**（36^5 ≈ 6046 万种组合，配合"5 次失败作废 + IP 限流"后枚举不可行）；
- 每个字符随机字体（Sans/Dialog/Mono）、±14° 旋转、随机剪切、随机字号、品牌色；
- 3~4 条低透明度贝塞尔曲线 + 浅色噪点，PNG 2x（224×96，前端按 112×48 显示）。

> ⚠️ 这只是"提高 OCR 成本"，**不是抗 OCR 的终点**。见第三节。

### 7. 交互修复（问题 ④）

旧行为：点「获取验证码」成功后立刻 `refreshCaptcha()`，用户看到一个空白的新图形码输入框，
误以为注册/登录前还要再输入一次（而提交接口其实根本不校验它）。

现在：

- 发信成功 → 组合式函数把 `captchaVerified = true`，界面切换成绿色「图形验证码已验证 · 本次操作无需再次输入」，
  **不再显示输入框、也不刷新图片**；
- 发信失败 → 图形码确实已被消费，自动换一张，并清空输入；
- 60 秒冷却结束（可重新发送）或用户**修改邮箱** → 自动恢复为需要重新验证；
- 图形码 input 去掉 `required`：它只服务于"发送邮箱验证码"，不作为表单提交的原生校验条件；
- 提交失败（邮箱验证码错等）**不会**再刷新图形码，避免误解。
- 实测（Edge headless，真实 BFF+Java+Redis）：发送成功后输入框消失、提示出现；
  提交错误邮箱验证码时**没有被要求重输图形码**，只提示"邮箱验证码错误，还可尝试 4 次"；改邮箱后图形码重新出现。

## 二、验证结果（本机真实链路）

| 断言 | 结果 |
|---|---|
| 错误图形码 | `400 图形验证码错误，请重新输入` |
| 正确图形码（从 Redis 取码） | `200 {"cooldownSeconds":60}` |
| 同一张图失败计数达阈值后输入正确码 | `400 图形验证码错误次数过多，请点击图片刷新后重试` |
| 发信第 6 次/分钟（同 IP） | `400 验证码发送过于频繁，请稍后再试` |
| 登录第 11 次/分钟（同 IP） | `400 登录尝试过于频繁，请稍后再试` |
| 邮箱验证码输错 1 次 | `400 邮箱验证码错误，还可尝试 4 次`（第 5 次后作废 + 锁 15 分钟） |
| 发信成功后界面 | 显示「已验证」，无输入框；60s 倒计时 |
| 提交注册（错误邮箱码） | 不要求图形码，只提示邮箱验证码错误 |
| 修改邮箱后 | 图形码重新出现、重新拉图 |

## 三、仍然存在的风险（必须知道）

1. **图形验证码不是抗 OCR 的可靠手段。** 5 位 + 扭曲 + 噪点能挡住通用 OCR/低端打码，
   但针对性训练的模型与人工打码平台仍可低成本通过。**真正的边界是限流 + 邮箱配额 + 验证码尝试上限**，
   图形码只是抬高单次成本。
2. **BFF 边缘限流是进程内计数**（`server/utils/rateLimit.ts`）：多实例部署时每实例各算一份；
   权威限制在 Java + Redis（上面的表），所以不会出现"完全没限流"，但边缘层会打折。
3. **图形码生成接口在后端没有 IP 限流**：目前靠 BFF 10 次/分钟挡。生产必须保证
   **9951 端口只对内网/BFF 开放**（不要直接暴露到公网），否则攻击者可绕过 BFF 直接刷图/刷接口。
4. **用户枚举**：登录/发信仍会明确返回"该邮箱尚未注册/已注册"。可用性优先的取舍，
   但攻击者可以批量探测邮箱是否注册。若安全优先，应改为统一文案（登录："邮箱或密码错误"；
   发信："如果该邮箱可用，验证码已发送"）。
5. 图形码的 code 走 Redis（60 秒 TTL），与 `enableLoginCaptcha` 解耦后，**本地开发也必须看图输码**（前端一直有图）。
6. 管理端登录仍受 `jeecg.firewall.enableLoginCaptcha` 控制（当前 false）；图形码变 5 位对管理端无破坏，
   但若开启管理端验证码，需确认管理端登录表单始终提交 captcha/checkKey。

## 四、方案选择（需要决策）

| 方案 | 抗 OCR/自动化 | 成本 | 备注 |
|---|---|---|---|
| **A. 托管验证码**（腾讯云验证码 / 阿里云验证码 2.0） | ★★★★★（风控评分、无感/滑块、持续对抗） | 需要云账号、SecretId/Key、前端 SDK；按量计费 | **线上推荐**；国内网络可达；无需自己维护对抗模型 |
| **B. 自托管行为验证码**（滑块/旋转/点选，如 tianai-captcha） | ★★★☆（无 OCR 问题，但存在打码平台/轨迹模拟） | 新依赖 + 图片资源 + 前后端改造；需验证与 Spring Boot 4/JDK17 兼容 | 不想上云时的折中 |
| **C. 维持加固图形码 + 严格限流（当前）** | ★★（对通用 OCR 有效，对定向模型/人工打码无效） | 0 新依赖 | 作为"够用"的过渡；本次已加到 5 位 + 多次作废 + IP 限流 |
| **D. PoW + 配额（不推荐单独使用）** | ★★（可被 GPU/脚本廉价求解） | 中（前端 Worker + 后端校验） | 只能作为补充，不适合单独保护发信 |

**建议路线**：线上直接上 **A（腾讯云/阿里云验证码）**；如果暂时没有云账号，先保留 C（已加固），
把"发信配额 + 失败锁定 + 监控告警"作为主防线，同时排期 B 或 A。
