# Nuxt Shop 项目结构与技术栈说明

> 本文档用于快速了解项目整体架构、技术栈、核心模块和开发规范，方便新成员或 AI Agent 快速上手。

---

## 一、项目概况

- **项目名称**：nuxt-shop（Nuxt 商城演示项目）
- **项目类型**：电商前台展示 + 用户系统（B2C 模式）
- **后端对接**：JeecgBoot（Java），通过 HTTP API 方式通信
- **核心架构模式**：BFF（Backend for Frontend），前端不直接调用 Java 后端，通过 Nuxt Server 层中转

## 四、核心架构详解

### 4.1 三层请求架构（BFF 模式）

这是项目最核心的设计模式。前端不直接调用 Java 后端，而是通过 Nuxt Server 层做 BFF 中转：

```
浏览器 → Nuxt Server (BFF 层) → Java 后端 (JeecgBoot)
```

**设计优势：**

1. **安全性高**：AES 密钥、签名密钥都只存在于 server 端 runtimeConfig，不会打包进浏览器 JS
2. **Token 安全**：token 存在 httpOnly cookie 中，前端 JS 无法读取，有效防止 XSS 窃取
3. **统一处理**：所有请求统一加签、统一错误处理、统一语言透传、统一响应解包
4. **无跨域问题**：前端只请求同源的 `/api/*`，不受浏览器跨域限制
5. **前端轻量**：前端页面只负责 UI 渲染，业务逻辑和安全处理都下沉到 server 层

### 4.2 核心文件职责速查

| 文件路径 | 核心职责 | 重要程度 |
|----------|----------|----------|
| `server/utils/apiClient.ts` | 后端 API 统一客户端，自动加签名/token/语言头，自动解包响应 | ⭐⭐⭐ 最高 |
| `server/utils/crypto.ts` | AES-CBC 加密密码（key/iv 从 runtimeConfig 读取） | ⭐⭐⭐ 最高 |
| `server/utils/signMd5.ts` | MD5 签名生成（JeecgBoot 签名机制） | ⭐⭐⭐ 最高 |
| `composables/useAuth.ts` | 前端认证状态管理（登录/登出/用户信息/恢复登录态） | ⭐⭐⭐ 最高 |
| `composables/useCaptcha.ts` | 验证码刷新逻辑 | ⭐⭐ 中 |
| `middleware/auth.ts` | 路由守卫，未登录跳登录页 | ⭐⭐ 中 |
| `nuxt.config.ts` | 项目全局配置（模块、i18n、SEO、runtimeConfig 等） | ⭐⭐⭐ 最高 |

### 4.3 完整请求流程（以登录为例）

```
1. 浏览器 login.vue 提交表单
   ↓ 用户点击登录
2. composables/useAuth.ts 的 login()
   ↓ $fetch('/api/auth/login', { method: 'POST', body })
   （浏览器 → Nuxt Server，同源请求，无跨域）
3. Nitro 路由匹配
   ↓ /api/auth/login → server/api/auth/login.post.ts
   （基于文件名自动路由，无需手写路由表）
4. server/api/auth/login.post.ts 执行
   ├─ readBody(event) 拿明文密码等参数
   ├─ encryptPassword(明文) → AES-CBC 加密（只在 server 端，浏览器看不到 key）
   └─ createApiClient(event) → 拿到 $fetch 实例
5. apiClient onRequest 钩子
   ├─ 加 Accept-Language / x-language 头（语言透传）
   ├─ 如果 withAuth，从 httpOnly cookie 读 token，加 x-access-token 等头
   ├─ signMd5Utils.getSign(url, params, body) → 计算 MD5 签名
   └─ 加 timestamp / sign / version / token 请求头
   ↓ （Nuxt Server → Java 后端，server-to-server，不受跨域限制）
6. Java 后端 (JeecgBoot)
   ├─ 校验 sign、timestamp（防篡改/防重放）
   ├─ 验证账号密码、验证码
   └─ 返回统一格式：{ code, message, result, success, timestamp }
7. apiClient onResponse 钩子
   ├─ 判断 body.success
   │    - 失败 → createError 抛 400，流程中断
   │    - 成功 → response._data = body.result（剥掉外层 envelope）
   └─ api() 函数最终 resolve 出 result 内部数据
8. 回到 login.post.ts
   ├─ setCookie('access-token', result.token, { httpOnly: true, ... })
   │   （token 写入 httpOnly cookie，浏览器 JS 读不到）
   └─ return { userInfo, tenantList }（只返回非敏感数据）
9. Nitro 序列化 JSON + Set-Cookie 头返回给浏览器
10. 浏览器收到响应
    ├─ 浏览器自动存 httpOnly cookie（JS 拿不到，自动带上后续请求）
    └─ useAuth 存 userInfo 到 localStorage（仅用于页面回显）
11. login.vue 跳转 /profile
```

### 4.4 JeecgBoot 签名机制

这是与 Java 后端通信的核心，所有请求都必须带签名，否则后端会拒绝。

**签名算法步骤：**

1. 合并所有参数：URL query 参数 + requestParams + body 参数 → 一个对象
2. 按 key 字母升序排序（sortAsc）
3. 删除 `_t` 字段（如果有）
4. 拼接：`JSON.stringify(排序后的对象) + signSecret`
5. 取 MD5 值，转大写 → 得到最终 sign

**请求必带 header：**

| Header | 说明 |
|--------|------|
| `timestamp` | 当前时间戳（毫秒） |
| `sign` | 上面算出的 MD5 签名（大写） |
| `version` | 固定值 `v3` |
| `token` | 登录后带上（与 x-access-token 等价） |
| `x-access-token` / `Authorization` | 登录 token |
| `tenant-id` | 租户 ID，目前固定 `0` |
| `Accept-Language` / `x-language` | 语言透传 |

**签名密钥：** 存储在 runtimeConfig.signSecret，从环境变量 `SIGN_SECRET` 读取，默认 `dd05f1c54d63749eda95f9fa6d49v442a`

## 五、认证与安全

### 5.1 Token 存储策略

- **存储位置**：httpOnly cookie（key 为 `access-token`）
- **安全性**：浏览器 JS 完全读不到，防 XSS 窃取
- **有效期**：7 天（`maxAge: 60 * 60 * 24 * 7`）
- **SameSite**：`lax`
- **Secure**：生产环境（HTTPS）开启，本地开发关闭

### 5.2 AES 加密配置

- **算法**：AES-CBC 模式
- **Padding**：Pkcs7
- **Key**：`AES_KEY`（16位，默认 `1234567890adbcde`）
- **IV**：`AES_IV`（16位，默认 `1234567890hjlkew`）
- **加密时机**：在 server 端加密，浏览器只传明文密码（HTTPS 传输也是加密的）
- **注意**：目前 IV 是固定值，CBC 模式下理论上应该每次随机，需与 Java 后端保持一致

### 5.3 环境变量（.env）

| 变量名 | 说明 | 默认值 |
|--------|------|--------|
| `API_BASE_URL` | Java 后端 API 地址 | `http://127.0.0.1:9951/api` |
| `AES_KEY` | AES 加密 key（16位） | `1234567890adbcde` |
| `AES_IV` | AES 加密 iv（16位） | `1234567890hjlkew` |
| `SIGN_SECRET` | MD5 签名密钥 | `dd05f1c54d63749eda95f9fa6d49v442a` |

> ⚠️ **重要**：这些密钥默认值是 JeecgBoot 开源默认值，生产环境必须更换！

## 六、国际化（i18n）

### 6.1 配置

- **策略**：`prefix` 模式 —— 所有语言都带 URL 前缀（如 `/en/`、`/zh/`、`/fr/`）
- **默认语言**：English (`en`)
- **支持语言**：中文(zh)、英文(en)、法文(fr)
- **语言包目录**：`i18n/locales/`
- **加载方式**：lazy 按需加载，减小首屏体积
- **浏览器语言检测**：只在根路径 `/` 自动跳转，用户手动切换后用 cookie 记住

### 6.2 语言透传机制

前端语言环境会通过以下方式传递给 Java 后端：

- 请求头 `Accept-Language`：如 `zh-CN`、`en-US`
- 请求头 `x-language`：如 `zh`、`en`

在 `server/utils/apiClient.ts` 中自动处理，优先级：
1. 读取请求头的 `x-language`
2. 读取 `event.context.locale`（@nuxtjs/i18n 解析出的）
3. 兜底默认 `en`

## 七、开发规范与约定

### 7.1 新增功能的标准流程

以"新增订单列表"为例：

**1. 新增 server/api（必须）**

```ts
// server/api/orders.get.ts
export default defineEventHandler(async (event) => {
  const api = createApiClient(event, { withAuth: true })
  return await api('/order/list', { query: getQuery(event) })
})
```

**2. 新增 composable（推荐，非必须）**

```ts
// composables/useOrders.ts
export const useOrders = () => {
  const orders = useState('orders', () => [])
  const fetchOrders = async () => {
    orders.value = await $fetch('/api/orders')
  }
  return { orders, fetchOrders }
}
```

**3. 新增页面（必须）**

```vue
<!-- app/pages/orders/index.vue → 路由 /orders -->
<script setup lang="ts">
const { data: orders } = await useFetch('/api/orders')
</script>
```

**4. 新增 i18n 文案（有多语言文本时）**

在 `i18n/locales/zh.json`、`en.json`、`fr.json` 中添加对应 key。

**5. 新增导航入口（需要时）**

在 `app/components/Header.vue` 中添加 `NuxtLinkLocale`。

### 7.2 请求方式选择

| 场景 | 用哪个 | 原因 |
|------|--------|------|
| 页面加载时展示的数据（普通 GET） | `useFetch` | 自动 SSR、去重、loading 状态 |
| 页面加载数据，但要自定义 key / 监听变量 / 合并多接口 | `useAsyncData` | 更灵活，完全可控 |
| 用户点击按钮、提交表单等一次性动作 | `$fetch` | 不需要和组件生命周期绑定 |
| composable 内部方法 | `$fetch` | composable 不在 setup 顶层同步执行 |

### 7.3 apiClient 使用规范

- **所有对接 Java 后端的请求都必须走 `createApiClient`**，不要直接写 `$fetch('http://...')`
- 需要登录态的接口传 `{ withAuth: true }`，会自动从 cookie 读 token
- 不需要登录的接口不传或传 `{ withAuth: false }`
- apiClient 会自动：加签名、加语言头、解包 result、统一错误处理

### 7.4 目录命名约定

- `server/api/` 下的文件按 REST 规范命名，动词通过 HTTP method 区分
  - `xxx.get.ts` → GET 请求
  - `xxx.post.ts` → POST 请求
  - `[param].get.ts` → 动态路径参数
- `composables/` 下的文件用 `useXxx.ts` 命名
- 页面组件放在 `app/pages/` 下，自动生成路由

## 九、待改进 / 注意事项

### 高优先级（安全类）

1. **生产环境密钥更换**：`.env` 中的 AES_KEY、AES_IV、SIGN_SECRET 用的是 JeecgBoot 默认值，上线前必须更换
2. **清理调试日志**：`login.post.ts` 和 `apiClient.ts` 中有 `console.log`，生产环境应移除或加 `import.meta.dev` 判断
3. **Header 下拉菜单英文硬编码**：`Profile`、`Logout` 等文案没走 i18n，与项目其他地方不一致

### 中优先级（代码健壮性）

1. **商品接口还是 mock 数据**：`products.get.ts` 和 `[slug].get.ts` 是写死的假数据，接入真实后端时要换成 `createApiClient` 调用
2. **apiClient 响应解包方式**：直接改写 `response._data` 属于 side effect 写法，类型推导不够精准，可考虑用包装函数替代
3. **AES 固定 IV**：CBC 模式下 IV 理论上应该随机，目前是固定值，需确认 Java 后端是否也如此
4. **缺少超时和重试配置**：apiClient 目前没有设置 timeout 和 retry，后端抖动时体验较差

### 低优先级（架构一致性）

1. **products 没抽 composable**：目前直接在页面用 useFetch，如果之后需要跨页面共享状态，建议抽出 `useProducts.ts`
2. **更多功能待开发**：购物车、下单、支付、搜索、分类等电商核心功能还未实现

## 十一、快速上手

```bash
# 1. 安装依赖
npm install

# 2. 启动开发服务器
npm run dev

# 3. 访问 http://localhost:3000
#    会自动跳转到 /en/（默认英文），可切到 /zh/ 看中文
```

**对接 Java 后端：** 修改 `.env` 中的 `API_BASE_URL` 为你的后端地址，确保 AES_KEY、AES_IV、SIGN_SECRET 与后端一致。
