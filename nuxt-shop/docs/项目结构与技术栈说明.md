# Nuxt Shop 项目结构与技术栈说明

> 本文档用于快速了解项目整体架构、技术栈、核心模块和开发规范，方便新成员或 AI Agent 快速上手。

---

## 一、项目概况

- **项目名称**：nuxt-shop（Nuxt 商城演示项目）
- **项目类型**：电商前台展示 + 用户系统（B2C 模式）
- **后端对接**：JeecgBoot（Java），通过 HTTP API 方式通信
- **核心架构模式**：BFF（Backend for Frontend），前端不直接调用 Java 后端，通过 Nuxt Server 层中转

### 2.4 构建与开发

包管理器为 **npm**（仓库内锁文件是 `package-lock.json`，没有 bun/yarn/pnpm 锁文件）。
`package.json` 中**全部**脚本如下（不再有其它脚本）：

| 命令 | 实际执行的命令 | 说明 |
|------|----------------|------|
| `npm run dev` | `nuxt dev --host` | 启动开发服务器（监听 0.0.0.0，默认 3000；局域网/手机真机调试可直接访问） |

| `npm start` | `node --env-file-if-exists=.env .output/server/index.mjs` | **生产启动**：直接跑 `.output/`，并由 Node 自带 `--env-file-if-exists` 读取 `.env` |

## 四、核心架构详解

### 4.1 三层请求架构（BFF 模式）

这是项目最核心的设计模式。前端不直接调用 Java 后端，而是通过 Nuxt Server 层做 BFF 中转：

```
浏览器 → Nuxt Server (BFF 层) → Java 后端 (JeecgBoot)
```

**设计优势：**

1. **安全性高**：AES 密钥、签名密钥都只存在于 server 端 runtimeConfig，不会打包进浏览器 JS
2. **Token 安全**：token 存在 httpOnly cookie 中，前端 JS 无法读取，有效防止 XSS 窃取
3. **统一处理**：所有请求统一加签、统一错误处理、统一语言透传、统一响应解包
4. **无跨域问题**：前端只请求同源的 `/api/*`，不受浏览器跨域限制
5. **前端轻量**：前端页面只负责 UI 渲染，业务逻辑和安全处理都下沉到 server 层

### 4.2 核心文件职责速查

| 文件路径 | 核心职责 | 重要程度 |
|----------|----------|----------|
| `server/utils/apiClient.ts` | 后端 API 统一客户端，自动加签名/token/语言头，自动解包响应 | ⭐⭐⭐ 最高 |
| `server/utils/authCookie.ts` | 登录 cookie 的**唯一写入点**（httpOnly，7 天，Secure 由 `COOKIE_SECURE` 决定） | ⭐⭐⭐ 最高 |
| `server/utils/crypto.ts` | AES-CBC 加密密码（key/iv 从 runtimeConfig 读取） | ⭐⭐⭐ 最高 |
| `server/utils/signMd5.ts` | MD5 签名生成（JeecgBoot 签名机制） | ⭐⭐⭐ 最高 |
| `types/store-locale.ts` | 语言清单唯一来源（i18n / BFF `?lang=` / Intl 标签都由它派生） | ⭐⭐⭐ 最高 |
| `composables/useAuth.ts` | 前端认证状态管理（登录/登出/用户信息/恢复登录态） | ⭐⭐⭐ 最高 |
| `composables/useApiError.ts` | `$fetch` 错误 → 可读文案（全站错误提示唯一实现） | ⭐⭐ 中 |
| `composables/useIdempotencyKey.ts` | 幂等键生成（下单/支付防重复提交） | ⭐⭐ 中 |
| `composables/useCaptcha.ts` | 验证码刷新逻辑 | ⭐⭐ 中 |
| `app/middleware/auth.ts` | 路由守卫，未登录跳登录页（契约见 `docs/auth-guard-contract.md`） | ⭐⭐ 中 |
| `server/middleware/csrf.ts` | 写操作 CSRF 防护 | ⭐⭐ 中 |
| `nuxt.config.ts` | 项目全局配置（模块、i18n、SEO、runtimeConfig、密钥非默认值校验） | ⭐⭐⭐ 最高 |

### 4.3 完整请求流程（以登录为例）

```
1. 浏览器 login.vue 提交表单
   ↓ 用户点击登录
2. composables/useAuth.ts 的 login()
   ↓ $fetch('/api/auth/login', { method: 'POST', body })
   （浏览器 → Nuxt Server，同源请求，无跨域）
3. Nitro 路由匹配
   ↓ /api/auth/login/password → server/api/auth/login/password.post.ts
   （基于文件名自动路由，无需手写路由表；另有 email-code.post.ts 走邮箱验证码登录）
4. server/api/auth/login/password.post.ts 执行
   ├─ readBody(event) 拿明文密码等参数
   ├─ encryptPassword(明文) → AES-CBC 加密（只在 server 端，浏览器看不到 key）
   └─ createApiClient(event) → 拿到 $fetch 实例
5. apiClient onRequest 钩子
   ├─ 加 Accept-Language / x-language 头（语言透传）
   ├─ 如果 withAuth，从 httpOnly cookie 读 token，加 x-access-token 等头
   ├─ signMd5Utils.getSign(url, params, body) → 计算 MD5 签名
   └─ 加 timestamp / sign / version / token 请求头
   ↓ （Nuxt Server → Java 后端，server-to-server，不受跨域限制）
6. Java 后端 (JeecgBoot)
   ├─ 校验 sign、timestamp（防篡改/防重放）
   ├─ 验证账号密码、验证码
   └─ 返回统一格式：{ code, message, result, success, timestamp }
7. apiClient onResponse 钩子
   ├─ 判断 body.success
   │    - 失败 → createError 抛 400，流程中断
   │    - 成功 → response._data = body.result（剥掉外层 envelope）
   └─ api() 函数最终 resolve 出 result 内部数据
8. 回到 password.post.ts
   ├─ setAccessTokenCookie(event, result.token)
   │   （server/utils/authCookie.ts：httpOnly cookie，浏览器 JS 读不到；Secure 由 COOKIE_SECURE 决定）
   └─ return { userInfo, tenantList }（只返回非敏感数据）
9. Nitro 序列化 JSON + Set-Cookie 头返回给浏览器
10. 浏览器收到响应
    ├─ 浏览器自动存 httpOnly cookie（JS 拿不到，自动带上后续请求）
    └─ useAuth 存 userInfo 到 localStorage（仅用于页面回显）
11. login.vue 跳转 /profile
```

### 4.4 JeecgBoot 签名机制

这是与 Java 后端通信的核心，所有请求都必须带签名，否则后端会拒绝。

**签名算法步骤：**

1. 合并所有参数：URL query 参数 + requestParams + body 参数 → 一个对象
2. 按 key 字母升序排序（sortAsc）
3. 删除 `_t` 字段（如果有）
4. 拼接：`JSON.stringify(排序后的对象) + signSecret`
5. 取 MD5 值，转大写 → 得到最终 sign

**请求必带 header（以 `server/utils/apiClient.ts` 实际代码为准）：**

| Header | 说明 |
|--------|------|
| `timestamp` | 当前时间戳（毫秒） |
| `sign` | 上面算出的 MD5 签名（大写） |
| `version` | 固定值 `v3` |
| `X-Access-Token` | 登录 token，**只发这一个 token 头**（`withAuth: true` 时从 httpOnly cookie 读取） |
| `tenant-id` | 租户 ID，目前固定 `0` |
| `x-language` | 语言透传（`zh` / `en` / `fr`） |
| `Accept-Language` | 语言透传（BCP-47，如 `zh-CN`、`en-US`） |

**签名密钥：** 存储在 runtimeConfig.signSecret，从环境变量 `SIGN_SECRET` 读取。
仓库中**不再保留可用的默认密钥**：`nuxt.config.ts` 启动时会校验 `AES_KEY` / `AES_IV` / `SIGN_SECRET`，
若为空或仍是 JeecgBoot 开源默认值（如 `dd05f1c54d63749eda95f9fa6d49v442a`）则**直接拒绝启动**；
只有显式设置 `ALLOW_INSECURE_DEMO_SECRETS=true`（仅限本地开发）才放行并打印告警。

## 五、认证与安全

### 5.1 Token 存储策略

- **存储位置**：httpOnly cookie（key 为 `access-token`；唯一写入点 `server/utils/authCookie.ts`）
- **安全性**：浏览器 JS 完全读不到，防 XSS 窃取
- **有效期**：7 天（`maxAge: 60 * 60 * 24 * 7`，与后端 JWT 对齐）
- **SameSite**：`lax`
- **Secure**：由 `COOKIE_SECURE` 决定，**默认 `true`**（只有显式 `COOKIE_SECURE=false` 才关闭；
  早期实现用 `NODE_ENV === 'production'` 判断，而生产启动命令并不设置 `NODE_ENV`，会导致线上 cookie 不带 Secure，已修正）

> ⚠️ **转发 token 时只能发一个头**：`apiClient.ts` 只设置 `X-Access-Token`。
> HTTP 头名大小写不敏感，若同时设置 `x-access-token` 和 `X-Access-Token`，
> undici 会把它们当成两个不同的头各发一遍，Tomcat 再用 `", "` 把重复头拼起来，
> 后端拿到的就是 `"token, token"` → JeecgBoot 报
> `The token was expected to have 3 parts, but got > 3`（Token非法无效!），
> 表现为"所有需要登录态的接口都调不通"。
> 后端只读 `X-Access-Token`（`JwtFilter` / `TokenUtils`），`Authorization` 与 `token` 头都不读。

### 5.2 AES 加密配置

- **算法**：AES-CBC 模式
- **Padding**：Pkcs7
- **Key**：`AES_KEY`（16 位）——**代码里没有默认值**，由 `nuxt.config.ts` 的 `requireSecret('AES_KEY')` 读取，缺失或为开源默认值则拒绝启动
- **IV**：`AES_IV`（16 位）——同上，无默认值
- **加密时机**：在 server 端加密（`server/utils/crypto.ts`），浏览器只传明文密码（HTTPS 传输也是加密的）
- **注意**：IV 目前由配置固定提供，CBC 模式下理论上应每次随机，需与 Java 后端保持一致

### 5.3 环境变量（.env）

变量清单以 `nuxt-shop/.env.example` 为唯一依据（复制为 `.env` 后填写）：

| 变量名 | 说明 | 默认值 |
|--------|------|--------|
| `API_BASE_URL` | Java 后端 API 地址 | `http://127.0.0.1:9951/api` |
| `STORE_CODE` | **本站点对应的店铺编码**（BFF 用 `X-Store-Code` 透传；留空时后端按域名兜底） | 无（示例值 `default`） |
| `AES_KEY` | AES 加密 key（16 位），须与后端一致 | **无默认值，必填** |
| `AES_IV` | AES 加密 iv（16 位），须与后端一致 | **无默认值，必填** |
| `SIGN_SECRET` | MD5 签名密钥，须与后端 `JEECG_SIGNATURE_SECRET` 一致 | **无默认值，必填** |
| `NUXT_OG_IMAGE_SECRET` | OG 图片签名密钥 | 无（示例值 `change-me`） |
| `STORE_SITE_URL` / `STORE_SITE_NAME` / `STORE_SITE_DESCRIPTION` | 站点域名与站名（canonical / sitemap / OG） | `http://localhost:3000` / `Cikian Shop` |
| `STORE_PUBLIC_ORIGIN` | Google OAuth 回调用的本站 origin | 无（生产必填） |
| `API_TIMEOUT_MS` | 调用 Java 后端的超时（毫秒） | `10000` |
| `COOKIE_SECURE` | 登录 cookie 是否带 `Secure` | `true`（http 隧道/IP 调试时才设 `false`） |
| `ALLOW_INSECURE_DEMO_SECRETS` | 危险开关：允许用 JeecgBoot 开源默认密钥启动（仅本地开发） | 不设置（即 `false`） |

> ⚠️ **重要**：`AES_KEY` / `AES_IV` / `SIGN_SECRET` 没有可用默认值，启动时会校验；
> 若仍是 JeecgBoot 开源默认值，前台会直接拒绝启动。生产环境必须使用与后端一致的**非默认**密钥。

## 六、国际化（i18n）

### 6.1 配置

- **策略**：`prefix` 模式 —— 所有语言都带 URL 前缀（如 `/en/`、`/zh/`、`/fr/`）
- **默认语言**：English (`en`)
- **支持语言**：中文(zh)、英文(en)、法文(fr)
- **语言包目录**：`i18n/locales/`
- **加载方式**：lazy 按需加载，减小首屏体积
- **浏览器语言检测**：只在根路径 `/` 自动跳转，用户手动切换后用 cookie 记住

### 6.2 语言透传机制

前端语言环境会通过以下方式传递给 Java 后端：

- 请求头 `Accept-Language`：如 `zh-CN`、`en-US`
- 请求头 `x-language`：如 `zh`、`en`

在 `server/utils/apiClient.ts` 中自动处理，优先级：
1. 读取请求头的 `x-language`
2. 读取 `event.context.locale`（@nuxtjs/i18n 解析出的）
3. 兜底默认 `en`

## 七、开发规范与约定

### 7.1 新增功能的标准流程

以订单模块为例（`server/api/order/index.get.ts` + `app/pages/orders/index.vue` 就是已落地的完整范例）：

**1. 新增 server/api（必须）**

```ts
// server/api/order/index.get.ts —— 文件名即路由：GET /api/order
export default defineEventHandler(async (event) => {
  // withAuth: true → 从 httpOnly cookie 取 token；转发目标由后端从登录态 + X-Store-Code 推导
  const api = createApiClient(event, { withAuth: true })
  return await api('/shop/order/store/list', { method: 'GET', query: getQuery(event) })
})
```

**2. 新增 composable（推荐，非必须）**

```ts
// composables/useOrders.ts（示意写法；当前订单列表直接在页面里取数，
// 已抽 composable 的参考实现见 composables/useCart.ts、composables/useFavorites.ts）
export const useOrders = () => {
  const orders = useState('orders', () => [])
  const fetchOrders = async () => {
    orders.value = await $fetch('/api/order')
  }
  return { orders, fetchOrders }
}
```

**3. 新增页面（必须）**

```vue
<!-- app/pages/orders/index.vue → 路由 /orders -->
<script setup lang="ts">
const { data: orders } = await useFetch('/api/order')
</script>
```

**4. 新增 i18n 文案（有多语言文本时）**

在 `i18n/locales/zh.json`、`en.json`、`fr.json` 中添加对应 key。

**5. 新增导航入口（需要时）**

在 `app/components/Header.vue` 中添加 `NuxtLinkLocale`。

### 7.2 请求方式选择

| 场景 | 用哪个 | 原因 |
|------|--------|------|
| 页面加载时展示的数据（普通 GET） | `useFetch` | 自动 SSR、去重、loading 状态 |
| 页面加载数据，但要自定义 key / 监听变量 / 合并多接口 | `useAsyncData` | 更灵活，完全可控 |
| 用户点击按钮、提交表单等一次性动作 | `$fetch` | 不需要和组件生命周期绑定 |
| composable 内部方法 | `$fetch` | composable 不在 setup 顶层同步执行 |

### 7.3 apiClient 使用规范

- **所有对接 Java 后端的请求都必须走 `createApiClient`**，不要直接写 `$fetch('http://...')`
- 需要登录态的接口传 `{ withAuth: true }`，会自动从 cookie 读 token
- 不需要登录的接口不传或传 `{ withAuth: false }`
- apiClient 会自动：加签名、加语言头、解包 result、统一错误处理

### 7.4 目录命名约定

- `server/api/` 下的文件按 REST 规范命名，动词通过 HTTP method 区分
  - `xxx.get.ts` → GET 请求
  - `xxx.post.ts` → POST 请求
  - `[param].get.ts` → 动态路径参数
- `composables/` 下的文件用 `useXxx.ts` 命名
- 页面组件放在 `app/pages/` 下，自动生成路由

## 九、待改进 / 注意事项

### 高优先级（安全类）

1. **生产环境密钥轮换**：`AES_KEY`、`AES_IV`、`SIGN_SECRET` 已**没有可用默认值**，非默认值校验会在启动时拦截
   （见 §5.3）；上线前仍需确认真实密钥与后端一致，且不要在任何入库文件里出现。
2. **清理调试日志**：`server/utils/apiClient.ts` 仍有 1 处 `console.log`（响应解包处），生产环境建议加 `import.meta.dev` 判断或移除。
3. **`COOKIE_SECURE` 部署口径**：默认 `true`；若线上用 http 隧道且未显式设置，登录 cookie 会被浏览器丢弃——
   属于部署配置问题，请按 §5.3 明确设置。

### 中优先级（代码健壮性）

1. **apiClient 响应解包方式**：直接改写 `response._data`（`server/utils/apiClient.ts`）属于 side effect 写法，
   类型推导不够精准，可考虑用包装函数替代。
2. **AES 固定 IV**：CBC 模式下 IV 理论上应该随机，目前由 `AES_IV` 固定配置，需与 Java 后端保持一致。
3. **重试策略**：`apiClient` 已配置 `timeout`（`API_TIMEOUT_MS`，默认 10s）且 `retry: 0`（有意不重试，避免重复写操作）；
   若后续要加重试，必须区分幂等与非幂等请求。

### 低优先级（架构一致性）

1. **语言清单已收敛**：新增/调整语言只需改 `types/store-locale.ts`（i18n、BFF `?lang=`、Intl 标签都由它派生），
   不要再在别处手工维护语言数组。
2. **订单/支付的后续扩展**：购物车表**刻意不存价格/库存快照**，下单时由服务端重新取价并留痕；
   后续接入真实支付渠道时，需沿用 `useIdempotencyKey` 与订单状态机的既有约束（见 `docs` 与根目录 `docs/订单模块-接口契约.md`）。

```bash
# 1. 配置环境变量（.env 已被 gitignore，不会提交）
cp .env.example .env
#    必填：API_BASE_URL、STORE_CODE、AES_KEY、AES_IV、SIGN_SECRET（须与后端一致）

npm run dev

# 4. 访问 http://localhost:3000
#    会自动跳转到 /en/（默认英文），可切到 /zh/ 看中文

# 5. 生产构建与启动（构建产物在 .output/）
npm run build
PORT=3001 npm start     # 隧道回源端口；本地开发仍用 3000
```

**对接 Java 后端：** 修改 `.env` 中的 `API_BASE_URL` 为你的后端地址（默认 `http://127.0.0.1:9951/api`），
并确保 `AES_KEY`、`AES_IV`、`SIGN_SECRET` 与后端完全一致，否则接口会因加密/签名校验失败而全部调不通。
